# 架构

## 分层

```
┌──────────────────────────── Electron 主进程 ────────────────────────────┐
│  src/main/index.ts                                                      │
│  窗口 · IPC 校验 · safeStorage · 剪贴板 · screen 工作区 · 生命周期       │
└───────────────┬─────────────────────────────────────────────────────────┘
                │ IPC（白名单 + Zod 校验）
┌───────────────▼───────────────┐        ┌──────────────────────────────────┐
│  src/preload/index.ts         │        │  src/renderer（Vue 3）           │
│  contextBridge 暴露 API       │        │  管理台界面，不触碰 Node/浏览器   │
└───────────────────────────────┘        └──────────────────────────────────┘
                │
┌───────────────▼─────────────────────────────────────────────────────────┐
│  src/core（纯 Node，不 import electron）                                │
│  engines/      Windows 注册表 + 标准目录 / macOS bundle / Linux PATH、    │
│                Flatpak、Snap 探测                                        │
│  cdp/          DevToolsActivePort、目标发现、Runtime.evaluate、窗口定位   │
│  launch/       参数构造、spawn、CDP 连接、停止与回收                     │
│  credentials/  safeStorage 抽象、凭据库、继承解析                        │
│  layout/       预设解析与窗口矩形计算                                     │
│  processes/    自有 profile 进程发现与清理、workspace 数据结构            │
│  service.ts    编排：站点 / 身份 / 视图 / 登录态 / 导入导出                │
└─────────────────────────────────────────────────────────────────────────┘
```

主进程内还托管两个与 UI 无关的服务：

- `src/main/mcp/server.ts`：本机 MCP 端点（AI 接入），只依赖 `WorkspaceService`；
- `src/main/embedded/`：内置浏览器表面（见下节）；
- `src/shared/transfer.ts`：导入导出文件的格式校验，纯数据、无 IO。

界面有四个窗口，共用同一份构建产物与同一个 preload：

- 控制台（默认路由）：浏览器与设置页两个视图，默认停在浏览器；站点 / 账号 / 更多三处
  管理内容以浮层盖在页面上（「更多」里是书签 / 标签 / 消息 / AI 记录）；
- 运行实例悬浮条：`index.html#overlay` 挂载 `overlay/OverlayApp.vue`，无边框、置顶、
  跳过任务栏。它不持有多余状态，只订阅同一份 `WorkspaceSnapshot`，点一下通过
  `Page.bringToFront` 把对应浏览器窗口提到最前（最小化则先恢复）；
- 切换回执：`index.html#focus-label` 挂载 `overlay/FocusLabelApp.vue`，无边框、不可聚焦、
  点击穿透，抬升窗口后显示两秒账号名；
- 授权卡片：`index.html#approval` 挂载 `overlay/ApprovalApp.vue`，无边框、置顶、跳过任务栏，
  固定在主窗口所在显示器的右下角。它回答一个必须有人回答才继续的问题（见「AI 接入」），
  所以与悬浮条共用窗口形态而不是并进去：两者的显隐条件与生命周期没有关系。
- 内置浏览器**没有独立窗口**：它画在主窗口的浏览器视图里。`BrowserPage.vue` 画地址行、
  左栏与页面标签行，页面本身是主窗口里由主进程托管的 `<webview>`。查找栏是舞台
  内右上角的浮层，不占文档流——它一出现就改变页面高度的话，页面会跟着重排。

  **页面宿主是 renderer 里的 `<webview>`**（[ADR 0011](architecture/adr/0011-webview-cdp-on-guest-pivot.md)），
  控制面仍是 CDP：main 在 `did-attach-webview` 里拿到 guest `webContents` 后
  `debugger.attach`。节点由 `GuestPool.vue` 在 App 根节点维护——**不在** `BrowserPage` 里，
  因为移出文档的节点会立刻销毁渲染进程，而打开控制台时浏览器页会卸载。主进程侧的适配层是
  `src/main/embedded/guests.ts`，纯逻辑（会话状态机、挂载硬化、等待队列）在 `src/core/cdp/`。
  没有第二套载体：`WebContentsView` 与它的定位/冻结/停靠资产已在 P4 全部删除。

悬浮条的位置保存在 `userData/overlay.json`（纯窗口偏好，不进入可导出的工作区文件）；
显示开关是 `settings.overlayEnabled`。

`src/core` 不依赖 Electron，所以能在纯 Node 下跑单元测试，也能被未来的 CLI 或 CI
直接复用。外部浏览器窗口不是 Electron 的 `BrowserWindow`，而是由 `spawn` 启动的独立
系统浏览器进程；内置浏览器的页面宿主是主窗口渲染进程里的 `<webview>`（控制面走 CDP），
两者的取舍见下文。

### 渲染层的共享控件

**有形状或状态的控件一律是组件，共享的只有布局与排版。** 判据是「这个东西有没有结构可
拥有」：按钮有变体、焦点态和禁用态，输入框有边框、焦点和尺寸，空列表有图标、文案和动作
槽——这些是组件。`.spacer`（占一个位置）、`.hint`（更淡的一段话）、`.mono`（一种字体）
没有结构可拥有，包一层组件只是多一次跳转，所以它们留在 `styles/base.css`。

`src/renderer/src/components/ui/` 下的共享控件：

| 组件 | 职责 | 关键属性 |
| --- | --- | --- |
| `AppButton` | 文字/图标按钮 | `variant`（default/primary/ghost/danger）、`size`、`type` |
| `IconButton` | 纯图标按钮 | `ariaLabel`（**必填**）、`variant`、`size`、`revealOnRow` |
| `LinkButton` | 内联文字动作 | `type`、`disabled` |
| `TextField` | 单行输入框 | `v-model`、`mono`、其余原生属性透传 |
| `FormField` | 标题在上 + 一个控件 | `label` / `#label` 插槽、`hint`、`as`、`grow`、`plain` |
| `Checkbox` | 复选框 + 文案 | `v-model`、`disabled` |
| `EmptyState` | 空列表的整套框架 | `text`、`note`、`#icon` 与默认动作槽 |
| `InputShell` | 输入容器：静止描边 + 聚焦时两条水平边从左向右铺开 | `size`（toolbar/hero）、`as` |

这条规则是踩出来的，两次：

1. 按钮。以前每个页面把 `.btn` 的样式复制进自己的 `scoped` 块，新页面只要「用了类名但没
   复制样式」，按钮就以裸文字渲染——流程页和它的新建弹窗就是这样上线的。
2. 表单字段。把 `.field` / `.input` 当全局词汇表也没能解决：二十个对话框各自在 `scoped`
   里重定义了一遍 `.input`，尺寸随之漂移（设备面板 26px，规范值 30px），内边距混用
   6/7/9px。单独看每一处都合理，摆在一起就是两套。

组件同时拥有结构与样式，漏法在结构上就不可能发生。页面特有样式仍通过 `class` 透传到根元
素（例如流程图里更紧凑的字段），但基础的形状、间距、悬停与焦点态不再由各页定义。

**组件根元素保留原来的类名**（`AppButton` 根仍是 `.btn.primary`，`TextField` 根仍是
`input.input`）。这是有意的：`scripts/e2e-*.mjs` 与截图脚本按这些选择器找控件，换掉类名
要同步改二十几处断言，而收益为零。变化的是**谁有权写**这些类——由
`tests/contracts/ui-components.test.ts` 守护：`components/ui/` 之外再出现 `class="btn"` /
`"input"` / `"field"` / `"check"` / `"link-btn"` / `"empty"` 即失败。

**搜索框是一个控件。** 地址栏与新标签页的搜索框都用 `InputShell`：它画底色，并用一层 SVG
画完整轮廓——静止是 1px 细线，聚焦后是 2px 主色线，中间跑一圈 2px 的短划（500ms，一遍即止）。
轮廓从头到尾都是 SVG，不用 CSS `border`：边框是另一条线、粗细也不同，2px 的扫光跑在 1px
边框上时，最终高亮看起来会比扫光细。两处曾经各写一套，地址栏浅色下的聚焦色取的是
`--accent-text`（深褐金，为白底正文选的颜色），看起来是一条脏线。扫光的动画由
`:focus-within` 纯 CSS 触发，失焦即复位，不需要 JS 状态。


**站点与账号两页都只有表格一种布局。** 每组一个列头，行与列头共用同一份 `--site-cols` /
`--id-cols` 网格模板，因此列始终是列。曾经有一个 `CollectionViewToggle` 提供「列表 / 表格」
两态，但两者共用同一份行标记、同一条网格线，差别只有 6px 行距和一个列头——这不是两种视图，
是同一个表格少画了一行字。删掉切换后布局无条件成立：每组的列头就是表格的顶盖，组内最后一行
是桌脚（`.last`），中间的行只保留侧边与下边框。行结构（`.env-card`、`.site-grip`、`.id-card`）
与拖拽、选择钩子不变，由 `e2e-collection-tables` 断言列对齐、单行、顶盖与桌脚。

**操作列里只有一种控制。** 站点行与账号行的操作列统一为图标按钮：同一簇里不混文字动作，
不留一处文字一处图标；控件高度一致（`IconButton` 的 24px，紧凑启动控件的 `compact` 变体
同样固定 24px），且整簇靠列尾右对齐。曾经账号行三个文字动作加一个编辑图标、站点行一个
文字按钮加一个分体启动控件，两页都在同一列里出现两种宽度与两种字号——用户看到的是
「有文字有图标，很乱」，以及「操作列间隔这么大」。同簇两种尺寸由
`e2e-collection-tables` 的 `actionsScript` 断言：控件数、无文字、高度集合唯一、右边缘唯一。

**所有写操作的表单都在 `Modal` 里。** 页面正文只留列表与筛选，新建、编辑、改名一律开
弹窗：一个按需出现的表单会把下面的列表挤下去，而内联的编辑会重排它所在的那一行——
档案页的新建表单甚至在保存成功后仍然留在页面上，用户看到的是一份没提交的表单加一行
已经写进列表的数据。表单提交成功才关闭弹窗，失败时保留输入（`run()` 失败返回
`undefined`，调用方据此判断）。地址栏、搜索框、地址列表的添加行是例外：它们本身就是
那块界面，不是列表上的编辑器。由 `tests/contracts/forms-are-dialogs.test.ts` 守护。

### 悬停提示：`v-tooltip`，不用原生 `title`

纯图标控件的说明走 `src/renderer/src/directives/tooltip.ts` 的 `v-tooltip`（app 级注册）：

```vue
<button v-tooltip="t('app.browserReload')" :aria-label="t('app.browserReload')">…</button>
<button v-tooltip="{ text: label, placement: 'top' }">…</button>
```

原生 `title` 不做成「少写一个属性」的替代：它等约一秒才出现、字体和缩放开不走应用自己的一套、
位置由系统决定，也没法跟主题。它此前留下的理由是内置页面曾是主进程的原生视图、画在渲染层
之上，任何自绘浮层都会被盖住——页面改成渲染层 DOM 里的 guest 之后，这个理由就不成立了。

运行时由 e2e `e2e-chrome-geometry` 断言（存在、可见、藏在窗口内、`pointer-events: none`、
移开即消失），源码层由 `tests/contracts/tooltips.test.ts` 守住：浏览器工具栏里不留
`:title="t(...)"`。长 URL 的页签仍用原生 `title`——那是「系统会截断并可复制」的另一种需求。

### 右上角归谁：`--window-controls-width`

`titleBarOverlay` 下 caption 按钮由 OS 画在客户端区域之上，所以每个触及窗口右上角的表面都要
让开它。宽度不写死：`src/renderer/src/composables/windowControls.ts` 用
`navigator.windowControlsOverlay.getTitlebarAreaRect()` 实测后发布成 CSS 变量（Windows 11
@1.5x 实测 137px；历史上三个文件分别硬编码 148/140/146）。

**这个保留是有条件的**：浏览器视图右上角是页面标签行，谁在右上角谁让位，另一个
把这部分还回去——两边同时预留会留一条死空。由
`e2e-chrome-geometry` 的几何断言守住。

**管理页与设置页的页头也要让开，但只让一次。** 它们没有标签条，页头右侧直接就是 caption
按钮。让位由两处共同完成：`.pane` 顶部有一条 `--titlebar-height` 高的拖拽带（`.pane-band`，
只在非浏览器页出现，保证窗口任何高度都能拖动），它先把整条 caption 带留出来；页头因此从这条
带下面开始，**不再重复扣一次 caption 宽度**。设置页自己那条标题栏是 `drag-region`，同样不压
caption 区。

历史上 `PageHeader` 曾经额外加过
`padding-right: max(0px, calc(var(--window-controls-width, 0px) - 28px))`，是在顶带还不存在时
补的。顶带上线后这条内缩没有删，两处让位叠加，每个管理页的主按钮都被推到比内容右缘左缩
100 多像素的位置——右侧空出一整条，页面看上去是歪的。而且它把「页面左右内边距 = 28px」写死
在里面，消息页（20px）就算在生效时也是错的。**保留只放在壳层一处**；漏掉时页面右上角的主按钮
（「新建身份」「新建站点」）会被三个系统按钮切掉一角，重复时按钮又对不齐内容。几何上由
`scripts/tmp-probe-layout.mjs` 那类探针量「页头动作右缘 vs 内容右缘」来验。


## 两种浏览器表面

两种表面共用同一套身份、凭据与站点模型，区别只在承载方式（决策记录见
[ADR 0006](./architecture/adr/0006-embedded-browser-first.md)）：

| | 内置（`<webview>` guest） | 外部（系统浏览器） |
| --- | --- | --- |
| 可控性：截图、接管、录制、并排、布局 | 完整 | 受限 |
| 保真度：真实版本、扩展、DRM、企业策略 | 较弱 | 最强 |
| 默认用途 | AI 驱动、静默运行、日常操作 | 确认「真实用户环境里也一样」 |

**没有全局启动模式：表面在启动点选。** 每个启动点是一个组合控件
（`ui/LaunchSplitButton.vue`）：左半直接执行主路径（内置浏览器），右半的箭头展开浏览器
列表——第一项是内置，后面是扫描到的每一个真实浏览器（被禁用的置灰并给出原因）。
站点页与账号页的行内启动都是这个控件。

**外置启动不参与标签页管理。** 浏览器页的 `+` 与批量启动都固定
内置：内置的页面模型是这套界面的主体，往里面加「这一页要不要开成真窗口」
会把它拆成两套逻辑。外置窗口有自己的入口——站点页与账号页启动控件的右半
——它们打开的是独立的系统窗口，与内置舞台互不相干。

**档案在外置侧也是独立的一份。** 内置用 `persist:profile-<id>` 分区，外置用
`profiles/profiles/<profileId>` 目录；两边从不共享 cookie（不同 Chromium 构建写不同位置），
所以「工作档案」在外置里是同一套命名下的另一个登录态，和现在「内置登录过、外置仍要再登一次」
完全一致，不新增需要解释的语义。一次性档案（干净会话）在外置用 `clean-<uuid>` 目录，窗口
关闭即删。

内置侧的落点固定：账号页点一张卡片就是在单格容器里新建一个页面并让它上台，页面已经在跑
也是这样；批量启动按选中的账号建页，第一个上台、其余在后台待命——整个批量（建页、摆位、
回收）由主进程一个 IPC 承担（`IPC.embeddedLaunchBatch`），
页内并发建页（并发度 3）、任一失败整批连同容器一起回收。`openEmbeddedView` 给每个新建的
页面排一次自动填充，所以「批量启动」与「点账号」在填写凭据上表现一致。

**「+」有两半，各答一件事**（`OpenSiteButton.vue`）。主半是空白答案：一下就在默认档案里
开一张空白页——应用自己的新标签页，不导航站点、不问账号；浏览器里其它「+」都是这个行为，
先问「用谁」会把「就想开个空白页」变成一趟预选了站点的账号选择。箭头半是账号答案：打开
选择窗（`SiteOpenMenu`）挑一个账号开页（落到起始地址并自动填充），或走站点自己的两条
出口——用默认档案打开、用一次性会话打开，两者固定在选择窗右侧顶部，一个站点有三十个
账号也压不掉它们。选择窗是**主动才走的次级入口**：这里的页面通常属于某个账号，而账号
决定会话分区。`lockedSiteId` 用在容器已经指明系统的地方——容器自己的「+」——此时选择窗
只列该站点的账号。

页面标签条上的「+」**不是**这个组件：往运行中的实例加页继承该实例的会话，没有可问的
问题。同一条打开路径带 `{ identityId }` 或 `{ url, clean }`，由主进程统一处理
「身份 → 起始地址 + 自动填充」。

缩放走 `webContents.setZoomFactor`，因此天然是**每页一份**：页面各有自己的 `webContents`，
没有共享的缩放状态。`settings.browserZoom` 只是「没被手动调过的页面的默认值」，
`zoomBy` 在页面上按 Ctrl +/-/0 时写入 `zoomOverride`（仅内存，随标签页消失），并在
`before-input-event` 里拦截——网页自己会吞掉这些按键。

刷新快捷键同理分两层拦截：焦点在页面里时由页面的 `before-input-event` 处理
（Ctrl+R / F5 重载、Ctrl+Shift+R 绕过缓存），焦点在应用壳上（地址栏、dock）时由主窗口层兜底，
重载的总是「壳当前框住的页面」；DevTools 面板聚焦时沿用既有行为（转发给被测页）。
Electron 不绑任何默认刷新，不拦就是死键。

**页面分辨率是另一根轴，也有两级作用域。** 缩放改变的是页面在自身布局尺寸下的比例，分辨率
改变的是布局尺寸本身（媒体查询、`innerWidth` 都按目标值算，页面等比缩放居中显示）。
`settings.browserViewport` 是工作区默认，工具栏的入口改它；单个页面在标签右键菜单里选
「跟随全局 / 自适应 / 固定尺寸」。解析顺序只有一条
（`browser.ts` 的 `viewportOf`）：页面自己的选择优先，否则用默认，否则铺满格子。
`viewportOverride` 的三态是关键：缺省=继承、`null`=显式自适应、对象=固定；只有页面明确
选过才允许和默认不一致。改分辨率的菜单项选中后**立即关闭菜单**——不关菜单就看不到重排
的结果。清除默认值必须传 `null` 而不是
`undefined`：设置经 `JSON.stringify` 过 IPC，`undefined` 会整键消失，主进程收不到要改的信号。

**并排观察交给拆窗与系统分屏。** 应用内舞台恒为单格（ADR 0012）；同一账号两页并排的需求
由「拆出到独立 OS 窗口」（见下文拆窗一节）与操作系统的窗口排布承接，应用内不再复制这套
几何。内部槽位机制（`slotTabs` / `slotPages`）保留为单槽运行。

内置表面在 `src/main/embedded/`：

- `browser.ts` 管理主窗口里的**浏览器实例**与页面。舞台恒为单格：容器记住台上是哪个
  实例的哪一页，其余实例的页面继续在窗口外运行（登录态保持、AI 可驱动）。页面按身份使用
  独立 `persist:` 分区（`embeddedPartition`），
  **与外部浏览器的 profile 目录分开**：两者由不同 Chromium 版本写，让 Electron 直接
  打开新版 Chrome 写过的 profile 会有降级迁移的风险，分开也避免内置侧污染正在用的
  外部登录态。
- 没有身份的页面属于**默认档案**（[ADR 0009](./architecture/adr/0009-daily-profile-and-bookmarks.md)）。
  账号各自持有独立的会话分区；档案作为独立管理对象的页面已并入账号模型，剩下的档案概念
  是无账号页面的落点。
  - **默认档案**（`id: "default"`）是一个固定的 `persist:` 分区，新标签页、书签与地址栏
    输入的地址默认都落在那里，登录一次长期有效。它沿用旧字符串 `persist:embedded-clean`
    是为了接住用户升级前已有的登录。**这个字符串是存储实现，不是语义**：MCP 的标签列表在
    返回前删掉 `partition`，只保留 `clean` 与 `profileId`，否则一个读到 "clean" 的客户端会
    把默认档案误判成一次性会话。
  - **干净会话**（`id: "clean"`）是每个浏览器一个不带 `persist:` 前缀的内存会话
    （`embeddedCleanPartition`），退出即消失。
  - **自建档案**（`persist:profile-<id>`，`embeddedProfilePartition`）与默认档案同构，
    只是名字不同——它们之间的隔离是靠分区，不是靠 UI 的约定。界面不再提供新建档案的
    入口；检测到存量自建档案时，设置页出现一次性迁移邀请：合并到默认档案（磁盘数据
    保留，已登录页面需重新登录）或保留并不再提示（`profilesMerged` 标记已答复）。
  - `defaultProfileId` 决定「没指定档案时落在哪」。它只能指向持久档案：把干净会话设为
    默认会让每个书签都变成未登录页，而用户看不出这和登录坏了有什么区别。
  - 档案列表在 `repairProfiles` 里兜底：设置文件缺字段、被手改删掉内置项、或
    `defaultProfileId` 指向已删除的档案，都在加载时修好，否则表现是「打开书签得到空白页」。
  - 分区是**存储边界**，所以 `guestPartitionAllowed`（`core/cdp/guest-policy.ts`）列着
    本应用会创建的每一种前缀。`will-attach-webview` 拒绝时不打印任何东西，漏掉一个前缀
    的表现是开页面等十秒超时——见 `docs/engineering/踩坑库.md` 的档案条目。
- **在默认档案里登录会被提议存成账号。** 书签、地址栏输入、新标签页搜索最终都落在默认档案；
  在那里提交登录表单时，页面里的 `LOGIN_CAPTURE_SCRIPT` 报出用户名，密码留在主进程
  （`LoginCaptureStore`，渲染层只拿到 token）。点「保存账号」时：
  1. 该 origin 没有站点就**当场建一个**（名称取 hostname，登录路径取当前页），不再要求先手填
     一整套站点字段——这是这条路径存在的理由；
  2. 账号按独立身份落库，拿到自己的 profile；
  3. **保存就到此为止，不启动浏览器。** 曾经在保存后顺手以该身份打开一次（"页面已是登录态，
     等于验证密码存对了"），但用户要求的是保存，不是打开：一个自己冒出来的窗口读起来就是应用
     擅自行动。保存结果由 toast 确认，想打开从身份列表点一下即可。

  重复登录同一账号只更新密码，不再建第二个身份（分会话）。

  提示条只在没有对话框时渲染。模态会锁 `body { pointer-events: none }`，而提示条是 `body` 的
  直属子节点、位于 dialog portal 之外——它能被看见（`z-index` 更高）却点不动，表现得像卡死。
  账号表单本身就是提示的答案，两者不必同时在场；捕获不受影响，表单取消后提示条自己回来。
  首次启动的**指南不算**这个条件（见 `captureCovered`）：它是开场白而非用户打开的工作面，
  让它压制提示会把新用户第一次登录的捕获藏在自己还没读完的介绍下面。

  保存不影响默认档案本身：它只是在旁边多出一个独立身份，默认档案的登录态与后续打开
  行为都没有变化。这一点放在提示标题旁的 info 图标里，不常驻占版面。

- **多租户站点的账号是「租户 + 用户名」。** 捕获脚本把密码框之前的其余文本框一并上报
  （标签取 placeholder / aria-label / name），去重按「站点 + 用户名 + 租户」比较：同一用户名在
  另一个租户下是新账号，不是重复。保存时租户随之落库并预填进账号表单——少了这一维，用户换个
  租户登录就完全看不到提示，而不是收到报错。
- **提示会走开，记录不会。** 主进程里的 `LoginCaptureStore` 是一个列表，提示条只显示最新的
  一条；关掉提示只是收起它，密码仍留在主进程内存里（随进程结束消失，不落盘）。要看历史就进
  「消息」页——见下。

### 消息中心

一个列表装三类过去没有共同去处的事：**登录捕获**、**账号问题**、**应用通知**。它们回答不同问题，
但都是「我不在的时候发生了什么」，而没有列表时唯一的回看方式是把事情重新做一遍——退出重登去
找捕获、重新启动去看失败。

**AI 操作不在这个列表里**，它是记录不是通知：见下面「AI 记录」。把两者放在一起时，一次自动化
就能写满列表，把真正的通知挤出去。

- 落在 `<userData>/messages.json`（`core/messages.ts`，纯 Node），上限 500 条，最旧的先丢。
  界面在 `MessagesPage.vue`；入口两个：左栏「更多」里的消息分区，以及工具栏的铃铛。铃铛**常驻**，
  未读时只加一个红点——数字会撑宽按钮，把它和旁边的图标挤得不对齐，而「9+」也没人真的读。
- **铃铛开浮层，不跳页。** 点它直接切到消息中心等于把一个「瞥一眼」的动作变成一次导航：消息
  中心占据整个面板，浏览器页被卸载，而那一页没有「回」的入口。浮层（`[data-bell-panel]`）列出
  最近 5 条，底部「查看全部消息」才进消息中心。浮层锚在铃铛右缘（与下载面板同一范式：
  `position: absolute; right: 0`），点外部与 Esc 关闭。
- **单条详情也是浮层，且不撑开列表。** 点一条消息（铃铛浮层里或消息页上）浮出
  `MessageDetailLayer`：完整正文、时间、动作、失效原因。它**不能**在列表内就地展开——展开会撑高
  那一行、把后面整体下移，而用户正在这张列表里挑选，行在指针底下换位比跳页更糟。铃铛浮层里这层
  开在左侧（`placement: "left"`），不遮住列表也不撑高它；消息页上开在行的下方。Esc 只关最内层。
- **行表现只有一份。** 标题翻译、图标、时间、失效原因、动作标签与执行都来自
  `composables/messageRows.ts`，消息页与浮层共用。两处各写一份的那天，只要其中一处加上第四种
  kind，另一边就会显示成裸 key 或没有按钮。
- **`stale` 每次呈现时重新求值。** 它由主进程在读取历史时判定（token 只活在进程内存、tab 可能
  已关）。消息页在 `onMounted` 调 `refreshMessages()`，铃铛浮层在每次打开时刷新——一个只读一次
  的界面会把过期判定永久固化，表现为「按钮在、点了没反应」。
- 处理掉一件事就要把对应的行标成已读，否则红点会一直亮着说「有新闻」。登录捕获保存后会按
  token 回找那一行并标已读（`markReadByCaptureToken`）——保存就是把它读完了。
- 行里的「能做什么」存成**数据**而不是回调：`login-capture`（token 只在进程内有效）、
  `identity`（重新登录）、`tab`（切到那一页）。**是否还有效由主进程在读取时判定**，失效的行
  标 `stale` 并只保留事实，不再显示按钮——历史跨重启仍然说得出「当时发生了什么」。
- 标题存 **i18n key + 参数**，切语言时历史一起变；不可翻译的内容（服务端报错、页面标题）放
  `detail`。
- 去重按「同一 kind + 同一标题 + 同一目标」在窗口内合并成一行，避免定时检查把历史刷满。
- 这条路径把「先建站点、再录账号、再启动」的手工顺序压成了「打开、登录、保存」。完整手工路径
  仍然在，两者落到同一套数据模型上，没有第二条启动链路。
- 页面自己开的弹窗（`setWindowOpenHandler`）继承所在实例的 `instanceId` 与分区，
  只改变该实例当前显示的页面，不会成为新的格位候选——这和外部模式里「一个窗口自带
  标签页」是同一个语义。`clean` 也随实例继承：干净会话里打开的登录弹窗不会掉进默认档案。
- `cdp.ts` 通过 `webContents.debugger` 说 CDP，**不开放任何调试端口**。调试端口无鉴权，
  本机任意进程都能驱动浏览器；进程内通道的唯一入口是已鉴权的 IPC 与 MCP。
- `bounds` 是**舞台相对**坐标，由 `guestNodeRect` 与舞台原点相加得到节点的窗口位置。
  不在台上的页面保持完整尺寸、停在窗口左缘之外：整页移出窗口会让合成器把它 cull，截图
  命令永不返回；缩成 0×0 或 `display:none` 则会让页面里的可见性判断全部答 false。
  规则只有这一个纯函数，主进程与渲染层共用。

由此带来的几条约束：

- 内置模式与外部模式各自维护登录态，切换表面要重新登录一次；切换必须由用户显式触发。
- 扩展、DRM 内容、企业证书策略在内置模式下不可用，需要保真结论时用外部模式复核。
- 截图优先走 `Page.captureScreenshot`；窗口最小化时它会停摆，此时退到
  `webContents.capturePage()`；窗口完全隐藏两者都不行。

### AI 驱动内置表面

MCP 暴露的浏览器工具覆盖：列标签、开视图、开标签（按身份分区）、导航、读页面、查可见性、
点击、输入、批量填表、等待条件、填充登录、截图、执行表达式、文档级脚本注入、切布局、
固定格位、调整标签页顺序 / 归属视图、切换实例当前页、关标签。完整的档位、来源闸门、
时限与返回形状见 [`docs/engineering/ai-tools.md`](./engineering/ai-tools.md)——那张表由
`tests/contracts/ai-tools-doc.test.ts` 与源码比对，不靠人维护。页面读取返回可见元素的
角色、可访问名称、稳定选择器与**表单项旁边的标签文字**，隐藏元素不出现——这正是「这个
账号实际能看到什么」。

**AI 开页面不抢前台，也不占台。** `open_browser_tab` 与 `open_browser_view` 都不调用
`focusPage()`：不抬窗口、不把界面切到浏览器页。UI 入口（工具栏「+」、账号卡、视图启动）
仍然抬窗口——那是用户刚刚点了一下，想看到结果；AI 是把页面当工作区在用，往往在用户读
文档或改设置时开页，每开一个页就把窗口顶到最前面会让这个端点没法用。`open_browser_tab`
的页面也不进任何容器：它落自己的实例（干净会话或身份分区），台上的格位与用户的选中都
不动，闲置后照常入冻；要上台由用户点实例条，或 AI 用 `open_browser_view` /
`pin_browser_tab` / `activate` 显式摆位。

- 不上台也照样能工作：台外节点保有完整尺寸的停靠框，所以截图与 DOM 读取在后台照常可用。
- 输入类工具开启 `Emulation.setFocusEmulationEnabled`，窗口不在前台也能派发事件。
- `openEmbeddedView(viewId, { reveal })` 用同一个函数服务两边，差别只有这一个参数。

**定位元素用语义目标，不是位置选择器。** 每个交互工具都接受 `label`（表单项旁的标签）、
`text`（按钮上的文字）、`role`，`selector` 仍然保留。原因是实测出来的：组件库的表单里
label 与 input 分属不同子树，快照只能表达成长串 `:nth-of-type`，多一个条件字段整条链就断；
而人从来不读这种路径，人读的是「用户名」。解析器按三种形状找控件：`<label for>`、
包住控件的 `<label>`、以及「wrapper 里同时有 label 与控件」（Naive UI / Ant Design /
Element Plus）。从 label 向上找作用域时，只有当该作用域里**恰好一个**可见控件才认，
多个控件时要求作用域自身的文字仍提到这个标签——否则整个表单会把所有字段都抢走。

- 点击与输入走 `Input.dispatch*` 真实输入事件，不是脚本 `click()`，否则框架不会响应。
- 输入类操作前会开启 `Emulation.setFocusEmulationEnabled`：窗口在后台时渲染进程报告
  `document.hasFocus() === false`，Chromium 会直接丢弃输入事件，而 `Runtime.evaluate`
  仍然工作——不开启时表现为"选择器明明对，点击却没反应"。
- **`wait_browser` 在页面内轮询。** 菜单、抽屉、toast 都是异步渲染的，没有等待语义时
  AI 只能 `sleep → read → sleep → read`，每一轮都是一次 MCP 往返，而两次调用之间页面
  还会自己变（菜单失焦自关、选项晚一帧出现）。条件有 `visible` / `hidden` / `text` /
  `url` / `value` / `network-idle`，一次调用等到条件成立或超时。导航会销毁执行上下文，
  所以 `wait()` 在上下文被销毁时用剩余时间重试——否则「点登录、等控制台」永远报错。
  `hidden` 把「元素已从 DOM 移除」也算成立：toast 消失常常是移除而不是淡出。
  `network-idle` 等的是「没有在飞的 fetch / XHR，且已经安静 `quietMs`」，回答的是
  「保存到底有没有发出去、发完了没有」，不需要预先知道哪个元素会出现。它**不**声称页面
  已停止变化：SSE / 长轮询页面在这一口径下永远不空闲，那种页面应当改等具体元素。
- **`fill_browser_form` 一次填完整个表单。** 逐字段调用不只是往返多，中途一次超时还会让
  页面停在半填状态。返回里每个字段单独标记是否密码，审计日志只打码那几个——把整条调用
  打码会让日志失去价值，不打码则密码必然落盘。
- 填充登录的密码只存在于主进程，工具返回值只有摘要；跨域页面拒绝填充。
- **自动填充也按标签找字段**：`buildFillExpression` 的 `labelText` 除了 `labels` /
  `aria-labelledby` / 包住的 `<label>`，还会向上找「唯一一个 label 元素」的作用域。
  缺这一步，组件库后台的额外字段（租户名）永远填不上——这是真实环境里先踩到的。
- **输入到密码框的值会被审计日志打码**：`type()` 从页面读回输入框自身的 `type`，是密码就回
  `secret: true`，MCP 层据此把参数 `text` 换成 `[redacted]`。靠参数名匹配不够——创建租户时
  密码也是走 `type_browser_text`，那个参数叫 `text`。
- 布局与格位工具作用于「台上的视图」：AI 不需要先知道视图 id，全是扁平标签时切布局会
  先把它们组成视图——这是 AI 侧的一次调用便利，界面上没有对应的自动建组行为。
- 开标签会自动把主窗口切到浏览器页，否则标签建在窗口外，用户看不到 AI 在做什么。
- `move_browser_tab` 与界面拖拽是同一套落点：相对某页之前 / 之后、加入某个视图、或移出视图。
  `set_tab_page` 切换的是「一个实例当前显示哪一页」——一个格位是一个实例，实例里的弹出页
  不占新格位。
- 内置表面是懒创建的可选依赖：测试里可以注入假实现，未打开过内置浏览器时工具会给出
  明确错误而不是崩溃。

### AI 能看见什么

浏览器工具不是「截图 + 盲点」。四类信息各有出处，边界也各不相同：

| 能力 | 工具 | 来源 | 已知边界 |
| --- | --- | --- | --- |
| 页面结构 | `read_browser_page` | 注入脚本的可访问性快照 | 隐藏元素不报；跨域 iframe 不可达 |
| 控制台 | `read_browser_console` | 主进程 `console-message` 事件 | 只覆盖该页所在的渲染进程 |
| 网络 | 同上 + `wait_browser` 的 `network-idle` | 注入脚本包 `fetch` / XHR | 只覆盖页面 JS 发起的请求 |
| 画面 | `screenshot_browser_tab` | CDP 或 `capturePage` | 完全隐藏的窗口拿不到 |
| 性能 | `measure_browser_performance` / `read_browser_performance` | CDP `Performance.getMetrics` | 只有主线程指标；没有 tracing 的调用树 |

**性能是事实，不是让 AI 自己算。** AI 判断「页面卡不卡」原本只有截图和 `evaluate` 两条路：
截图看不出耗时，自己在页面里跑 `performance.now()` 循环测的是它那段脚本，不是页面的渲染
与 GC 开销——比没有数字更糟。所以这两个工具直接把 CDP 的同一份计数器给出去，出处与
Chrome 性能监视器一致。形状是**汇总而不是曲线**：模型读不了走势图，一百个原始点会让它
在正文里做算术并且做错；`{avg, max, maxAt, last}` 能直接回答「有没有卡、卡在哪一刻」，
`maxAt` 还是相对毫秒，能与 `read_browser_console` 里日志行的时间戳对上。要逐点数据的
调用方（自己算任意统计量）走 `read_browser_performance`。

采样的所有权是分开的：面板在它的页显示时拥有采样器，切走即停；AI 的采样没有页签可看，
改由**闲置超时**回收（连续读取会续期），并且在面板已经采样时**接管而不重启**——一次 AI
读取把用户正在看的图清空，是那种「功能正确但用户会骂」的错误。两次连续读取之间也在采样，
这才是「测一次 → 点一下 → 再测一次」能看见那次点击开销的原因。

**快照是扁平列表，但带 `parent` 与 `depth`。** 保持扁平是因为每个使用者本来就把它当
列表处理，树形会把主要是文字的页面翻倍；而「这个按钮在哪个对话框里」只需要一个下标。
`parent` 指向最近的**被上报**祖先（可见，且是控件 / 标题 / 自有文字的叶子），不是 DOM
父节点——被跳过的层没有模型能用的信息。跨 shadow root 与同源 iframe 的归属按同一条链
解析。

**控制台走主进程，网络走页面。** 不是随手选的：页面侧包 `console` 只能在文档存在之后
安装，而「页面为什么没起来」恰恰发生在之前；`console-message` 从第一个文档的第一行就会
触发，还能报出页面脚本包不住的东西（网络错误、CSP 违规、混合内容拦截）。反过来，
「请求是否在飞」只能靠包 `fetch` / XHR 得知，而长期挂着的 CDP 会话正是本应用为躲开
反自动化探测而拒绝的东西——guest 会话空闲 1.5 秒就释放。两个来源在
`readPageActivity()` 合并，读取即清空：它回答的是「上次读取之后发生了什么」。

**截图默认只返回路径，`inline: true` 才带图像。** 本地客户端能直接打开路径，省 token；
容器或远程的 AI 够不到那个路径，没有图像就等于看不到画面。图像走 MCP 的 `image`
内容块，元信息仍留在 `text` 块里，所以只渲染文本的客户端也不会拿到空结果。

- **离开舞台的页面保持完整尺寸、停在窗口左缘之外**（`guestNodeRect`）。三条实测约束：
  1. 坐标不能是 `-100000` 这种大负数：渲染器会把视口算成 0×0，脚本照跑但整页按零宽度
     布局，凡是依赖渲染几何的判断（这段文字可见吗、按钮在哪）都会得到「什么都没有」。
  2. 不能缩成 0×0 或用 `display: none`，原因同上；也不能用 `visibility: hidden`——它保住
     了尺寸，却让页面内的 `checkVisibility()` 对每个元素答 false，并拒绝截图。
  3. 整页移出窗口会被合成器 cull，`Page.captureScreenshot` 从此永不返回。所以停在
     `x = -width`：不在窗口内、拿不到指针，但离得足够近，截图前搬回来只要一帧。
- 节点尺寸由 `bounds`（舞台相对）加舞台原点得到，主进程与渲染层共用同一个纯函数。
- 窗口 resize 会重新上报舞台矩形，页面节点跟着重排。
- **舞台尺寸要经过响应式状态，不能直接读 `clientWidth`。** 实例行与标签行的几何由渲染层按
  舞台矩形算出来，页面节点按 `setStage` 上报的矩形铺，两者必须同源。`reportStage` 把
  `clientWidth` 写进 `stageBox` 这个 ref，消费它的 computed 依赖它，ResizeObserver 触发的
  重报就同时更新两边——直接读 `clientWidth` 的 computed 不会因为布局变化重算，页面已经变宽
  而头部还停在旧宽度，右边留出一条死带。
- **站点图标在主进程内联。** `EmbeddedTab.favicon` 是一个 `data:` URL，渲染层只负责画。
  渲染层 CSP 是 `img-src 'self' data:`，不加载远程图片；更重要的是图标要用页面自己的会话去取
  （登录态、区域、Cookie 都跟着走），只有主进程做得到。`inlineFavicon` 把类型与大小规则抽成
  纯函数，避免为了测它而启动 Electron。
- **停放页空闲后睡眠（`aiIdleFreeze`，headless 关闭，`ENSEMBLE_SLEEP_TEST` 可开）。**
  页面挪出窗口只是看不见，Chromium 仍视其为「可见」，原生后台节流永不触发——应用窗口在屏上
  时，每个停放页（包括 3D 首页）都会满速渲染。真正生效的是 CDP
  `Page.setWebLifecycleState: "frozen"`：页面 JavaScript 整体挂起（冻结页上 evaluate 永不
  返回），3D 场景随之停。停放页闲置 60 秒（窗口期内无任何 CDP 流量）后由 10 秒一轮的扫描
  冻结，**扫描在浏览器构造时无条件启动**。AI 的每条命令在 `GuestCdp` 的 `send` /
  `evaluate` / `screenshot` 前都会 **await** 一次唤醒，回台、导航、窗口恢复与托盘归位也会
  唤醒，所以截图、点击永远落在活页面上；`lifecycle()` 自己不走这条钩子，否则扫描的冻结会把
  自己标成活动。
  扫描的判定集中在 `src/core/cdp/sleep.ts` 的 `shouldSleepPage`，它把用户可见、已冻结、
  无载体、加载、崩溃、空白、DevTools、有声、`sleepPolicy: "never"`、AI 窗口与**命令在途**
  一次性判完。豁免按同一顺序由 `sleepExemptReason` 给出短串，与判定同源（事实组装只在
  manager 的 `sleepFacts` 一处），随页面状态发布为 `sleepExempt`，AI 据此判断谁在占资源。
  「用户可见」不是占格：它是台上实例的当前页 × 宿主窗口可见——窗口最小化、隐藏到托盘时
  台上页照常入冻（minimize/hide 即扫一轮，restore/show 唤醒台上页），批量启动的后台成员与
  AI 经 `open_browser_tab` 开的页（落自己的实例、不占格）同样按闲置入冻。
  命令在途由 `CdpExecutor.busy()` 报告，guest 只数 **AI 命令**（`GuestCdp.aiInFlight`）：
  观察通道（性能采样的 5 Hz 心跳等）不算忙碌，否则扫描的宽限刷新会被采样命令连续续命，
  被观察的页永远睡不着。扫描遇到忙碌页就刷新 AI 窗口并跳过——一个跑了几分钟的 `evaluate`
  不会在脚本中间被冻住，命令结束后仍享有完整宽限期。
  每个标签页可单独设「永不休眠」（右键菜单，`setSleepPolicy`），设为 never 时立刻唤醒；
  默认策略就是「跟随默认」。休眠页在 favicon 槽显示蓝色雪花，永不眠页在标题旁显示图钉，
  两处标签的 `title` 也写明状态；实例行条目上有冻结标识（全部页冻结灰标、部分冻结半标，
  映射在 `src/shared/instance-freeze.ts`）。`sleepGraceMs` / `sleepSweepMs` 是构造参数，
  仅 e2e 用 `ENSEMBLE_SLEEP_GRACE_MS` / `ENSEMBLE_SLEEP_SWEEP_MS` 缩短；生产恒为 60s / 10s。
  另注意窗口级遮挡：整个应用被盖住或移出屏幕时，Chromium 原生节流本就会把所有页压停。

### 流程：把走通的操作存成资产

MCP 另外暴露 4 个流程工具：`list_flows` / `save_flow` / `run_flow` / `delete_flow`，
界面上对应 AI 记录页里的**流程**标签（`AiActivityPage.vue` 装着 `FlowsPage.vue`）。
数据模型见
`src/shared/flows.ts`，动作有 10 种：`navigate` / `fill` / `click` / `select` / `press` /
`login` / `wait` / `read` / `script` / `cdp`。

**动作层是步骤，编排层才是脚本。** 每个动作都走 `Input.dispatch*` 这条真实输入管线；
`script` 步骤只做编排——循环、条件、从读到的值推导下一步——它在 `node:vm` 里跑，
能调用的只有动作原语（不含 `login` 与 `cdp`），能力边界就是工具集合，执行器见
`src/main/embedded/flow-script.ts`（vm 强度的诚实说明在其文件头）。`read` 动作把
页面文字收进 `{{变量}}` 供后续步骤使用。

- **参数与变量在保存时校验**：未定义的 `{{name}}`、缺 `value` 的 `fill`、不认识的键名都在
  `saveFlow` 拒绝，消息点名第几步——这些字符串直接给到要改它的 AI。校验放在
  `service.saveFlow` 里，界面、IPC、MCP 三条入口共用同一套规则。
- **失败即停**：某一步失败返回 `failedAt` 与原因，后面的步骤不跑，避免写进半套数据；
  标了 `optional` 的步骤例外。
- **打开标签页只有一条实现**（`openFlowTab`）：IPC 与 MCP 都调它，否则会出现
  「应用里能跑、AI 跑不通」的漂移。
- 流程按站点归属；删站点时级联删除它的流程，导入时站点不在就跳过并计入 `skipped`。
- `run_flow` 的 `read` 目标可以指向非交互元素（订单号在 `<p>` 里），因此解析器多一条
  「按可见文字找最深的元素」的回退路径——常规解析器只搜可交互元素，对 `read` 够不着。

## 为什么用 CDP 而不是 Playwright

Playwright 是自动化测试库，它默认会接管对话框、下载和文件选择：

- 没有注册 `dialog` 监听时，`alert` / `confirm` / `prompt` 会被自动 dismiss。
- 下载落到临时目录，context 关闭即删除。

人手操作浏览器时，这些行为会让测试结论失真。所以外部模式直接用系统浏览器 +
`--remote-debugging-port=0`，内置模式用进程内 `webContents.debugger`，两条路径都用同一套
CDP 方法，只做这几件事：

1. 导航（`Page.navigate` 或重定向）
2. 登录表单填充（`Runtime.evaluate` + 原生 value setter + `input` / `change` 事件，
   支持账号密码之外按标签匹配的额外字段）
3. 登录态检测（页面内 `fetch` 携带 Cookie）、窗口定位
   （`Browser.getWindowForTarget` + `Browser.setWindowBounds`）与窗口切换
   （`Page.bringToFront`，最小化的先恢复）
4. 内置模式下的读页面、点击、输入、截图与页面内查找

Playwright 只通过显式开启的调试端口接管内置表面（`connectOverCDP`），或者用于管理台
自身的 E2E 测试，不进入主链路。

批量登录态检测（`checkAllAuth`）对每个身份执行同一段检测，最多 3 个并发——不同身份
是独立浏览器与独立 CDP 连接，唯一共享的是被测站点本身——并在整批结束后只写一次
`workspace.json`、广播一次快照。判定与启动自动登录共用同一段探测逻辑：HTTP 状态之外，
站点的 `authCheckSignedOut` 标记命中响应 body 时按未登录计。**私订头令牌站点**（会话
凭证不是 cookie 而是页面 localStorage 里的 token、随私订请求头发送）还需配置
`authTokenKey`（localStorage 键名，`authTokenHeader` 可选、默认 `token`）：探测在检查时
从页面读出令牌随请求发送，否则 cookie-only 的探测把登录态永远读成已过期。显式重新登录
（`fillLogin`）在提交成功后延迟复检一次并落库，过期徽标无需再手动检测；提交后的静置
是在等服务端应答与页面跳转完成，复检过早会读到登录前的状态。

对话框、下载、上传、扩展、原生密码管理器、Google SSO 全部保持浏览器原生行为。

## 启动链路

**管理台自己先显示一层启动画面。** workspace 快照、内置表面状态和首帧排版不是同时到的：
把壳体直接画出来，会先闪一帧空数据的新标签页，或一帧被启动行挤成半高的布局。启动画面
因此是覆盖整个窗口的 `position: absolute` 层（居中 Logo），壳体在它背后完成挂载与首次
测量；两帧之后启动画面淡出。它**不能**做成 flex 行——那正是旧实现把新标签页压到下半屏
的原因。启动期间 `stageSuspended` 保持为真，把原生 guest 全部停在窗口外：原生表面会盖过
任何 HTML，恢复中的页面不能在启动画面上面露出来。最短显示 500ms 只是避免快速启动时
闪两帧 Logo，不是假进度；workspace 一直不返回时 8 秒看门狗会放行到界面，避免永久停在
启动页。`scripts/e2e-boot-splash.mjs` 在启动早期采样：启动层必须铺满窗口、壳体必须已是
全高，随后启动层消失。

外部浏览器的启动链路：

```
resolveEngine(identity, environment)
  → profileDir = <profileRoot>/<envId>/<identityId>
  → 清除残留 DevToolsActivePort
  → spawn(exe, [
      --user-data-dir=<profileDir>,
      --remote-debugging-port=0,
      --no-first-run,
      --no-default-browser-check,
      --window-position=…, --window-size=…,
      <startUrl>
    ])
  → 轮询 <profileDir>/DevToolsActivePort（必须同时端口可响应）
  → GET /json/version 拿浏览器级 WebSocket
  → GET /json/list 找目标页（优先非 about:blank）
  → 连接页面级 WebSocket，登记到 cdpRegistry
```

Firefox 走外部模式：`-profile <dir> -no-remote -new-instance <url>`，不做 CDP，
因此不提供自动填充与登录态检测。

## 数据模型

模型是：站点 / 身份 / 全局标签 / 流程，外加保留数据的视图字段，见
[ADR 0007](./architecture/adr/0007-site-and-view-model.md) 与
[ADR 0008](./architecture/adr/0008-sites-as-login-recipes.md)（站点降级为登录配方、标签升为全局）。
浏览器表面的交互设计见 [浏览器表面：视图与标签页](./design/browser-surface.md)。

```
Site     1 ── N Identity
Site     1 ── N View（定义）
Site     1 ── N Flow（可重跑的步骤序列）
View     N ── N Identity（只引用，不复制）
View     N ── 1 LayoutPreset（内置或用户自定义）
Site     N ── N Tag（多对多，用于查找与分组）
Identity N ── N Tag（同上；筛选时合并所属站点的标签）
View     N ── N Tag（同上；筛选时合并成员及其站点的标签）
```

- **视图只剩数据，入口退役。** workspace 的 `views` 字段与其关系（成员、槽位映射、布局
  引用）原样保留，读写 round-trip 不丢；界面上没有视图页与创建入口，「启动一组账号」由
  账号页的多选批量启动承接（第一个上台、其余后台待命）。MCP 侧 `list_views` /
  `open_browser_view` / `compose_view` 等工具仍作用于打开的容器，AI 的摆位能力不受影响；
  存量 `views` 值回落浏览器页。未来如有「保存组合」的真实需求，在设置里另立
  「启动预设」，当前不做。
- 身份只属于一个站点。同一账号要测两个站点时创建两个身份，因为不同主机名的
  Cookie 域不同，复用 profile 会串站点。要在两个站点间共享账号资料，用
  `passwordMode: "reference"` 指向另一个身份；登录态与 profile 仍各自独立。
- 站点没有「类型」字段，也没有隐式的生产/非生产区分。启动一个窗口只是打开一个
  登录页，真正的破坏性动作发生在被测系统里，靠站点名字猜风险既会漏判也会误判；
  权限边界由 MCP 的 run 档和用户自己开的窗口负责。
- **站点不是全局作用域。** 没有「当前站点」；`settings.lastSiteId` 只是新建账号时的
  默认值。账号页按站点分组展示全部账号。
- 标签是一套命名空间，站点、身份、视图共用；删除标签只解除关联。管理入口是左栏「更多」里的
  **标签**分区（`TagsPage.vue`），因为标签不属于站点作用域，也不是一年改一次的设置项。
- **列表顺序只有两种来源，不要混用。** 站点、身份、视图、标签、流程的顺序就是它们在
  工作区数组里的位置，拖动即数组重排（`moveView` / `moveSite` / `moveTag`）；书签与
  书签文件夹例外，用 `order` 字段，因为它们按文件夹/同级分组、共享一个数组。把对象拖到
  另一个分组属于改归属，不是排序，走编辑弹窗。
- 凭据：身份存自定义密码，站点存默认密码，身份还可以引用另一个身份。
  解析顺序是引用目标 → 身份自定义 → 站点默认 → 报错；引用只允许一层。
- **账号密码之外的登录字段只存在身份上。** 租户名、公司码这类值是「谁登录谁提供」，
  所以站点不再带 `extraFields`；站点是登录配方，没有自己的账号。旧文件在
  `sanitizeWorkspace` 里把站点字段复制到其下每个账号。
- **`Identity.siteId` 可以为空**，表示账号的站点归属丢了（1.0 迁移曾把 v1/v2 混写文件
  读成已当前格式，导致站点列表变空、账号全部失联）。账号页把它们放在「未关联站点」
  分组下，批量选择后可一次关联到站点；`profileDirFor` 对这种账号返回 `undefined`，
  不会拼出 `<root>/undefined/<id>` 这种假目录。
- 站点记录 `lastOrigin`：填充前发现当前页面 origin 与它不同就暂停，要求用户显式确认，
  确认后更新（SSH `known_hosts` 的做法）。
- Profile 目录用 UUID，显示名可随时改；引擎绑定在身份上，换引擎是复制身份
  生成新 profile，而不是迁移目录。

## 窗口布局

### 两种视图：浏览器与设置页

壳只有两个视图，`App.vue` 的 `View` 就这两个值：

| 视图 | 组成 | 何时出现 |
| --- | --- | --- |
| **浏览器**（默认） | 地址行 + 左栏 + 页面标签行 + 舞台 | 启动即此，绝大多数操作发生在这里 |
| **设置页** | 自己的标题带 + 分区列 + 当前分区 | 应用菜单、`Cmd+,`、AI 面板的齿轮 |

**舞台恒为单格**（ADR 0012）：当前选中的实例上台，其余实例在后台运行——登录态保持、
AI 可继续驱动，只是不占像素。多账号并排观察由拆窗（实例拆出到独立 OS 窗口）与
操作系统分屏承接，应用内不复制分屏几何。

浏览器视图是一条竖排的两段：

```
.browser
├─ .toolbar          地址行：贯穿窗口宽度，本身是窗口拖拽带与 caption 预留的那一条
└─ .work-area
   ├─ AccountRail    左栏：运行中的账号，竖向一列
   └─ .content-col
      ├─ .tabstrip   上台实例的页面标签
      └─ .stage      舞台（页面节点、缩放/查找浮层、DevTools 分栏都挂在它里面）
```

**左栏必须与 `.stage` 是兄弟，不能叠在舞台上。** 舞台的 `getBoundingClientRect()` 是
`useStageGeometry` 上报给主进程的唯一几何来源，页面节点、空白页表面、`PageSizeFrame`
与 DevTools 分栏全部由它推出；把它盖住一截不是「遮住一点」，而是连同尺寸一起算错。

左栏（`AccountRail.vue`）的每个条目是一个浏览器实例：色条、站点图标、账号名、AI 三态点、
冻结标识与单独关闭。点一下把该实例的当前页放上舞台；其余实例继续在后台运行。底部是
[+ 启动]（多选账号批量拉起，第一个上台、其余后台待命）与 站点 / 账号 / 更多 三个入口。
竖向排列替代了横向折叠：一列可以滚，条目不会被 `+N` 藏起来。

### 管理是浮层，不是第二个视图

站点 / 账号 / 更多三处内容以 `ui/FloatingPane.vue` 盖在页面上：`min(720px, 60vw)` 宽，
从地址行下沿铺到窗口底部，左缘与左栏右缘对齐。它们不替换浏览器视图，关掉只是把
`layer` 置空，页面标签与左栏都不重建。

三件事由这个壳统一做，缺一件浮层就会「关不掉」或「被挡」：

1. **透明遮罩承接点击。** 舞台上是 `<webview>` guest，它 `pointer-events: auto` 时会把指针
   事件吃掉、不冒泡到 document——没有遮罩时「点页面空白处关闭」根本不触发。遮罩只盖页面区，
   不盖左栏与地址行：那两处是切换账号与地址的入口，盖上去会把一次点击变成「先关浮层」。
2. **走 `useFloatingLayer`。** 它在浮层存在期间让 `-webkit-app-region: drag` 的顶带交出
   拖拽角色（否则点标题带空白处的事件进不了页面），并通知主进程停下停靠的 DevTools——
   面板是原生视图，会盖在所有 HTML 之上。
3. **Esc 最内层优先。** 模态开着、焦点在输入框里、或某个下拉（`role="listbox"` /
   `role="menu"`）开着时，Esc 归那一层；否则才关浮层。

同一族浮层之间切换不叠加：壳里只有一个 `layer` 值，切换是赋值，两个浮层不可能同时打开。
「更多」里的四个分区（书签 / 标签 / 消息 / AI 记录）由一个页签条切换，状态同样由壳持有。
AI 记录暂时挂在这里，设置页仍是应用菜单打开的整页。

### 页面标签行在右列

标签行列出**上台实例**的页面——语义与大浏览器的标签条一致：切页统一走顶部，同一个动作不
提供两个入口。换实例由点左栏完成，左栏与标签行互不混排。

**排序与关闭。** 标签拖到另一个标签的左半边落在它前面、右半边落在后面，走同一个
`dropTab` 重排；只接受同一实例的页，别的窗口的页拖进来不响应，否则两个窗口的标签序会被拼在
一起。重排只改页序、不重建内部槽位表。中键关闭标签：按下时 `preventDefault` 挡住 Chromium
的自动滚动，关闭发生在
`auxclick`——右键同样会触发 `auxclick`，靠 `button === 1` 区分。`scripts/e2e-tab-strip.mjs` 守着这几条。

**活动标签画成地址行的颜色，且没有下边框**，标签条本身用框架色。两者因此连成一个连续表面，
标签像是从这块面上切出来的缺口。这是「像浏览器」与「像带抽屉的网页」之间最主要的差别，
比任何圆角或阴影都重要。`tests/contracts/browser-shell.test.ts` 守着这条：
两处必须引用同一个 `--chrome` token，标签不得自带下边框，标签条高度必须来自 token。

**窗口顶带只有一个：地址行。** 原生窗口按钮由主进程按 `TITLEBAR_HEIGHT`（`src/main/index.ts`）
定位，OS 按那个高度把按钮画在客户区右上角。同时满足三件事才不错位：`TITLEBAR_HEIGHT`、
`tokens.css` 的 `--titlebar-height`、**地址行与设置页顶带的 CSS 高度**都取同一个值（44px）。
历史上这个 token 只有 34px，是「顶部一行标签条」时代的尺寸；地址行接替顶带之后仍用 34 会
让按钮贴在 44px 条的上半截。页面标签行不再是窗口顶边，改用 `--tabstrip-height`。

### 管理页面共用一个框架

站点 / 账号 / 更多里的每一页都走同一条规则：**页头固定，且恰好一个区域滚动**。

| 原语 | 职责 |
| --- | --- |
| `.page`（`styles/base.css`） | 页面框架：撑满、`overflow: hidden`、统一内边距 |
| `.page-body`（同文件） | 唯一滚动区，`flex: 1 1 auto` + `overflow-y: auto` |
| `ui/PageHeader.vue` | 标题（`h1`）、一行说明、右侧操作槽；`numeric` 让说明用等宽字体显示活数字 |
| `ui/SplitPane.vue` | 左列表 + 右详情，两栏各自滚动；`dense` 收窄列表列 |
| `ui/GroupHeader.vue` | 可折叠分组头（箭头、色点、名称、计数），带 `meta` / `actions` 槽 |

需要第二个固定行（筛选条、标签页、面包屑）的页面把它放在两者之间并保持 `flex: 0 0 auto`。
`PageHeader` 自己带底部间距，页面不再各自写 `margin-top`。

### 外壳的形状：一行顶带 + 左栏 + 页区

```
.shell
├─ 地址行                BrowserPage 的 .toolbar：贯穿窗口宽度，也是窗口拖拽带
└─ 工作区
   ├─ 左栏               运行中的账号（AccountRail）
   └─ 页区               上台实例的页面标签行 + 舞台
```

管理内容（站点 / 账号 / 更多）是盖在页区上的浮层，设置页是唯一替换整个壳的页面。
两者都不出现在上图里：一个是 `position: fixed` 的层，一个是另一个视图。

实例的选中态用中性灰阶 `--selected` / `--selected-strong`，不用 `--accent`：
琥珀色的语义是「可执行的主操作」，而选中态是「你正看着这个」；若选中行也给琥珀底，
两者会被读成同一类东西。同样的理由，AI 入口与新建标签页两颗按钮的常态不加琥珀底，
只在 hover / 激活时着色。

设置页有自己的分区列：分区行铺 `--frame`，选中行才铺得出来。选中态和浏览器标签是同一种
表达：在边框色上铺一格更亮的表面。左栏的三个管理入口沿用同一对比关系（`--selected-on-frame`）。列没有自己的底时继承页面的 `--content`，而浅色主题里
`--chrome` 与 `--content` 都是 `#ffffff`——当前分区是一块白方块压在白底上，选中状态整个消失。
深色下同一对是 `#262b31` 压 `#1e2227`，勉强能看出，所以这个问题只在浅色暴露。

**分区列里的选中格比宽列表里需要更亮。** 宽列旁边是大片空白，`--chrome` 抬一格
就够；分区列只有 192px，同列还有多个未选中项，26px 外就是内容卡片，同样的 1.19:1
读起来只是「灰得不太一样」。为此加了 `--selected-on-frame`：深色 `#333941`（对 frame 1.45:1），
浅色直接取 `--chrome`（白，1.30:1，已经是浅色调色板能给的最大一阶，再深就成洞了）。

**分区列的两侧都要有内缩。** 行左侧 28px 呼吸、右侧留 12px 内边距，选中块才有右边缘；
浅色下块与内容区都是白的，没有右内缩时两块连成一片，当前分区看起来像从内容区里挖出来的
一块。列还要求铺到窗口边缘：取消页面的 24px / 28px 内边距再在自己身上还回来，它才和上方
标题栏接成一整条，不会在行旁边留一窄条内容底色。

设置页内部的分节是它自己的**纵向 tab**（`data-section`），分区列整个让开。

### 设置页按主题分卡片，说明只在悬停时出现

一个标签页里曾经只有一张大卡片，所有设置项之间只隔一条发丝线，「外观」和「网络代理」看起来
是同一张长表单，分组等于没分。现在每个标签页由若干 `SettingGroup` 组成（外观 / 浏览 / 启动与
填充 / 网络 / 窗口 / 检测），一张卡片一件事。

**卡片标题是表头，不是没样式的第一行。** 标题原来架在第一项上方 2px、中间没有线，字号也和
下方标签只差一档——眼睛没有理由把「外观」读成标题，它和「主题 [深色][浅色]」是同一块文字，
于是每张卡片都像一张列表，第一项碰巧加粗了。标题下的一条发丝线是把它变成表头的东西：它说
下面那几行是它的内容，而这条线在卡片边界已经出现过一次，所以读起来是同一个规则用在卡片内部。
标题字号用 `--fs-md`（行标签是 `--fs-sm`）；`SettingRow:first-of-type` 去掉自己的上边框但保留
内边距，否则标题线下面 25px 处会再印一条。

设置项用 `SettingRow`：左边只有名称，右边只有控件。解释性文字全部收进名称旁的 `HintIcon`
（信息图标，`v-tooltip` 悬停或聚焦才出现），不再逐行常驻一段小字。**唯一保留常驻说明的是
影响安全或不可逆的**：主密码不可找回、打开 MCP 删除权限意味着什么。

这条规则不限于设置页，是全界面的硬约束，见 `AGENTS.md` 第 15 条。

**页面头只有标题，没有副标题。** `PageHeader` 曾有一个 `note` 口子，七个页面各填了一句
复述标题的话（「AI 记录 / AI 在页面上的操作」、「站点 / 管理多账号访问的站点」），于是每一屏
都先要读一行什么也没多说的字。现在 `note` 这个口子对所有页面关闭，只有 `#note` 插槽还开着，
而它只装数字——身份页的「12 账号 · 3 运行中」是页面上别处看不到的实时统计，删掉会丢信息。
一句说明如果要写，写进空状态或 `v-tooltip`，只在真需要时出现。
由 `tests/contracts/page-headers.test.ts` 守护。

- 左栏的三个管理入口带 `data-rail-entry`（`sites` / `identities` / `more`），浮层里的
  分区带 `data-manage-item` 与「更多」的 `data-more-tab`，e2e 与截图脚本靠它们切页。
- 管理内容开在浮层里，顶带由浮层自己让开：页头不再需要额外的 caption 保留，那条
  `padding-right: calc(var(--window-controls-width) - 28px)` 的历史内缩也没有去处。

拆成组件而不是「统一复制一份样式」，是因为这些规则里有对齐细节（分组头箭头向左探出，
让组名与下方卡片对齐）、有相对宽度（`SplitPane` 的列表列 260–340px），复制三次必然分叉：
迁移前 `ViewsPage` 与 `FlowsPage` 已经从 260–340px 漂成 240–320px，同一个窗口宽度下两页
的列表栏不一样宽。

空状态同理，由 `.empty` / `.empty-actions`（同在 `base.css`）统一：虚线框、居中、宽度上限
560px、`margin: auto` 在滚动区里自居中。页面只保留位置差异（身份页的响应是网格，书签页有
「文件夹内为空」变体）。

**空状态里的按钮只放此刻真的能用的操作。** 前置数据缺失时（零站点时的「新建流程」、零身份时
的「新建视图」），按钮换成指向补前置条件那一页的跳转，并把禁用原因挂在页头按钮的 `title` 上。
一个点不动的灰按钮只说「不行」，不说「先去做什么」。

### 禁用态必须是结构性的，不是调暗

`AppButton` 的禁用态不用全局 `opacity`（`styles/base.css` 里 `button:disabled` 的 0.45）叠加：
把填充色原样调暗会留下一块淡色，浅色主题下像品牌色坏了，两个主题下都容易被误认成 hover。
禁用态改为去掉填充——`--surface-2` 底、`--line-soft` 边、`--faint` 文字、字重归 400，
`opacity: 1`。这样「不可用」来自形状本身，不依赖某个主题下的明度差。

### 界面是平的：没有斜面、没有投影、没有玻璃

这一条约束的是整个渲染层，不是某个组件。

- **主按钮一个纯色。** 曾经是 `180deg` 双色渐变 + 深色下边框 + hover 时 `brightness(1.06)`，
  即一个斜面。在一屏平面板和发丝线里，那颗凸起的药丸是立体感最强的东西。现在底与边都是
  `--accent`，hover 换 `--accent-strong`——两个主题各自把它定义成「更极端的那一侧」
  （深色更亮、浅色更深），这是单条 color-mix 公式做不到的。各处对话框里复制的渐变覆盖
  已删除，让共享样式接管。
- **`--shadow-tab` 置空。** 它原本给选中的标签和行加投影。选中是**填充**，不是**抬起**；
  投影留着只会让平面上的行看起来浮起来。
- **卡片与页面同色时，边框用 `--line`。** `--line-soft` 对 `--surface` 只有 1.15:1，
  大面积深色截图能看清、白色页面上看不见。去掉渐变之后，层次只能靠边框。
- **空状态没有框。** 虚线圆角框把「你还没建」画成了一个不存在的容器。居中的图标 + 一句话
  + 按钮说同一件事，且不在空页上再画一个盒子。
- **新标签页背景很淡（≤7% 不透明度）。** 之前 16%/18% 的双角辉光在整窗尺度上就是一层色，
  而这个页面上唯一的内容是一个搜索框，背景不该是第一个被注意到的东西。
- **不用 `border-radius: 999px` 做通用控件。** 胶囊留给真正成对/成组的标记（徽章、计数、
  色点）。46px 高的搜索框用半高圆角是手机主页的语言，不是桌面窗口的。

判断标准：**如果一样东西的强调依赖明暗渐变或投影，它就是这条例外的目标。** 强调应该来自
它是这一行里唯一被填充的东西。

### 浮层是一个统一状态，不是每个菜单各自的事

`useFloatingLayer(open)` 是渲染层唯一登记浮层的地方，维护一个模块级的打开层计数。计数从 0
变正、或回落到 0 时，它顺手做两件只有「知道有没有浮层」才能做对的事：

1. 在 `<html>` 上挂 / 摘 `data-floating`，让 `-webkit-app-region: drag` 的标题带交出拖拽
   角色。否则点标题带的空白处关菜单时，事件根本不进页面——而那正是人最容易去点的地方。
2. 告诉主进程停放停靠的 DevTools。面板是原生视图，绘制在渲染层所有内容之上，跨过它的
   下拉会被腰斩。

两件事都必须按**计数**判断，不能按布尔值：菜单会嵌套（标签菜单上叠一个视图菜单、再叠一个
确认框），每层各自开关会在第一层关闭时就把底下的状态恢复掉。历史上有过两次同源缺陷——早期
只有标签菜单调用了停放，另外六个菜单漏了；而那个唯一的调用点传的是布尔值，嵌套时立即失效。
判断挂在共用计数器上之后，新增一个菜单不可能再忘。

停放时**页面保持当前宽度**，只把面板的视图缩到 0×0。两个都收的话面板消失、页面同时长回
整幅，任何菜单一开页面就明显跳宽一次，读起来是「开发者工具没了」而不是「上面盖了个
菜单」。空出来的那块由浮层本身或面板的标题条占着，分界线停在原处。

面板的生命周期跟页面绑定：关标签时 `discardTab` 走 `dropDevTools`。少这一步的后果不是留个
看不见的视图——前端网页本身还在跑，缩略图和断点都活着，而所有能关它的入口都要先查到一个
已经不存在的标签。

### 动效必须看得见

动效不是装饰，但也不能小到看不见。上一版把浮层入场做成 `4px` 位移 + `110ms`，结果每个
菜单都像是「直接出现」——位移在眼睛登记之前就结束了。现在统一成：

| 令牌 | 值 | 用途 |
| --- | --- | --- |
| `--motion-fast` | 110ms | toast、退出 |
| `--motion-base` | 160ms | 下拉框、应用菜单、对话框、书签文件夹 |
| `--motion-slow` | 220ms | 大幅位移动画（登录捕获提示条入场等） |
| `--motion-shift` | 10px | 浮层入场位移 |
| `--motion-pop-scale` | 0.97 | 浮层入场起始缩放 |

规则：**入场用 `--ease-out` 并伴随位移与轻微缩放，出场用 `--ease-in` 且更短**；移动距离
与容器尺寸成比例（整列变宽用 slow，一个小菜单用 base）。锚定浮层把 `transform-origin`
设到它所依附的那条边，这样缩放读起来是「从这里长出来」而不是「从中心弹开」。
`e2e-motion` 从帧里读 `animationDuration` 与实时 transform，保证时长来自令牌而不是硬编码。

### 舞台几何只有一个出口

渲染层测量舞台矩形并上报主进程，主进程据此算出每个页面在自己的舞台里占哪一块。这段逻辑
收在 `composables/stageGeometry.ts`：**这是与「用什么显示页面」之间唯一的契约**——「给你
一个矩形，把页面放进去」。节点位置由 `shared/embedded.ts` 的 `guestNodeRect` 统一计算，
主进程和渲染层共用同一个纯函数，不再各算一遍。

把它单独成模块的实际用途：换载体（或再换一次）时改动收敛在这里，而不用在两千多行的组件里
重新找散落的 `getBoundingClientRect`。

内置舞台恒为单格：台上实例的当前页铺满整个舞台，没有分屏几何、格子拖放或布局选择器。
内部的槽位机制（`shared/embedded.ts` 的槽位解析与 `core/layout/grid.ts`）保留以单槽运行——
`computeSlots` 对单格返回铺满舞台的一个矩形，布局数据读写 round-trip 不丢。多账号并排
由两条路径承接：

- **拆窗**：实例拆出到独立 OS 窗口（见下文拆窗一节），窗口之间由操作系统排布。
- **外置窗口**：外部浏览器各自成窗，`1x1` 布局下的「无布局」是互相重叠的多窗口，
  用任务栏 / Alt+Tab 切换。

用户自定义预设（`LayoutPreset`）与视图槽位映射（`View.slotAssignments`）的数据字段
随 workspace 保留，读写不丢；界面上没有编辑入口。

### 实例拆出到独立窗口

一个运行中的页面可以拆到独立 OS 窗口（`popout.ts` + 标签右键菜单「拆出到独立窗口」），配合
系统分屏与多显示器做并排观察；再点一次收回主舞台，同一实例同时只允许一个拆出窗口。

- **拆出即页面重载**：`<webview>` 节点无法跨窗口迁移，节点从宿主 DOM 移除即销毁 guest，
  「卸下旧节点 → 在新窗口重建节点」的换代序列（`EmbeddedBrowser.remountCarrier`）是唯一
  路径。会话分区与 CDP 会话全程不变（分区在 session 层，与承载窗口无关），SPA 内存态
  不保留，登录态与存储原样可用。
- **空白页不拆**：没有内容可搬，换代的唯一结果是多出一个空窗口。菜单里那一行禁用，
  主进程 `popOutBrowserTab` 同样拒绝——界面禁用只是提示，主进程是裁决者。
- **底色跟随主题**：弹窗只有内容区、没有宿主 UI，页面加载出第一帧之前的底色由主进程按
  当前主题作为 query 参数传入（`popout.html?theme=dark|light`）。弹窗入口刻意不接 Vue
  应用，页面不去读 workspace store。
- **截图路径**：弹窗最小化时 guest 的 `Page.captureScreenshot` 不回复（无帧不答），
  退到 `capturePage` 渲染路径——与主窗口最小化同一分支。
- **不挂 `parent`**：挂上之后弹窗是主窗口的 owned window，主窗口最小化时它跟着不可见，
  而拆窗要的正是「主窗口收起来，这一页还在」。两者生命周期因此完全解耦，「不留孤儿」
  改由显式登记承担：主窗口销毁时与退出时各调一次 `popouts.dockAll()`。用户点 X 关窗后
  页面自动回主舞台；拆出的窗口是本进程的 Chromium 窗口，退出顺序的「回收浏览器」覆盖它们。
- **AI 入口**：`pop_out_browser_tab`（run 档），已拆出时再次调用即收回；标签页投影带
  `popout` 字段，拆窗状态是决策信息，随 `list_browser_tabs` 一并发布。

三项实测（焦点归属、关闭回收、最小化截图，Electron 45.2.1）由
`scripts/e2e-popout.mjs` 守着，结论亦记录于 `src/main/embedded/popout.ts` 的头注。

### 内置表面的页面与实例

两个概念必须分清，它们的 id 关系是最容易踩的地方：

- **页面**（`EmbeddedTab`）：一个 `<webview>` guest，等同于浏览器的一张标签页。
- **实例**（browser instance）：一个共享会话的浏览器窗口。实例 id 是它的**根页面 id**。
  页面自己 `window.open` / `target="_blank"` 出来的页面加入同一个实例，共享 cookie。
  舞台恒为单格，内部槽位表（`slotTabs`）以单槽存**实例 id**——批量启动的多页摆位、
  AI 的显式摆位都经这条机制，只是槽数为 1。

两条由此推出的硬约束：

1. `createTab` 给新页面写的 `instanceId` 必须是**父页面的 `instanceId`**，不能是父页面的
   `id`。把根页面当成实例 id 用，一开始不出错（两者相等），但关掉根页面后剩下页面的
   `instanceId` 会指向一个已经不存在的页面，此后往这个实例里开页就会被判成新实例。
2. `closeTab` 关掉**根页面**时必须把槽位改指向活下来的最早一页。槽位表里存的还是根页面 id，
   根页面一没，`resolveSlotTabs` 就把那一格判成空——页面还在跑，舞台却空了。

舞台显示的是上台实例的「当前页」（`instanceActive`），切页不改变摆位；一个槽位恒为一个
实例。空白页（`about:blank`）不上屏，舞台让给渲染层画的「新标签页」（搜索框 + 引擎选择）——
空白页如果只是原生表面的一块空白，点「+」就得不到任何反馈。

**「哪一页在台上」和「哪一页在加载」要在同一次广播里说清。** 界面是否画新标签页，只看该页
的 URL 与「它是不是台上正在显示的那一页」。`createTab` 等待 `loadURL` 完成才切
`activeTabId` 的话，整个加载期渲染层仍认为前一页（空白页）在前台，舞台一直画着新建标签页，
直到站点首字节回来——慢站点上就是「点了账号，卡住几秒」。标签记录因此从第一帧起就带着目标
地址与 `loading: true`，并且**选择在 `openCarrier` 之前完成**、立刻广播一次；等页面就绪只
影响调用方拿结果，不影响界面显示什么。判别「台上该显示哪一页」时，有 pin 用 pin，没有则
跟随该实例的活跃页（`tab.active`，与主进程 `pageForSlot` 同一条规则）——这里若错用全窗口的
`activeTabId`，批量启动就只有一页在台上，其余会被当成离台、停放到窗外。

新标签页顶部还有一条
**书签栏**（`BookmarkBar.vue` + 递归的 `BookmarkBarFolder.vue`）：根层一行，文件夹悬停展开、
子级向侧边弹出；一行能放几条是实测 `offsetWidth` 回推的，放不下的进溢出菜单。它长在这个
表面上而不是工具栏上——浏览器外壳没有书签栏，页面有了地址这条栏就不存在。

新标签页上只有书签栏与搜索框，没有瓦片网格。曾经有一版把整棵书签树铺成图标瓦片（叫「固定
标签页」），读起来像用户自己钉的常用入口，实际是书签的第二种画法：删一条书签瓦片就少一个，
在网格里拖一下改的是书签的存储顺序。两种语义混在一起，任何一处的改动都会在另一处意外生效，
所以整块撤掉了；真正要的「常用入口」是独立数据，不借书签实现。

书签本身在左栏「更多」的**书签分区**里逐层导航：当前层的文件夹先成瓦片（点击下钻，计数覆盖整个子树），
其后是该层自己的书签；条带是面包屑，回跳之外还是投递目标——磁贴拖到瓦片或面包屑即归档进对应
文件夹。不做整棵树平铺：浏览器导入一次几百条、层级又深，平铺就是一面墙。深层书签的
主路径是检索而不是导航：搜索框输入即全树匹配书签（回车打开，不选中则照常走网址/引擎）；
面包屑每级带下拉箭头列出该层子文件夹，链两级下拉即达任意深度。

书签栏不只是一排能点的名字：右键给改名与删除（文件夹的删除连带内容，确认框写明条数），
行与行之间可拖拽排序，两者都走管理页同一套服务方法，所以两处看到的顺序永远一致。整条栏
共用一份**打开路径**（`bookmarkFlyout.ts` 的 `path: string[]`）：指针换到别的分支时旧面板
立刻退场，只有同一路径上的祖先面板保留——面板贴着父级行弹出，父级退了新面板就没定位基准。

**后台页面的呈现不等于显示。** 读页面、点页面、截图都要求节点在窗口里有一个真实 box，
所以 CDP 命令期间会把离台节点挪回舞台（`GuestCdp.presented`）。它只借 box，保持
`opacity: 0`：批量启动时多个页面会同时装登录监听，早期实现顺手把呈现做成显示，于是
三四个整窗页面叠在同一个矩形上闪。合成器对透明节点照常出帧，截图路径不受影响。
详见 `docs/design/browser-surface.md` 的「呈现」一节。

**声音是标签页的状态，不是页面的实现。** 主进程监听 `audio-state-changed`，页面主动发声时
标签条出现喇叭（`Volume2`），静音时出现 `VolumeX`；点击即切换，走 `embedded:muted` 通道由
主进程调 `setAudioMuted`。静音记在标签记录上，`did-finish-load` 重放一次，所以刷新不丢。
它只关 Ensemble 的输出：页面里的 `AudioContext`、音量节点与「是否在播放」的判断都不受影响，
AI 调试声音界面才不必被外放打扰。

**AI 操作默认静音，除非用户要过声音。** MCP 的 `tools/call` 在审批通过后、执行工具前调
`muteForAi(tabId)`；AI 新建的标签、`open_browser_view` / `run_flow` 打开的页面从创建起就带
`muted`。用户手动点过取消静音后 `userUnmuted` 置位，之后的 AI 操作不再自动覆盖；AI 显式调用
`set_browser_muted` 仍然可以静音——那是它自己的意图，不是默认策略。

**JS 弹窗是一条有状态的 AI 工作流，不是一个报错。** 实测（Electron 45.2.1）：弹窗打开期间
触发它的 `Input.dispatch*` 永远不 ack。`Page.javascriptDialogOpening` 一到，挂着的输入命令靠
事件信号立刻返回，返回体带 `dialog` 类型与内容——不重试点击，先答弹窗（`read_browser_dialog`
/ `handle_browser_dialog`）。唯一会自动应答弹窗的是「无人应答超预算」的兜底定时器；其它一切
超时只报错，不动弹窗。弹窗挂起期间会话钉住（见闲置释放一节的统一谓词）：分离会把被抑制的
弹窗交还 Electron 的原生对话框兜底，那是用户桌面上的真弹窗；guest 注册即开会话并保到首个
文档落地，堵住「弹窗先开、会话后附」的空窗。beforeunload 不走 CDP 弹窗事件（Electron 换成
`will-prevent-unload`，且 Chromium 只在页面有用户激活时才拦）：拦截自行记账为不阻塞页面的
记录，`navigate` 返回体带 `cancelled: "beforeunload"`，`accept: true` 带放行标记重发被拦的
导航（`preventDefault` 只在事件派发期间有效，只能同步消费）。`prompt()` 本环境同步抛错，
页面循环不停摆；真正的循环停摆由 `read_browser_page` 的页内定时器探针在 800ms 内报出。

**批量操作要合并广播。** `BrowserManager` 的 `withoutBroadcasts()` 包住 `createView` 与整个
`launchIdentityBatch`：逐条广播会让渲染层把「容器在、页面还没到」的中间态真画出来，舞台就
空一下再填满。合并后一次启动只发一次终态；失败回滚的路径必须先释放 hold 再抛错，否则界面
会停在已经回滚的页面上。启动到达的「一次跳变」与「零重叠」由 `e2e-batch-launch` 逐帧采样守住。

### 视口尺寸、设备模拟与面板分栏

停靠面板顶部是三个页签：**前端**（原生 DevTools）、**设备**、**性能**。原生前端是
`WebContentsView`，自绘页签是渲染层的 HTML，一块矩形只能有一个主人——所以「切换页签」是
「谁拥有这块矩形」，不是「谁盖在上面」。切到自绘页签时原生前端被**移到 0×0 停放**而不是
销毁，控制台历史因此还在。

**原生前端的语言是宿主偏好，不是 localStorage。** 接上宿主后，DevTools 从 Electron 的
DevTools pref service 读 `language` 与 `disable-locale-info-bar`（值都是 JSON 字符串），
只有前端自己的 `InspectorFrontendHost.setPreference` 写得进去；未挂载的文档拿到的是 stub，
写 localStorage 看起来成功，真正的面板永远读不到。打开面板前先用一个**离屏、真正挂到被测页**
的临时前端写入并读回这两个偏好，关掉它，再开可见面板。**不能**在即将变成面板的那份视图里
预加载前端：前端先初始化、后 `setDevToolsWebContents`，会留下一个工具栏正常、Elements 全空的
空壳。`devtools-language.ts` 收口这段临时视图的创建与清理。

**设备页先分桌面与移动端，再选具体尺寸。** 桌面模式是纯几何：自适应、五个常用桌面分辨率、
自定义；页面仍是无触摸、桌面 UA 的浏览器。移动端模式是身份：五个设备各带尺寸、DPR、触摸
与移动端 UA，点一下整套生效；「自定义」沿用上一个设备的 DPR / UA，只改宽高。旋转按钮交换
宽高并保留设备名；拖动页面边缘或输入宽高，选择自动落到「自定义」——列表始终回答页面现在
穿的是什么，且只有一行处于选中态（自定义尺寸恰好等于某个预设时仍算自定义）。切回桌面模式
恢复的是**进入移动端之前的桌面答案**（某个分辨率、显式自适应，或继续跟随工作区默认），
不会把手机的 393×852 当成一个自定义桌面视口留在页面上。底层仍是 viewport / device 两条
路径，`mobile` 跟**设备身份**走，不跟触摸开关走（见踩坑库 2026-11-14）。

三条实测得出的规则（来自 CDP 探针，不是推测）：

1. **上面三个 `Emulation.*` 覆盖都不跨 CDP 会话。** 会话一释放，页面立刻回到桌面。
   因此穿设备的页面必须**钉住会话**，不能沿用「闲置 1.5 秒释放」的策略。谁需要会话由
   `syncSessionHold` 一个谓词统一回答（设备模拟、性能采样、环境覆盖、init 脚本、登录捕获、
   挂起的弹窗），各功能只声明需求，不直接调 `holdSession`——多个功能各自 pin/unpin 同一个
   布尔标志，等于谁都能悄悄解除别人的防御。
2. **设备跨文档导航靠重新下发。** 覆盖是 per-document 的，点了链接就没了。`did-finish-load`
   里对带设备的页面重放一次（`reapply`），否则「点进下一页变回桌面」会在最需要它的时候翻车。
3. **`setDeviceMetricsOverride` 会钉死 CSS 视口，与节点的 box 无关。** 这让几何错误在设备
   模式下不可见：box 算错了，页面照样报 393px。修几何问题时不能只在设备模式下验收。

**触摸能力常开，鼠标转触摸跟着指针开关。** 两个 CDP 命令不是一回事：

- `Emulation.setTouchEmulationEnabled` 只声明 `maxTouchPoints`，让页面相信自己支持触摸。
  它对整个设备会话常开，`maxTouchPoints` 不会因为指针移动而闪成 0。
- `Emulation.setEmitTouchEventsForMouse` 把鼠标按下 / 移动 / 抬起合成 touch 事件，拖拽才会
  变成滑动。它**同时会给原生窗口装一张 Chromium 自己的触摸光标**（深灰色圆点），而且这张
  光标是窗口级的，不是页面级的。

旧实现一直开着第二条命令，所以切到移动端后整个窗口都是灰点，连工具栏和原生 DevTools 都
盖住；页面里再画一个 DOM 圆点，就成了两个圆点。现在由主进程轮询系统指针
（`screen.getCursorScreenPoint`），只用 `pointerInsidePage` 判断指针是否落在某个触摸页
的矩形内：落在里面才启用鼠标转触摸，离开、窗口失焦或最小化就立即禁用。圆点因此就是
Chromium 的原生触摸光标，只在该页面内出现，跟随没有 IPC 延迟，也不会污染页面 DOM 或截图。
页面自己的 `maxTouchPoints` 始终不变。

**关闭转换就会交还光标。** 触摸光标是 `setEmitTouchEventsForMouse` 的副作用，不是窗口上
残留的图片：命令一关，Chromium 按指针下的元素重新算光标并调 `SetCursor`，指针随后移过
工具栏时也会继续按宿主自己的 cursor 走。早期实现额外在渲染层注入过一张 32×32 的箭头图片
（`html.cursor-refresh` 类），用来「逼」一次刷新；它和系统主题不同色，指针每次进出页面都会
闪一下，这套 IPC 与样式已整体删除。应用根（`body`）与 DevTools 前端根仍显式写
`cursor: default`，按钮、输入框与缩放手柄各自的 cursor 仍然覆盖它。**缩放因子由布局统一归还。** 固定视口激活期间，页面 `zoomFactor` 就是 fit 比例，用来让
CSS 视口保持请求的尺寸；设置页、设备页、拖拽边框、键盘快捷键都能清掉视口，任何一条路径
忘了恢复，页面就会带着 0.4 倍缩放进入自适应模式——文字特别小，而尺寸状态看起来全对。
`placePageSurface` 的「无固定视口」分支因此无条件执行
`applyZoom(tab, tab.zoomOverride ?? defaultZoom)`：布局是每条路径都会经过的地方，把恢复放
在这里，新增一条清视口路径也不会再留下残留缩放。e2e 用固定 1920×1080 再切自适应，断言
页面 DPR 回到基线、CSS 视口等于主进程发布的页面盒宽度。

**分栏按舞台算，不按适配后的页面算。** 页面有固定视口时会 `viewportFitRect` 缩成一个保持
宽高比的盒子；拿这个盒子去分 42% 给面板，一个 393×852 的手机适配出来的窄盒会让面板只剩
一百多像素——用面板选设备，选完就没法再操作。正确做法是：分栏宽度 = 舞台宽度 ×
(1 − 面板占比)，页面再在**剩下的区域**里重新 `viewportFitRect` 并同步 `zoomFactor`。
一句话：**面板占多少由容器决定，页面画多大由宽高比决定**，两个矩形不能混用。

**尺寸在页面边沿上拖，面板只负责精确值。** 舞台在页面外框上叠一层 `PageSizeFrame`：右边、
下边、右下角三段拖拽区，右下角常驻一个斜纹握把，悬停边线时亮起主色，`W × H` 徽标贴在页框
外侧（贴边时收进内侧并让开握把）。固定视口的页面在舞台内再让出
`EMBEDDED_PAGE_FRAME_GUTTER`（10px）的舞台边距，手柄因此落在**页面外的宿主空间**：guest 是
原生表面，压在手柄上的那截会把指针和光标一起抢走，触摸模式下更会被页面的圆点光标盖住——
留边之后，圆点停在网站视窗边缘，边框恢复成普通的缩放光标。拖动按页面中心与**起始 fit
比例**换算，被拖的边跟指针走；宽高先钳到 `cell`（主进程随 `bounds` 一起发布的适配盒）在
该比例下装得下的上限，超过就停在舞台边缘，而不是让页面重新缩小——否则指针继续外移时页面
反而在另一边变窄，边框也会从页面上滑开。页面缩小到重新装进舞台时按新的 fit 比例重画草稿
框，边框始终贴在页面上。80ms 节流，松手提交最终值。拖拽期间 `store.holdPointer()` 让 guest
让出指针，否则 `webview` 会吃掉 mousemove。带设备的页面只改宽高、保留 DPR / 触摸 / UA，并
去掉设备名——拖过之后它就是自定义尺寸，不再冒充某个型号；自适应页面不显示手柄，没有固定
视口可调。

**性能采样只在那一页显示时进行。** `Performance.enable` + `Performance.getMetrics` 拿到的是
累计计数（`TaskDuration`、`LayoutCount`、`RecalcStyleCount` 等），需要按间隔差分才是
「每秒」与「CPU 百分比」。`core/cdp/performance.ts` 是纯算术（负差值记 0、CPU 封顶 100）。
切走即停——留着采样等于让一个看不见的面板常驻持有一个调试会话。

**采样间隔与采集区间都是设置项**（默认 200ms / 20 秒，范围 100–2000ms / 5–120 秒）。选这两个
默认值是一次取舍：更细更短，卡顿看得越清；更粗更长，慢速爬升才看得出来。两个数相乘就是曲线
点数，所以除了设置里的区间还有一道 `PERF_HISTORY_MAX`（1200）的硬上限——两分钟配 100ms
正好撞上去，没有它，「合法的设置组合」就能把监视器变成被测量的负载。改动会在下次采样器
启动时生效（面板切走再回来，或 AI 重新读取）：间隔写在 `setTimeout` 链里、区间决定保留多少
历史，半新半旧的曲线在横轴上会撒谎。

**首个样本必须标 `warmup`。** 它没有上一个计数可差分，速率字段是「未知」而不是 0。当成 0
会同时骗过三处：图表在左缘画一个从未发生的归零、`avg` 被这个假 0 拉低（两个样本的窗口直接
报出一半的真实 CPU）、峰值时刻也可能落到它身上。实测时正是它让「采样变细 → CPU 变高」的假
象出现，而独立测量（页面自己数完成的批次）显示各档吞吐与基线相差 0–6%、并不随间隔单调恶化。

关于开销：每次采样是在页面主线程上做一次同步 CDP 读数，所以更细确实更贵，但贵得有限——在
一个已经把主线程吃到 96% 的页面上，100ms 档的吞吐比无采样基线低 3%，200ms 与 500ms 档都在
噪声内。真正该担心的是「曲线在测量自己」：读数落进它自己统计的 `TaskDuration`。这也是面板
只以 1 Hz 广播状态、由渲染层自己轮询的原因。

四条关于这套图的硬规则，都是踩过之后补上的：

1. **分母必须是「距上一次的间隔」，不是「距开始的总时长」。** 用后者时每个尖峰都被摊进整段
   历史：页面正在忙着布局，曲线照样是一条直线。`t` 仍是绝对时间（供横轴用），速率用间隔，
   两个数分开算。
2. **横轴按真实时间排布，不按样本序号。** 忙页面会让定时器迟到；等距排布会把这个空隙压掉，
   尖峰出现的时间点就报错了。
3. **横轴跨度固定为一个窗口，右端恒为「现在」，绝不按现有数据缩放。** 早先的横轴取「最老
   样本 → 最新样本」，于是面板刚打开时一秒的数据被铺满整个宽度，随后每来一批样本就被压窄
   一次——看上去像图表自己在缩放，而且 200ms 的卡顿被拉成一条缓慢的波。现在窗口恒为
   `PERF_WINDOW_DEFAULT_MS`（默认 20 秒，可在面板里改），最新样本贴右边缘，年轻序列只占它已填满的那一段；满窗之后旧的
   从左边滑出、新的从右边进入。**滑动窗口从第一帧就成立**，不是等装满才开始滑。裁剪也按
   时间（`pushSample` 以最新样本回推一个窗口），计数上限只作兜底——采样被卡顿拖慢时，只按
   数量裁剪会保留超过一个窗口的历史，那些点画出来也会被夹在左边缘。
4. **图表由渲染层轮询，不由状态广播推送。** 采样最细 10 Hz，而每次 `emitState` 都会跑一遍渲染层
   的响应式流程；按采样频率推送会让面板本身成为被测量的负载。主进程最多每秒广播一次，面板自己
   250ms 拉一次历史。
5. **每条曲线必须有刻度、网格和填充。** 只画一根线时「有波动」说得出来，「到了百分之多少」
   说不出来——线的高度没有参照物。纵轴取三个刻度（顶 / 半 / 底），刻度值用
   `perfAxisLabel` 压缩到 36px 装得下的形式（`100%` / `1.8M` / `13k`），并向下取整到可读的
   数字：刻度写 `2.38M` 而数据从没超过 `1.8M`，读者会去验算而不是读图。填充用 10% 不透明度，
   让贴底的曲线也有可见的形状。
6. **顺序与配色按类别，不按行。** 顺序沿用 Chrome 性能监视器：总体开销 → 内存 → 页面结构 →
   抖动。颜色表达的是「这是哪一类数字」（CPU 暖色、堆紫、四个 DOM 计数同蓝、两个每秒速率
   同粉），八条互不相干的颜色只是噪音。
7. **横向空间优先给曲线。** 面板本来就窄，早先一行里四段（勾选框、名称、曲线、数值 + 峰值）
   各占一截，曲线只剩一百来像素。现在名称 / 当前值 / 峰值收成一行，曲线独占下一行、占满面板
   宽度；三个纵轴刻度挪进曲线左侧 34px 的窄槽，不再参与横向分配。容器窄到 380px 以下时省略
   峰值与零点刻度，名称从不换行（`min-width: 0`，否则 flex 项的默认最小宽度会把它挤成两行）。
8. **采集区间与采样间隔由面板自己配。** 两者都在面板表头（`data-perf-window` /
   `data-perf-interval`），跟它们影响的曲线在同一屏。放到设置页意味着「要测卡顿 → 离开正在测
   的页面 → 找那两行 → 再回来」，而采样器会因此重启、丢掉刚攒的历史。选项是固定的四档而不是
   输入框：两个值相乘决定绘制与保留的点数，手填一对可以要求每条序列上千个点。设置本身仍存在
   `AppSettings`（主进程采样器与面板读同一份），所以两个进程不会各说一套。
9. **hover 高亮只给控制部分，不给整行。** 整行两行高、含 40px 曲线，整块变色会让曲线跟着变暗
   ——看上去像数据变了。行本身仍是开关（`<button>`），hover 提示落在勾选框 + 指标名那一行。

**缩放不再占工具栏。** 它是最多人用快捷键/滚轮驱动的控件，而一个常驻的百分比读数在几乎每页
都是 100% 的情况下要占掉工具栏十分之一的宽度。现在两处入口（分辨率菜单、应用菜单）保留同一
套 − 数值 +，而手势缩放（Ctrl ±、Ctrl+滚轮、Ctrl+0）由主进程经 `embedded:zoom-notice` 通知
渲染层，浮出一个 1.2 秒后自动消失的百分比提示——手势发生在页面里，界面侧看不到，没有这个
提示就等于按了没反应。固定视口下 Ctrl ± 不改缩放（那是适配比例），但仍会浮出当前值，避免
「按了没反应」的错觉。

与 `profiles/` 互不相干。其中**默认档案**是持久目录，**干净会话**（不带 `persist:` 前缀）
只在内存里，不产生目录。

### 开发版与安装版各用一份工作区

安装版落在 Electron 默认的 `%APPDATA%/ensemble`；开发版（`electron .`，`app.isPackaged` 为 false）
落在 `%APPDATA%/ensemble-dev`，窗口名与托盘名是「Ensemble Dev」，Windows AUMID 是
`io.github.onefanki.ensemble.dev`，MCP 默认端口 47822（安装版仍是 47821）。

这四项缺一不可，原因是它们各自对应一种「用了安装版就没法开发」：

| 共用时会发生什么 | 隔离的东西 |
| --- | --- |
| `pnpm dev` 改写你正在用的 `workspace.json`，站点与账号跟着变 | userData 目录 |
| 两边的单实例锁在同一个 userData 里，先开的赢：后启动的进程静默退出并唤起另一个窗口 | userData 目录 |
| 两边的浏览器 profile 落在同一个 `profiles/`，两个 Electron 版本互相写同一个 Chromium profile | userData 目录 |
| 两个窗口挤进同一个任务栏按钮，没法分别固定/切换/关闭 | AUMID |
| 一个端点抢到 47821，另一个等满重试梯度后报「端口被占用」 | MCP 默认端口 |

判定逻辑在 `src/main/user-data.ts`（纯函数，有单测）。**显式指定目录的调用方不受影响**：
e2e 与截图脚本各自传 `--user-data-dir`（或 `ENSEMBLE_USER_DATA`），这些标记优先，否则每一轮测试都会
写进开发者的真实工作区。

所有写入使用「临时文件 + rename」保证原子性，`vault.json`、`mcp.json`、导出文件以 0600 权限写入。

## 界面语言

`settings.locale` 是三值：`"system"`（默认）/ `"zh"` / `"en"`。**默认值不写死任何一种语言**——
硬编码的默认语言等于替用户做决定，而应用没有依据判断用户读哪种语言。

解析规则在 `shared/locale.ts`（纯函数，不依赖 Electron）：

- `resolveLocale(setting, systemLocale)`：显式值优先，`"system"` 回落到系统语言。
- 系统语言 tag 由主进程通过 `app.getPreferredSystemLanguages()[0]` 取，随
  `WorkspaceSnapshot.systemLocale` 下发。**不能用 `navigator.language`**：它跟着应用自己设的
  `--lang` 走，问它只会读回应用的选择。
- `--lang` 启动开关用同一个解析结果，所以被测页里的 `navigator.language` 与应用语言一致
  （站点若按浏览器语言本地化，看到的就是用户读的那一种）。
- core 层拿到的是**解析后的** `"zh" | "en"`，不是三值。三值只在设置与渲染层存在。

**DevTools 面板是应用自建的原生视图，停靠在页面右侧。** `openDevTools({ mode: "right" })` 在
启用 `titleBarOverlay` 的 Windows 上只会落成独立窗口（已实测），所以面板由一个
`WebContentsView` 承载，`setDevToolsWebContents` 把前端指过去，页面与工具在同一格位里分成
两部分，中间留 7px 真实缝隙给渲染层的分隔条。

两个容易踩的坑（详见 `docs/engineering/踩坑库.md`）：宿主视图必须在
`setDevToolsWebContents` **之前**拿到非零矩形，否则前端在零尺寸里初始化、内容层永远不会建立；
往 `devtools://` 文档注入脚本（`executeJavaScript` 或自建 CDP 会话）同样会让前端起不来且不报错。

因此应用**不代答**前端那句「切换到中文」的提示条：它的答案存在 Electron 从不持久化的宿主偏好里，
而唯一能点掉它的方式就是注入脚本。前端语言跟随 `--lang`，首次出现的一次性提示由用户自己点。

面板顶部的 26px（`EMBEDDED_DEVTOOLS_HEAD`）让给渲染层画标题带和关闭键：原生视图盖在 HTML 之上，
关它的按钮只能画在视图之外的那条缝里。同样因为它是原生视图，`devtoolsOpen()` 判的是「有面板
**且** 页面此刻有格位」（`cellOf(tab)`）——面板只为台上页面停靠，空白页没有格位，报告为开就会
留下一条没有面板的缝。

## 首次运行

新装第一次打开时自动弹出**使用指南**（`GuideDialog.vue`）：一个居中的分页窗口，八页，
每页一件事——左半一张内联 SVG 示意图，右半最多三条要点。页面顺序就是产品的介绍顺序：

1. `isolation` — 它首先是个浏览器；特殊之处是每个实例各自隔离，几个账号能同时开着
2. `twoSystems` — 档案/书签（用什么身份上网）与站点/账号（测哪个系统、谁的登录）两套体系
3. `compare` — 选几个身份并排看同一套系统，权限差异摊在一屏里
4. `mcp` — 在设置里打开 AI 接入，把配置贴进任何支持 MCP 的客户端
5. `aiActs` — AI 能读结构、点按钮、读控制台，每次调用都有记录
6. `headless` — 界面完全关掉，AI 照样在后台调用这些页面，不弹窗、不抢焦点
7. `devtools` — 停靠的开发者面板：设备模拟与性能监视器
8. `reopen` — 关掉就不会再打扰，从工具栏右端的应用菜单再打开

顺序经过一次推翻：最早的首屏先讲「建站点 → 录账号 → 启动」，那是产品的配置成本，不是它
是什么。这个项目面向开发与测试，「同一套系统里每个身份看到什么」才是要回答的问题，AI 是把
每个身份边界跑一遍的手段，所以 AI 排在手工路径之前，而「多个隔离实例」排在最前——它是这个
浏览器与普通浏览器的唯一区别。

页面数据在 `onboarding/guide.ts`（纯数据，不 import 组件），每个 id 对应的场景组件在
`GuideDialog.vue` 的 `SCENES` 表里解析，`Record<GuideScene, …>` 让漏挂场景在类型层就报错。

**每个场景只播一次入场，然后停在终态。** 这一点有过一次返工：所有动画最初都是
`infinite`，每 5.2 秒把整个画面从 `opacity: 0` 重新拼一次，读者停在那页会看到插图反复闪空。
现在只有真正表示「持续发生」的元素循环——无头页的心跳曲线、MCP 页沿线路跑的数据包、
AI 动作页轮流点亮的三个标记；窗口折叠、围栏绘制、菜单展开这些是一次性事件，播完就停。
分页切换时场景组件靠 `:key` 重新挂载，所以翻回来自然会重播，这也是唯一需要重播的场合。

关闭即记为已读（`settings.guideVersion`），之后从工具栏右侧的应用菜单（「使用指南」）随时
重新打开；内容大幅改动时递增 `GUIDE_VERSION`（`onboarding/guide.ts`），让读过旧版的人再看
一次新版。

它取代了以前的高亮引导（spotlight tour）。那种形态在这个产品里失败了两次：它指向真实控件，
界面一改高亮就落在空处；而且一串气泡只教「按钮在哪」，从不说这个产品要做什么。

## 进程生命周期

- 应用是浏览器实例的唯一所有者，`workspace.json` 里不持久化运行中实例。
- **单实例锁**：`app.requestSingleInstanceLock()`。第二个实例直接退出并唤起已有窗口，
  避免两个进程各自启动浏览器、争抢 MCP 端口、并发写 `workspace.json`。
- **托盘模式**（默认开）：窗口关闭只 `hide()`，进程、浏览器、MCP 端点继续运行。
  托盘菜单提供「打开」与「退出」；设置页也有「彻底退出」。
- 所有退出路径（托盘菜单、设置页按钮、系统关机、`app.quit()`）都收敛到
  `shutdownAndQuit()`：先 `mcpServer.stop()`，再 `tray.destroy()`，最后
  `service.shutdown()` 回收浏览器。顺序不能反——否则 AI 可能在浏览器回收途中发起新启动。
  退出在每个步骤完成后向 `main.log` 写一行 `quit: <step>`（`shutdown-start`、
  `mcp-stopped`、`tray-destroyed`、浏览器回收等），卡住的退出以最后一行指认停在
  哪一步，抛错则写 `failed`——顺序打点，不改变行为。
- 外部表面的批量启动是原子的：中途失败会回收本次已拉起的窗口，不留下半套。
- `window-all-closed` 在托盘模式下直接返回，不触发退出；关闭托盘模式后恢复原有行为。
- 干净会话的 profile 放在 `profiles/<siteId>/clean-*`；不属于任何站点的空白会话放在
  `profiles/clean/clean-*`，独立分段，删除站点不会误停它们，启动清扫仍会覆盖。
- 启动时清理 `--user-data-dir` 指向自有 `profiles/` 根目录的残留进程。
- 停止单个实例：CDP `Browser.close` → 等待 → 按 PID 兜底。
- 退出应用时先优雅关闭全部实例，再退出主进程。

## AI 接入（MCP）

```
AI 客户端 ──HTTP POST /mcp──▶ McpServer ──▶ WorkspaceService ──▶ 浏览器
              Bearer Token        tools/call      同一套业务方法
                                            └─▶ EmbeddedBrowser（内置表面）
```

- 传输：回环 HTTP，路径 `/mcp`，固定端口（`mcp.json`，默认 47821）。无状态，
  只处理 POST；`GET`/`DELETE` 返回 405。
- 协议：MCP JSON-RPC 子集（`initialize`、`ping`、`tools/list`、`tools/call`、
  `resources/list`、`prompts/list`）。不引入官方 SDK，避免为几十行协议给安装包加依赖。
- 鉴权：`Authorization: Bearer <token>`，`timingSafeEqual` 比较；`Host` 必须是
  `127.0.0.1:<port>` 或 `localhost:<port>`，`Origin` 必须是回环——两层分别挡 DNS 重绑定
  与浏览器跨源请求。
- 权限门：工具分 read / write / run / danger 四档，后三档由设置页开关控制。
  删除类还要 `confirm: true`。
- 必填校验：`inputSchema.required` 在执行前统一检查（`confirm` 除外，它由工具自己给出
  更有指向性的提示）。少了这个检查，一个空选择器会让点击落到页面第一个元素上。
- 凭据：工具可以写密码，但**没有任何读密码的工具**，返回值里也没有明文。
- 审计：每次调用追加一行 JSON 到 `mcp-audit.log`，`password|passphrase|token|secret`
  字段递归替换为 `[redacted]`。`type_browser_text` 的参数叫 `text`，名字上看不出秘密；
  它聚焦目标后会回读 `input[type=password]`，是密码框就在结果里置 `secret: true`，
  MCP 层据此把这条 `text` 也换成 `[redacted]`。不做这一步，AI 给新建租户设置初始密码时
  明文就必然落进审计日志。**碰到页面的调用还记一个 `origin` 字段**，回答「AI 在这个站点上
  做了什么」不需要再按时间窗去 Join；同一事件也推给渲染层，实例行的 AI 三态点据此点亮
  （正在操作呼吸、30 分钟内动过常亮），明细在 AI 记录页。
- 浏览器工具与账号工具同权：`run` 档同时覆盖「启动窗口」和「操作内置页面」，因为两者
  都是对现场的改动而不是对数据的改动。`open_browser_tab` 带 `identityId` 时与手动入口
  一样走 `scheduleEmbeddedFill`，AI 不必额外记得调 `fill_browser_login`。
- **档案页面的操作范围可配**（`shared/ai-policy.ts`）：档案页面是真实登录态，所以 AI 在
  那里默认只能读——读页面、截图、切标签、等待都放行，点击 / 输入 / 填表 / 填登录 /
  执行表达式 / 跑流程一律拦在 `tool.run` 之前。账号页与干净会话不受限制，那本来就是给
  AI 驱动的。
  四个档位（`mcp.json` 的 `aiMode`）：`allowlist`（默认，只在名单内可操作）、`denylist`
  （名单内只读）、`allow-all`（完全放开）、`deny-all`（全部只读，含已列地址）。
  **名单（`aiOrigins`）与档位分开存**：切到全允许或全拒绝时名单原样保留，切回来继续生效——
  否则「为了方便放开一小时」就等于把配置删了。名单支持手输地址与从书签一键加入。
  实现上靠 `ToolDefinition.inputTarget` 声明「这个工具碰到哪一页」，闸门在 `tools/call` 里
  统一执行一次——新加一个输入类工具只要声明它，不会忘记过闸。
  一个尚未授权的来源会被拒，但**读仍然可用**，这样 AI 至少能看清页面再向用户要授权。
  **判定只有一份**：`aiWriteDenial` 说该不该放行，`aiGateState` 把它折成界面能画的三种状态
  （可操作 / 已被拒 / 未决定）。工具栏面板用它显示当前页的结论，不再自己读一遍档位——
  那份手写副本迟早会和服务器给出不同答案。
- **授权维度是来源（origin），记录的上下文另算。** 判定只看 `identityId / clean / origin`
  三个事实（`AiPageContext`）；档案与站点是给记录和弹窗看的事实，由 `actionFacts` 单独提供。
  两者分开是刻意的：允许决策依赖的字段越少，越不会被「日志想多记一个字段」顺手扩张。
- **未授权的来源会问人，不直接拒**：`allowlist` 下遇到没决定过的来源，闸门弹一张授权卡片
  （见下节），而不是把 `只读` 丢回给 AI。名单里明确禁止的、以及 `deny-all` 两个绝对档位
  不弹——那是用户已经给过的答案，反复再问只是骚扰。
  四个答案：**本次允许**（只放行这一次）、**本次运行都允许**（进 `sessionGrants`，只在内存，
  停端点即清）、**始终允许**（写进 `aiOrigins`，与设置页同一份数据）、**拒绝**（超时也是拒绝）。
  拒绝的文案明确要求 AI 停下来告诉用户，不要重试也不要换工具绕过。
- **授权卡片是主进程提的问题，不是渲染层的对话框**：`main/approval.ts` 的
  `ApprovalCoordinator` 只做队列与超时（纯 Node，可单测），窗口由 `index.ts` 的
  `ensureApprovalWindow()` 负责——与悬浮条同样的无边框/置顶/`setBounds` 定位，右下角、
  16px 边距、主窗口所在显示器。`answer` 通道校验发送者必须是那个窗口：四个渲染进程共用一个
  preload，权限决定的来信方必须是被展示的那张卡。
- **导航目标必须来自用户或工作区**：`navigate_browser_tab` 只允许空白页的首次导航、
  同源链接、或工作区里已有的站点 / 书签地址。这条防的是提示注入——页面正文里的文字不能被
  AI 当成下一步要去的地方。导航本身不受档位限制：移动页面不等于往用户账号里打字，
  「到了之后能不能操作」才是 `aiWriteDenial` 的问题。
- **AI 自己开的无身份标签是干净会话**：`open_browser_tab` 不带 `identityId` 时显式传
  `clean: true`。否则 AI 能自己造一个落在默认档案里的标签，等于绕过上面那道闸门。
- 生命周期：与主进程同生共死。`stop()` 先 `closeAllConnections()` 再 `close()`，
  保证客户端保持长连接时也能立即释放端口。

### AI 记录

AI 在页面上做了什么，是一个**记录**，不是通知。它有过一段住进消息中心的历史，那次尝试说明了
两件事：一次自动化能写满 500 条的共享上限，把真正的登录问题挤出去；而按 tab 去重的行会把
一次点击和紧随其后的输入折成同一行，工具名还停在第一次那个。

- 存在 `<userData>/ai-activity.json`（`core/ai-activity.ts`），自己的上限 1000 条，自己的
  去重键（工具 + 结果 + 是否被拒 + 授权结论 + 来源，10 秒窗口），**没有已读状态**——没人需要确认
  AI 点了一下，一个随调用增长的徽标只是把这堆噪音挪了个位置。
- **每条调用留一份可核查的细节。** `details` 最多 3 条，每条存脱敏后的参数与结果摘要；
  `evaluate_browser_page` 的摘要行以脚本首行开头，展开能看到完整脚本与结果（结果截断到
  4000 字符）。`type_browser_text` 的正文永远记成 `[redacted]`，密码字段不进库。历史记录
  没有这部分，不补造。
- 每条带 `origin / siteId / identityId / profileId / clean / tabId / tabTitle / ok /
  originAuthorized / approval / error`。站点与档案不是判定依据，是读记录时要回答的问题
  （「它在这个站点的哪个档案里做的」）。**`partition` 不写进记录也不返回给 AI**：默认档案
  的历史分区名里带着 "clean"，读它的人会把长期会话误判成一次性会话。
- 分组在 `shared/ai-activity.ts` 里做，面板与页面共用：有已知站点按 `siteId`，没有就按
  origin。两处各写一份的那天，面板会换一种方式分组而没人发现。
- 入口两个：工具栏的 AI 按钮（面板里最近两个站点、各三行，加当前页的授权状态与服务状态），
  以及「更多」里的「AI 记录」分区（全部站点、全部行、可清空）。面板**不**承担编辑完整策略的
  职责——那是设置页的 `AiPolicyEditor`，四个档位与整张名单在那里。记录页与消息页都走
  `.page` + `.page-body` 的固定页头 / 单滚动区契约，长历史不会把后面的行裁掉。
- 写入发生在 `onPageAction` 里，且**在检查窗口是否存在之前**：应用收在托盘里时 AI 照样在动，
  只记屏幕上看得到的调用等于漏掉最没人看着的那些。

## 导入导出

两种格式，用途不同，不要混用。

**配置导出**（`shared/transfer.ts`，`format: "ensemble.workspace"`）是整机迁移：把站点、账号、
视图、标签、布局预设全部带走，**按 id 合并**。`WorkspaceService.exportWorkspace / importWorkspace`
负责组装与合并。

- 导出不含运行实例、Profile、登录态。
- 密码可选：给定口令时用 `createKdfParams` + `seal` 把 `{environment, identity}` 密码表
  加密成 `secrets.payload`，与 vault 同一套 scrypt + AES-256-GCM。
- 导入按 id 合并，缺失所属站点的条目跳过并计数；有加密段但口令错误时整体抛错，
  不写入任何数据。

**账号包**（`shared/accounts-transfer.ts`，`format: "ensemble.accounts"`）是把登录交给别处：
只挑几个站点、几个账号，不带走你的视图与布局。

- 匹配键里**没有 id**：站点按 `baseUrl`、账号按 `baseUrl` + 小写 username。接收方的
  workspace 有自己的 id，用发送方的 id 去合并只会覆盖无关账号或造出重复项。
- 密码同样用口令密封；`secrets` 里的键就是 `accountSecretKey(baseUrl, username)`，接收方
  可以自己重算，所以解密后的密码能准确落到对应账号上。密码可选，不带口令时只导资料。
- 文件里每个站点 / 账号带 `hasPassword`，接收方据此知道「这个账号本来有密码但没解开」，
  不会保存一个永远登不进去的账号却什么都不说。
- 导出路径：界面走保存对话框；MCP 没有可以应答对话框的人，固定写到
  `userData/accounts-export/`，文件路径作为返回值给 AI。

## 版本检查与安装

`shared/update.ts` 负责解析 GitHub Releases API 的返回并比较版本，`src/main/index.ts` 的
`app:check-update` 在 8 秒超时内请求 `/releases` 列表（`per_page=100`）。更新提示把当前版本
（不含）到最新版本之间的全部 release 各展示一节，升序排列，最多 10 节，更早的折叠为一句计数；
单个版本没有说明就显示占位文案。

- 检查是自动的（启动后一次、之后每 6 小时），**下载与安装都必须由用户点一下**。
- 版本号比较按点分段数值比较，不是字符串比较（`0.10.0` 比 `0.9.0` 新）。
- 返回体不符合预期（代理错误页、tag 名不是版本号）一律按「检查失败」处理，不猜版本。
- 下载走 `net.request`（`src/main/update-fetch.ts`），**每一跳重定向都校验域名**，只认
  `github.com` / `githubusercontent.com` 及其子域；离开这两家就中止。不能用 `net.fetch`：
  它在 Electron 里从不填 `Response.url`，逐跳判断拿不到事实（见踩坑库 2026-11-09）。
- 安装包必须先与 GitHub 发布的 `digest`（SHA-256）对上才落盘为最终文件；没有摘要按
  「无法验证」处理，不降级为「照样装」。下载写 `<file>.part`，中断不会留下一个像样的安装包。
- Windows 上由脚本等待主进程退出后静默安装并重启（NSIS 不能覆盖正在运行的 exe）。
  产物未签名，UAC / SmartScreen 提示仍可能出现，这需要证书才能消除。
- 用户点「打开 Releases」时由主进程用 `shell.openExternal` 打开，渲染层只能传
  `http(s)` 地址。

## 安全边界

- 渲染进程：`contextIsolation: true`、`nodeIntegration: false`，导航与 `window.open` 一律
  拦截，外链交给系统浏览器。主窗口开着 `webviewTag`（内置浏览器的页面宿主，见
  「内置浏览器」一节），其余窗口不开。
- 内置浏览器的页面是远程内容：`nodeIntegration: false`、`contextIsolation: true`、
  `sandbox: true`，不挂任何 preload；权限请求（摄像头、麦克风、定位、通知）默认全部拒绝，
  需要时在 `configureSession` 里逐项放开。
- 内置表面只允许 `http(s)` 与 `about:blank`；`file:`、`javascript:`、`data:` 一律拒绝，
  页面不能借内置浏览器访问本地文件。
- IPC 入参全部经过 Zod 校验；密码不在任何 IPC 返回值中出现。
- 密码只存在于主进程内存与加密后的 `vault.json`。
- 自动填充前校验当前页面 origin 属于目标站点，且与站点记住的 `lastOrigin` 一致，否则拒绝或要求确认。
- **启动自动登录例程**：站点配了 `authCheckPath` 时，内置表面的每次账号启动都会先在页内
  fetch 检查路径判定登录态（结果只留在主进程），未登录则导航到 `site.loginPath` 填充凭据；
  是否替用户点提交由 `site.autoSubmit ?? settings.autoSubmitLogin` 决定（站点可选覆盖，全局
  默认开启），这个开关的语义就是「授权自动提交」，提交动作是点登录按钮本身而不是提交表单。
  登录确认后页面回到账号 `startPath`。**接口信封式后端**（200 也表示未登录、结果在 body 里）
  会在站点上配 `authCheckSignedOut`：探测对响应 body（前 4 KiB）做子串匹配，命中即按未登录
  处理，HTTP 状态不再单独定案。**私订头令牌站点**再配 `authTokenKey`，探测会读页面
  localStorage 的令牌一并发送（见「登录态检测」一节）。凭据的读取与填充全程在主进程，
  渲染层只收到不含密码的 `AutoFillReport`。没配检查路径的站点维持旧行为（等密码框出现
  就填，仅此而已）。
- MCP 端点只绑回环、必须带 Token、校验 Host/Origin；工具永远不返回明文密码。

## 自动化运行（headless）

所有端到端脚本与截图脚本都启动一个真实的应用进程，并用 CDP 驱动它。这些进程设
`ENSEMBLE_HEADLESS=1`，含义是**不出现在桌面上**：主窗口以零不透明度显示、不进任务栏、
不抢焦点，托盘图标、运行实例悬浮条、切换回执都不创建，`focusPage()` 只通知渲染层换页而不抬窗口。

两个实现细节值得记住，两者都只有实际跑过才能发现：

- **窗口必须 `show()`，不能只创建不显示。** 从未显示过的窗口不产生合成帧，而 guest 的
  合成器跟着宿主走：`Page.captureScreenshot` 会一直挂着而不是返回图片（实测从 ~100ms 变
  永不完成）。所以是「以零不透明度显示」，不是「隐藏」——`show()` 之后立刻 `setOpacity(0)`。
- **`focusPage()` 的两半要拆开。** 它同时做「抬窗口」和「通知渲染层切到浏览器页」；
  headless 模式下跳过前者、保留后者，否则脚本驱动的页面在界面上根本不会被切过去。

`tests/headless-runs.test.ts` 静态守着这条契约：开关存在、窗口是被移走而不是隐藏、
四个会出现在桌面上的表面（悬浮条、回执、托盘、`showMainWindow`）都尊重开关，
以及每个脚本都真的传了环境变量。
