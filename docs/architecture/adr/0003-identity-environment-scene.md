# 0003. 三层模型与凭据边界

- 日期：2026-10-19
- 状态：已采纳

## 背景

需求是「同时登录多个账号做权限与协作测试」，讨论中出现过「环境管理多个账号体系」
「profile 与账号分离」「顶层统一密码库」等几种模型。

## 决策

```
Environment 1─N Identity
Environment 1─N Scene
Scene       N─N Identity（只引用，不复制）
```

- **环境**：被测目标的作用域（baseUrl、登录入口、检测地址、类型）。不隔离。
- **身份**：一个账号 + 一个独立 profile。隔离单元。
- **场景**：一次测试要一起拉起的身份组合与窗口布局。不隔离。
- **凭据边界**：身份存自定义密码；环境存默认密码；应用顶层只存加密密钥与配置，
  不维护全局账号库。

## 被否方案

**再加一层「账号体系」**：profile 本身就是账号的身份卡，再拆一层会出现「profile 对应哪个
账号」的二次查询问题，过期重登时用户还得反查。

**顶层全局账号库 + 环境引用**：同名 admin 在 dev 与 staging 不是同一个账号，全局库会绑错、
误填；删除身份后还会留下孤儿凭据。所有环境共用一个种子密码时，用「环境默认密码」即可。

**profile 跨环境复用**：不同环境的 Cookie 域不同（甚至不同主机），复用会串登录态；
本地换端口不隔离 Cookie 也是同类问题。同一账号测两个环境就建两个身份。

## 后果

- 删除身份时同时清掉它的自定义密码；删除环境时清掉环境默认密码与所有成员。
- 换引擎是「复制身份生成新 profile」，不是改字段，因为 profile 格式与引擎绑定。
- 未来的团队共享或云同步需要重新设计凭据层，不在当前范围。
