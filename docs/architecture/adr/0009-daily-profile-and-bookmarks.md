# 0009. 日常档案与独立书签

- 日期：2026-10-24
- 状态：已采纳（修订 [0008](./0008-sites-as-login-recipes.md) 的第 4 条）

## 背景

[ADR 0008](./0008-sites-as-login-recipes.md) 第 4 条定的是「站点即书签，不新增书签实体」：
站点本身就是书签，三个入口共享同一份站点列表，落点只有「干净打开」与「用某个账号打开」。

那条决策成立的前提是「内置浏览器只用来做多身份验证」：每个打开的页面都该属于一个明确的
账号或一个明确的一次性会话，所以「打开某处」和「打开某个登录配方」是同一件事。

产品定位扩展成「同一套系统里多个身份同时在场」之后，出现了两个前提之外的需求：

1. **日常使用**。用户想直接拿这个浏览器当日常浏览器，并且让 AI 在**已登录**的档案上帮忙
   做后台操作。这要求存在一个稳定的个人档案，登录一次长期有效。
2. **不属于任何站点的地址**。文档站、内部工具、随便一个链接——它们不需要登录配方，也不该
   被要求先建一个站点。

同时暴露了一个既有实现的事实错误：所有无身份标签落在 `persist:embedded-clean` 上。它是
**持久**分区，所有无身份标签共用同一个 cookie 罐，重启后仍在。名字承诺的「干净」和实际行为
完全相反：既不是干净会话，也不是一个稳定的个人档案。

## 决策

### 1. 无身份页面落在「日常档案」

所有没有身份归属的页面（新标签页、书签、地址栏输入的地址）落在同一个**持久**分区，登录一次
长期有效。

分区字符串沿用旧值 `persist:embedded-clean`。这是刻意的：用户升级前已有的登录全在那个分区
里，换新名字等于把所有人在所有站点上一次性登出。名字不准确，但迁移的代价更贵；真正的语义
由常量 `EMBEDDED_DAILY_PARTITION` 和文档承担。

### 2. 干净打开是每个实例一个内存级会话

干净打开用 `embedded-clean-<实例 id>`，**不带 `persist:` 前缀**，Electron 因此只把它放在内存里：
退出进程即消失，两次干净打开互相也看不到。同一实例里页面打开的弹窗继承该实例的会话，登录
流程里的 popup 不会掉进日常档案。

按实例而不是全局一个会话，是因为「干净」的承诺有两层：不留在磁盘上，以及不跨窗口泄漏。

### 3. 书签是一等对象，与站点分开

书签是名字、地址、图标、顺序，加上一个可选的 `folderId` 指向书签文件夹树
（`BookmarkFolder`：id、名字、`parentId`，可多层嵌套）。没有凭据、没有登录路径、
没有默认引擎、不引用站点。文件夹是独立记录而**不是书签上的名字标签**——单层目录时代
曾是标签，多层嵌套让「改名中层节点要级联重写所有后代路径」成为不可接受的写放大，
树拥有名字、书签只指向叶子（2026-10-29 定稿，取代此前「文件夹按名字存」的方案，
见被否方案）。

两者靠**结果**区分，不靠概念解释：

| 点它 | 发生什么 |
| --- | --- |
| 书签 | 直接打开那个地址，用日常档案里已有的登录 |
| 站点 / 账号 | 打开登录页并自动填充，进那个账号自己的分区 |

「从站点打开」因此有三行：日常打开（默认）、干净打开、用账号打开。

### 4. 书签随工作区迁移，但重新编号

导出导入带上书签和文件夹树。导入时 `order` 从本地末尾重新分配，不采信文件里的绝对值：
两台机器都从 0 开始编号，直接采用会把两组书签交错在一起，而用户期望的是「新增的排在后面」。
书签的 `folderId` 只在同一个文件里带着那个文件夹时才保留——导入半棵树不能把书签指向
谁都没有的文件夹。旧版文件里按名字存的文件夹标签，读取时迁移成真实的顶层文件夹。

此外支持从本机已安装的 Edge / Chrome / Firefox **直接导入书签**（`core/bookmarks-import.ts`，
只读解析它们的书签文件，浏览器自身不被改动；Firefox 的 places.sqlite 复制临时副本后用
`node:sqlite` 只读打开，绕开 WAL 锁）。导入按浏览器原有分组落成「<浏览器> 书签」顶层文件夹，
地址按与工作区相同的 URL 规范化去重，被去重清空的分支自动剪枝，重复导入幂等。

## 被否方案

**把书签建成「没有账号的站点」。** 那样每个书签都要有一段登录路径和一份默认凭据槽位，用户
为了存一个文档链接得先填一份他永远用不到的登录表单；而且「点它是打开地址还是打开登录页」会
变成数据里的一个隐含开关，而不是一个清楚的对象类型。

**干净打开继续用持久分区，只在退出时清理。** 这要求退出路径可靠地清空一个可能被别的进程
占用的分区目录，中途崩溃就漏；而且同一进程内两次干净打开仍然共享 cookie，等于「干净」只在
重启这个维度上成立。内存分区把这个维度的承诺直接交给 Chromium 的生命周期。

**把 `persist:embedded-clean` 改名成 `persist:embedded-daily` 并做一次迁移。** Chromium 的分区
目录按分区名散列，改名就是换目录；迁移要在启动时搬动整个 Cookies / Local Storage 目录，
失败一次就是全体登出，收益只是名字好听。保留旧名、用常量与文档讲清楚，成本低得多。

**给书签也做「从当前页新建站点」的对称入口。** 当前页能提供的只有地址与标题，不足以生成一份
登录配方；弹一个要填登录路径和核对表单的对话框，反而打断用户正在做的事。新建站点仍在站点页
与「从站点打开」里。

**书签文件夹按名字存在书签上，不建独立记录**（2026-10 单层目录时代的选择，2026-10-29 被
多层目录需求推翻）。名字方案的收益是「无孤儿、无空文件夹、删除即解散」，但这些只在单层
成立：一旦目录可嵌套，改名一个中层节点就要重写所有后代书签的路径，分隔符转义和空名歧义
也随之而来。改为 id + parentId 的树后，改名与移动子树都是一次写；删除文件夹改为把内容
上提一级，孤儿规则从「不可能有」变成「删除时重挂」。

## 后果

- 升级后用户已有的登录态全部保留（日常档案就是旧分区），首次打开见到的是自己原来的登录状态。
- 「干净打开」的语义第一次成立：关掉窗口、退出程序，登录都不在了。之前四处文档里「不带任何
  账号的登录态」的说法，在这个版本之前是错的。
- 书签与站点并存，界面需要让两者的差别在**用一次**之后就明白，而不是靠一段教程。新标签页
  的书签网格与「从站点打开」的三行结构就是为此服务的。
- 登录态成为日常状态之后，AI 在登录档案上的权限必须收紧（按来源只读、来源级审计）。这条是
  下一步，不是本决策的一部分，但它是本决策的直接后果。
