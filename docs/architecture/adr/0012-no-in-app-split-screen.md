# 0012. 应用内分屏与应用内多视图不做，舞台单格

- 日期：2026-11-17
- 状态：已采纳（[0007](./0007-site-and-view-model.md) 引入的视图对象随之退役，
  推进计划见 [`../../plans/single-stage-simplification.md`](../../plans/single-stage-simplification.md)）

## 背景

四宫格与视图的原意是并排对比多账号：一个视图把一组身份摆进格子，同屏观察同一站点
在不同账号下的表现。视图也因此背上了三个职责——启动分组、布局排列、停靠分组。

真实使用的证词来自两处：作者本人与外部用户。双方的使用习惯一致：

- 应用内分屏从不用。四宫格摆好之后，真正观察时靠的仍是切换、AI 记录和截图。
- 多屏与系统级窗口并排才是真实习惯。需要并排时，用户本来就把窗口拖到第二块屏，
  或用操作系统的窗口分屏——应用内再提供一套格子几何是重复造轮子。
- 用户反馈概念过载：视图、格子、停靠、分屏各自是一套词汇与交互，
  为一个没人用的能力付出了整层界面的理解成本。

## 决策

- **应用内分屏与应用内多视图不做。** 舞台永远一格：当前选中的浏览器实例上台，
  其余实例后台运行，登录态与 AI 可操作性不受影响。
- **并排对比由「拆窗到独立 OS 窗口 + 系统分屏」承接**（P2 期）：实例的页面容器
  （`WebContentsView`）可挂到独立 `BrowserWindow`，剩下的布局交给操作系统。
- **同账号标签拖拽分屏不做。**
- 界面上的视图入口与格子几何交互随之移除；workspace 数据里的 `views` 字段
  静默保留，无 UI 读写入口。

## 被否方案

**保留四宫格、藏进设置**：复杂度没有消失，只是看不见。格子几何、静默替换格子、
拖拽分区的全部代码与测试仍要维护，而使用证词是零。藏起来只降低新用户的困惑，
不降低维护成本，还多出一个藏的位置要解释。

**临时二分对比模式**：YAGNI。当前没有任何真实场景需要「恰好两个并排」——
证词表明需要并排的人都直接用系统分屏。真出现这类需求时按当时的场景设计，
现在预留一个形状未知的模式只会成为死代码。

**同账号标签拖拽分屏**：理解得了不等于用得上。拖拽交互本身可学习，
但证词显示没有人用它完成对比；为此保留的整套分屏布局机制是纯负担。

**多窗口即多套管理台**（每个窗口一套完整 UI）：等于把概念过载复制 N 份——
每个窗口都要让用户重新面对一遍全部导航与词汇。采用的本方案是
「单管理台 + 可拆出的纯实例窗」：管理概念只存在一份，拆出去的窗口只有页面容器。

## 后果

- `embedded-cell-geometry` / `embedded-slots` / `embedded-views` 等一大片测试
  与对应实现随 P2 收缩：UI 单格化后内部先保留 1 槽，几何与多槽代码逐步拆除。
- README 截图与叙事更新：从「同屏多账号」改为「同时在线」，并排观察的介绍
  改为拆窗 + 系统分屏。
- 存量 `views` 数据保留在 workspace 里，无 UI 入口；未来若出现「保存启动组合」
  的真实需求，在设置里另立「启动预设」，届时再议数据形状。
- 在拆窗落地之前，多账号并排观察退化为「切换 + AI 记录 + 截图」；
  后台实例的 AI 可操作性保持不变。
