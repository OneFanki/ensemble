# 踩坑库（Known Pitfalls）

> 遇到报错、现象诡异、行为不符预期时，先查这里再排查。坑是经验型知识：不进 README、
> 不进架构文档，只在这里按条目累积。
>
> 维护规则：解决后当场追加条目（含日期）；失效条目标记 `状态: 已过时` 并注明原因，
> 不删除。代价高的坑（数据损坏、账号串号、凭据泄漏、进程失控）解决后，必须同步升级为
> `AGENTS.md` 硬约束。

## 浏览器启动与 CDP

### 场景启动失败：`启动 Microsoft Edge 失败：fetch failed`

- **环境**：Windows 11，Edge 155，Electron 44，CDP 启动方式
- **原因**：profile 目录里残留上一次运行写下的 `DevToolsActivePort`。新实例启动瞬间读到了旧端口，旧端口已经没人监听，`/json/version` 直接 fetch 失败。
- **解决**：启动前主动删除 `<profileDir>/DevToolsActivePort`；读取后不要只信文件内容，必须同时探活 `http://127.0.0.1:<port>/json/version` 才算就绪。
- **日期**：2026-10-19
- **状态**：有效（已修复并落地）

### 抓到的页面是 `about:blank`，注入脚本无效

- **环境**：Chromium 系浏览器，`--remote-debugging-port=0`
- **原因**：浏览器启动后先出现 `about:blank` 目标，随后才创建真正加载 URL 的页面。直接取 `/json/list` 第一项会拿到空白页。
- **解决**：`waitForPageTarget` 优先选择 `url !== "about:blank"` 的目标，超时后再退化为第一项。
- **日期**：2026-10-19
- **状态**：有效（已修复并落地）

### 原生 `confirm` / `alert` 被自动取消

- **环境**：任何用 Playwright 驱动人工操作场景
- **原因**：Playwright 文档明确：没有注册 `dialog` 监听时，所有对话框自动 dismiss。
- **解决**：人手操作的窗口不要交给 Playwright 托管。用系统浏览器 + CDP，只启用 Page/Runtime 的必要域，不接管 dialog。下载同理：Playwright 默认落到临时目录且 context 关闭即删除。
- **日期**：2026-10-19
- **状态**：有效（架构级约束，禁止回退）

### 浏览器没开远程调试，但也没有报错

- **环境**：企业统一管理的 Chrome / Edge
- **原因**：Edge 策略 `RemoteDebuggingAllowed=0` 会禁用 `--remote-debugging-port`，或安全软件拦截本地端口。
- **解决**：拉起后等 `DevToolsActivePort` 超时，给用户明确提示「可能被企业策略阻止」，并允许改为外部模式。不要静默卡住。
- **日期**：2026-10-19
- **状态**：有效

### 浏览器版本自动升级后 profile 行为异常

- **环境**：系统 Chrome / Edge
- **原因**：profile 格式随大版本迁移，通常单向，不支持可靠降级。
- **解决**：升级前备份 profile 元数据；出问题时新建 profile 重新登录，不要试图把 profile 降级。需要可复现版本时，单独用固定版本 Chromium，不替换系统浏览器。
- **日期**：2026-10-19
- **状态**：有效

### 便携版冷启动比安装版慢一秒多

- **环境**：electron-builder portable target，Windows
- **原因**：portable 产物是一个自解压程序，每次启动都先把 Electron 运行时解压到
  `%TEMP%\<随机目录>` 再拉起主进程，解压本身就要一秒左右，且每次都是冷目录。
- **解决**：日常使用装 `setup.exe` 或直接跑 `win-unpacked\Ensemble.exe`；便携版只用于临时
  试用。判断当前在跑哪种形态，看进程命令行路径是否在 `%TEMP%` 下。
- **日期**：2026-10-19
- **状态**：有效

### 首次启动慢：窗口在等引擎扫描和进程清理

- **环境**：启动时同步执行 `scanEngines()` 与 PowerShell 进程枚举
- **原因**：`Get-CimInstance Win32_Process` 单次约 1.1 秒；引擎探测又要串行跑注册表查询
  和版本探测。这些都在 `createWindow()` 之前，用户看到的是几百毫秒到两秒的空白。
- **解决**：`initialize()` 只读本地 JSON 与引擎缓存，立刻建窗口；进程清理与引擎扫描放到
  `startBackgroundMaintenance()` 后台执行，完成后广播。缓存文件 `engines.json` 记录上次
  扫描结果，启动时先用缓存，再静默刷新。注册表查询和版本探测改为并发。
- **日期**：2026-10-19
- **状态**：有效（已落地）：安装形态二次启动约 660ms，首次约 1.3s

### 右下角 toast 文字被裁掉半截：原生页面视图盖住了伸进舞台的左半截（2026-10-31 二次修正）

- **环境**：Windows，Electron 44，125% 显示缩放，8 账号批量启动后的登录失败 toast，dock 展开态
- **现象**：toast 卡片文字从「…02」的中间开始可见，结尾「管」字丢失——左右各缺一截。
- **⚠️ 曾写错的结论**：本条最初诊断为「fixed 锚点被祖先 transform 劫持」，据此发了 1.3.1 的
  Teleport 修复——**没打中要害**。用户实机复跑依旧被裁。根因是本架构的硬边界：
- **真正的原因**：舞台上的页面是原生 `WebContentsView`，**永远画在一切 HTML 之上**。toast 盒子
  `position: fixed; right: 18px; max-width: 380px`，而 dock 默认只有 292px 宽——盒子左缘
  (视口-398px) 比舞台右缘 (视口-292px) 还要靠左 106px，这 106px 连同折行后的尾字全部被台上
  的原生页面盖住。`getBoundingClientRect` 完全不知道原生遮挡的存在，所以纯 DOM 断言全绿、
  用户看到的依旧是残句。文字侧还有一个叠加因素：30 字文案比 380px 盒子的内容区宽约 1 字，
  恰好折出一个孤字行，孤字也落在被盖区域。
- **解决**：**toast 必须整体落在 dock 矩形内**——宽度钳制 `min(380px, calc(var(--dock-w) - 36px))`，
  `--dock-w` 由 ToastStack 直接绑定 embedded store 的 `dockWidth`（Teleport 到 body 后拿不到
  dock 元素上的同名变量，改为组件自带）。dock 展开态从此完整可见；**dock 折叠态（34px 图标列）
  无解**——任何 toast 都必然压进舞台，彻底解决需要独立原生 toast 窗口（悬浮条同款方案），记录
  为后续方向。Teleport 到 body 保留：它防的是另一类真问题（祖先 transform 劫持 fixed 锚点）。
- **教训**：① 原生视图盖 HTML 是这个架构的第一性约束——**任何浮层的水平范围都必须 ⊆ 它所在
  的 HTML 安全区**（dock / 状态栏 / 工具栏），跨进舞台就是隐形；② `getBoundingClientRect`
  对原生遮挡是盲的，回归断言必须「stack ⊆ dock 矩形」这种**区域包含关系**，而不是只看视口；
  ③ 修复后要让用户实机确认，不能只凭 e2e 绿就宣布修好。
- **回归**：`e2e-toast-geometry.mjs`（9 项）——新增「stack ⊆ dock 矩形」断言（2048×1222 +
  dpr 1.25）。
- **日期**：2026-10-31（同日二次修正：推翻劫持诊断）
- **状态**：有效（展开态已落地；折叠态为已知架构边界）

### 扁平舞台弹 HTML 弹层时，页面整体上移一个标签条高度

- **环境**：Windows，Electron 44，内置表面扁平模式（无布局 / 松散标签，带实例标签条）
- **现象**：点「+」或右键菜单等会弹 HTML 弹层的入口，弹层底下的冻结截图比实况页面高出一截
  （位移 = 26px 头带），弹层关闭后恢复。
- **原因**：`freeze()` 的扁平分支用原始 `stage` 当截图矩形，注释还写着「扁平模式没有头带」——
  那是 2026-10-26 给扁平舞台加实例标签条之前的旧事实。实况摆放（`applyLayout` 扁平分支）用的
  是 `embeddedViewRect(stage)`（顶部让出 26px），冻结截图却从 `stage.y` 画起。多格路径用的是
  `embeddedViewRect(slot)`，所以只有扁平模式中招。
- **解决**：扁平分支同样过 `embeddedViewRect(stage)`，与实况摆放共用同一个几何函数。守则：
  **冻结矩形与摆放矩形必须出自同一个函数**，凡是给摆放加几何偏移的地方，同步检查 `freeze()`。
  回归：`e2e-overlay-freeze.mjs` 新增「扁平冻结矩形 == 实况视图矩形」断言（7 项）。
- **日期**：2026-10-30
- **状态**：有效（已落地）

### 引擎版本号显示为 `-`

- **环境**：Windows，Edge / Chrome
- **原因**：Edge 与 Chrome 的可执行文件固定在 `Application\msedge.exe`，版本号在**同级
  的版本目录**里（如 `Application\155.0.4283.62\`）。`versionFromExecutablePath` 读的是
  父目录名，取不到。另外这两个浏览器执行 `--version` 在 Windows 上不输出任何内容。
- **解决**：新增 `versionFromSiblingFolders()` 读同级的最大版本目录名；Firefox 这类没有
  版本目录的，用一次批量 PowerShell 读 `VersionInfo.ProductVersion`。
- **日期**：2026-10-19
- **状态**：有效（已落地）

### 停放页满速白烧资源：CPU 节流与 hide 都停不掉 rAF，真睡眠是 lifecycle frozen；扫描必须构造时启动

- **环境**：Windows，Electron 44 / Chromium 152，内置表面多账号 + 重页面（3D 首页）
- **现象**：同时跑多个账号时，看不见的停放页（含 3D 场景）依然满速渲染，GPU/CPU 持续被吃；
  Chromium 原生后台节流完全没生效。
- **实测四个事实**（离屏 harness + 同 partition 读者页信标，全程不触碰被测页）：
  1. 停放 = 把视图 `setBounds` 到窗口右缘外。Chromium 的可见性判定不含「子视图在窗口客户区
     外」，页面仍是 visible，`backgroundThrottling`（默认本就开着）永不触发——**前提是应用
     窗口本身在屏上可见**；整个窗口被盖住/移出屏幕时，窗口级遮挡节流会把一切（含台上页）压
     停，这层是 Chromium 送的，不需要我们做。
  2. `Page.setWebLifecycleState: "frozen"` **真挂起 JavaScript**：冻结页上 `Runtime.evaluate`
     永不返回（executeJavaScript 超时实测）。2026-10-30 曾记录「frozen 只浅冻结、rAF 照跑」，
     **那轮测量被污染了**——当时的读数通道走 `EmbeddedCdp.send`，其唤醒钩子会先把页面解冻再
     执行，测到的是解冻后的活页。以本条为准。
  3. `view.setVisible(false)` 连 `document.visibilityState` 都不变（仍 "visible"），JS 照跑、
     rAF 照跑（读者页信标实测）。（`setFrameRate` 仅 offscreen 渲染生效；
     `setVisible(false)` 唯一的实际效果是 compositor 停出帧——这正是当年「CDP 截图卡死」的
     原因，capturePage 仍可用。）
  4. `Emulation.setCPUThrottlingRate` 只拖慢任务调度，rAF 由 compositor 驱动，对 GPU/帧循环
     为主的开销不成比例；作为「睡眠」杠杆被 frozen 取代。
- **解决（2026-10-31 定稿）**：`aiIdleFreeze` = 10 秒扫描，停放页闲置 60 秒（窗口期内无 CDP
  流量）即 `lifecycle "frozen"`（JS 全停，3D 场景随之停）；AI 每条命令在 `EmbeddedCdp.send`
  **await 唤醒**（lifecycle "active"）再执行；回台/导航/刷新也唤醒。豁免：台上/加载中/崩溃/
  空白/有声/带 DevTools。headless 运行整体关闭。
- **⚠️ 第二个坑（1.3.0 实际踩的）**：扫描最初是**惰性启动**（第一次 CDP 命令才建 interval），
  而 CDP 命令只有 AI 才发——纯手工使用的会话里扫描从未运行，降速一次都没发生。扫描必须在
  构造时无条件启动。
- **测量陷阱**：测每页机制时，窗口被盖住/移出屏幕会让遮挡节流淹没一切读数——「测不出差异」
  不等于机制无效； harness 的窗口必须真实可见地摆在桌面上。
- **日期**：2026-10-30（2026-10-31 二次修正：更正被污染的 frozen 结论、换杠杆、修扫描启动）
- **状态**：有效（已落地；最终实机确认待窗口可见的多账号场景）

### `<webview>` 的 guest 截图会一直挂住，直到嵌入方先产出过一帧

- **环境**：Electron 45.2.1 / Chromium（<webview> 载体迁移，P2 前置实验）
- **症状**：`guest.webContents.debugger.sendCommand("Page.captureScreenshot")` 永不返回。
  `Runtime.evaluate` 正常返回页面文本，说明 CDP 已连上、JS 在跑，只有截图挂死。
  换成 `fromSurface: false`、`captureBeyondViewport: true`、`guest.capturePage()` 全部一样挂。
- **原因**：guest 的合成器在嵌入方从未产出过帧时不产出画面，`Page.captureScreenshot`
  等的是合成帧而不是「页面存在」，于是永久 pending。**这不是 webview 独有**，与
  `WebContentsView` 停放窗外时截图挂起是同一条规律（见本文件「CDP 截图路径矩阵」），
  只是 webview 下更容易撞上：窗口刚显示、页面刚 attach、或宿主自己还没画过。
- **解决**：在驱动 guest 之前，先对**嵌入方 webContents** 做一次 CDP
  `Page.captureScreenshot`（实测 146ms，之后 guest 截图 50ms，连续两次 detach/re-attach
  仍正常）。只 attach 宿主不行，必须真正取到一帧；`win.capturePage()` 反而抛
  `UnknownVizError`，不能替代。
- **测量陷阱**：第一个实验用 `data:` URL 做宿主页面，结果宿主自己的 `capturePage` 抛
  `UnknownVizError`、guest 截图全部超时。换成 http 服务的宿主后，**单个 guest 截图
  40ms 正常**。宿主用 `data:` 会污染整个合成器，排查 webview 问题时宿主页面必须走真实
  协议（http 或 file）。
- **日期**：2026-11-04
- **状态**：有效（迁移 P2 必须内建；尚未在正式代码里落地预热）

### 移除 `<webview>` 节点会立刻销毁它的 guest 进程

- **环境**：Electron 45.2.1，`el.remove()` 移除已 attach 的 webview
- **症状**：移除节点后 1.2s 内 `guest.isDestroyed()` 为 true。相邻未移除的 guest 不受影响。
- **原因**：节点即进程所有权。DOM 里没了，Chromium 就回收 guest。
- **解决**：后台标签**不能靠拔出节点来隐藏**，只能留在 DOM 里用 CSS 藏（`display:none`
  实测可行，guest 存活且 evaluate 正常，但截图同样需要先预热合成器）。这条直接决定了
  「一个标签一个常驻节点」的架构，也决定了 teardown 必须先 detach 再让渲染层移除节点。
- **日期**：2026-11-04
- **状态**：有效

### guest 只有留在窗口内才产帧：`opacity: 0` 保得住，挪到窗外保不住

- **环境**：Electron 45.2.1，`<webview>` 节点用固定定位摆放
- **症状**：把后台页面的节点移到 `left: -1147px`（窗口左边缘之外）之后，
  `Page.captureScreenshot` 又开始永不返回。同一页面在舞台上时，裸 CDP 截图正常返回。
- **原因**：合成器的裁剪是按**窗口可见区域**算的，不是按 opacity。节点完全在窗口外时
  整个 guest 被 cull，和 `visibility: hidden` 是同一个结果。
- **解决**：隐藏用 `opacity: 0` + `pointer-events: none`，节点必须留在窗口矩形内；
  只有在需要截图而页面又确实在窗外时，才把它**挪回**舞台（改 `left/top/width/height`）
  再截，截完挪回去。只翻 opacity 不够——那是把一个被裁掉的页面变透明。
- **附带结论**：`opacity: 0` 的 guest 同时保持真实视口与截图能力，所以「后台标签用
  display:none」是错的：`display:none` 让视口变 0×0，页面里所有 `checkVisibility()`
  返回 false，AI 读到的是「元素不存在」。
- **日期**：2026-11-04
- **状态**：有效（`GuestPool.vue` 的 `layout()` / `presentNode()` 按此实现）

### guest 的键盘输入要先把指针真的点到目标元素上

- **环境**：Electron 45.2.1，`<webview>` guest 内的 `Input.dispatchKeyEvent` / `Input.insertText`
- **症状**：`evaluate` 找到输入框、`el.focus()` 也成功，`document.hasFocus()` 返回 true，
  但输入的文字一个都没进页面。`Input.dispatchMouseEvent` 的 click 却正常生效。
- **原因**：guest 的输入路由跟着**最后一次真实指针事件落到的元素**走。只发一个页面中心的
  `mouseMoved` 不够——它把输入路由指回 body，键盘事件仍然丢掉。
- **解决**：输入前先对目标元素做一次完整 click（move + press + release），再
  `Input.insertText`。这条差异用 `CdpExecutor.requiresPointerBeforeTyping` 表达，
  native 载体为 false，guest 为 true，由 `typeInto()` 统一处理。
- **附带结论**：`selectAll` 不能用普通 `keyDown` 发 "a"——guest 上它连 `keydown` 都不产生。
  必须 `rawKeyDown` + `modifiers: 2` + `commands: ["selectAll"]`。
- **日期**：2026-11-04
- **状态**：有效

### CDP 会话一释放，页面自己抛出的事件就没人收，而且不会补发

- **环境**：主进程通过 `webContents.debugger` 驱动 guest，空闲 1.5s 后 detach
- **症状**：登录表单捕获（`Runtime.bindingCalled`）在人工点登录时**完全不触发**；
  用 CDP 调 `evaluate` 触发同样的提交却能捕获到。页面里 `__ensembleCaptureInstalled`
  为 true、binding 也是 function，一切看起来都装好了。
- **原因**：`Runtime.addBinding` 的 binding 函数活在页面里，但 `bindingCalled` 事件只投递给
  **当前 attach 的**会话。空闲释放是正确的（反自动化探测），但事件不像命令那样排队等下一次
  attach——没有监听者就直接丢弃。
- **解决**：`GuestSessions` 增加 `pin`/`unpin`。凡是页面会**自己按用户节奏**抛事件的
  （目前只有登录捕获），装载捕获脚本时 pin 住会话，直到页面离开。命令/响应型流量继续保持
  空闲释放。

### 占位记录让「carrier 还不存在」成了一个真实状态

### 停靠时序不能靠「等舞台消失」，要在决定画面板的同一个任务里把页面停掉

- **环境**：guest 载体，页面上有活页面时打开控制台（设置页）
- **症状**：页面和面板互相覆盖、闪一下。DOM 探针在点击后的第一帧就已经看到节点被移到
  窗口外，逐帧像素采样也只捕到「已停好」的状态——**状态层完全正常，闪烁在合成层**。
- **原因**：停靠发生在 `BrowserPage` 卸载时的 `onBeforeUnmount` → `setStage(null)`。
  控制台是普通流内 HTML，页面节点是 `z-index: 1` 的 fixed 图层，所以面板首帧可能画在
  活页面**下面**，一帧之后节点才被移走。Vue 的 job 顺序按挂载顺序排，父组件先渲染，
  子组件的 flush 排在后面——正是那一帧。
- **解决**：两道，缺一不可。
  1. **结构**：`.console` 自己 `position: relative; z-index: 2`。任何上游时序错误都不可能
     再把页面画到面板前面。
  2. **时序**：store 加 `stageSuspended`，对 `view` 做 `{ flush: "sync" }` 侦听，切视图的
     同一个任务里就把所有节点停到窗口外。挂在 `view` 而不是 `switchView` 上，因为视图有
     六个直接赋值入口（原生菜单、状态栏、引导页……）。
- **踩到的第二层**：`placeFor()` 内部重读了 `embedded.stageRect`，`layout()` 里算好的
  `stage` 没传进去，所以「挂起」对停靠毫无作用——节点被移走了但 `onStage` 仍为 true，
  `opacity`/`pointerEvents` 没跟着降。**停在窗口外但仍可点**，比看得见更糟。
- **验证方式**：`scripts/e2e-console-overlap.mjs`。关键是断言在**点击的同一个任务里**
  读状态——等一帧再读，坏构建也会通过（实测过）。反向验证：撤掉修复后 3/5，失败的正是
  「同一任务内停好」和「控制台图层更高」两条。
- **日期**：2026-11-04
- **状态**：有效

### 最小化窗口的截图：CDP 必超时，`capturePage` 41ms

- **环境**：Electron 45.2.1，guest 页面，窗口 `minimize()` 之后
- **症状**：`screenshot_browser_tab` 一次调用挂了 **178 秒**才失败（渲染进程被拖垮）。
- **实测两条路径**（真实窗口，非 headless）：

  | 状态 | guest `Page.captureScreenshot` | guest `webContents.capturePage()` |
  | --- | --- | --- |
  | 窗口可见 | 有图 | 109ms，16673 字节 |
  | 窗口最小化 | **5s 超时** | **41ms，同样 16673 字节** |

- **原因**：截图前会调 `primeForCapture()`，它去截**宿主窗口**——而最小化时宿主本身不再
  产帧，那一步先挂住；就算跳过预热，guest 的合成器跟着宿主停摆，CDP 命令永不返回。
  另有一条被推翻的旧结论：「guest 不能用 `capturePage`」。那是 native 载体时期的判断
  （`capturePage` 打在 Window 上会 `UnknownVizError`）；打在 guest 自己的 `webContents`
  上完全正常，因为它画的是离屏表面，不需要窗口在屏幕上。
- **解决**：`browser.screenshot` 先判 `isOnScreen`，再决定要不要预热——离屏时**跳过预热**，
  直接走 `preferRenderer`。`GuestCdp.screenshot` 补上 renderer 兜底，并把状态判错的情况
  （最小化发生在检查之后）也接住。
- **顺带修掉的一个反向 bug**：`viewIsOnScreen` 只判「左上角在窗口内」。节点停在
  `x = -width` 时 `-1320 < 1320` 成立，被判成**在屏**，于是后台页面的截图全走必超时的路。
  改成真正的相交判定。
- **教训**：截图路径的选择必须由「宿主窗口是否产帧」决定，不能由「页面节点在哪」单独决定；
  两者的关系在最小化时是反的。
- **日期**：2026-11-04
- **状态**：有效

### 活动标签与工具栏不同色，整个窗口立刻像网页后台

### 分辨率与缩放争用同一个因子

- **现象**：把全局分辨率改回自适应后，工具栏缩放显示 100%，但页面实际还是缩小的样子。
- **原因**：固定分辨率模式下，`webContents` 的 zoomFactor **被适配比例占用**（`页面按目标
  CSS 尺寸排版 → 整体缩放到格子大小`）。清掉分辨率时若只更新状态、不把 zoomFactor 还回去，
  页面就继续保持那个比例；而界面读的是 `zoomOverride ?? defaultZoom`，它会诚实地报 100%。
  两边各说各话，且只有肉眼能发现。`setDefaultViewport`（全局）漏了复位，`setViewport`（单页）
  当时是对的——同一件事写了两遍，漏了其中一份。
- **解决**：**凡是让页面离开"固定分辨率"的代码路径，都必须显式把 zoomFactor 重新写回**
  （`delete viewportScale` + `applyZoom(zoomOverride ?? defaultZoom)`）。判断依据用
  `viewportOf`，不要自己拼条件。回归断言必须量**实际渲染尺寸**（在内置页面 target 上读
  `window.innerWidth`），不能只断言状态字段——状态字段正是那个说谎的地方。
- **日期**：2026-11-02
- **状态**：有效（已落地；`scripts/e2e-viewport-scope.mjs` 用 CDP 连到被嵌页面读 `innerWidth`，
  断言「有分辨率时 = 1280、清掉后 = 格子宽度」）

### 传 `undefined` 过 IPC = 没传

- **现象**：把全局分辨率设成固定尺寸后，再选「自适应」毫无反应，尺寸一直留着，看起来像
  「改不回去了」。
- **原因**：设置走 `saveSettings` → `toPlain`（`JSON.stringify`）→ 主进程。`JSON.stringify`
  会**丢掉值为 `undefined` 的键**，所以 `{ browserViewport: undefined }` 到主进程时是 `{}`；
  主进程那一侧判断的是 `"browserViewport" in parsed`，条件永远为假，改动静默丢弃。
  schema 恰好允许 `null`，于是「设成某尺寸」正常、「设回自适应」永远无效。
- **解决**：**"清除某设置" 要用 `null` 表达，不能用 `undefined`**；接收端也要用
  `"key" in patch` 判断而不是 `patch.key !== undefined`，两者语义不同（前者=用户明确要求清空，
  后者=用户没提这个键）。所有可清空的设置项都按这条检查。
- **日期**：2026-11-02
- **状态**：有效（已落地；`scripts/e2e-viewport-scope.mjs` 断言清除后 `viewport === null`
  且存储值为 `null`）

### 同一实例占两格时，兄弟格会跟着变

- **现象**：把一个实例的两页拖进两个格子做同账号对比，结果两格显示同一页。
- **原因**：格位只记 `slotTabs`（实例），实例只记一个「当前页」。拖入新页后新页成了当前页，
  另一格没有自己的页记录，跟着实例一起变——分屏等于没分。
- **解决**：格位多一层 `slotPages`（这一格固定显示的页，缺省=跟随实例）。
  **在三处维护它**：① 放入新页前，把其余同实例格位「此刻正在显示的页」先写进 pin；
  ② `resolveSlotTabs` 只在本意分屏时允许重复实例，否则布局一过就折叠回一格；
  ③ 关掉被 pin 的页时先清 pin，让格子回落到实例当前页。另一处易漏：格位标签条点选页
  也要走 `splitPageIntoSlot` 而不是 `activate`，否则激活的是实例级当前页。
- **日期**：2026-11-02（2026-11-06 补充第三种破法）
- **状态**：有效（已落地；`scripts/e2e-split-view.mjs` 断言两格 pin 不同页、
  布局重算后仍是两格、关闭被 pin 页后该格释放）

  **第三种破法（2026-11-06）**：把某一格**正在显示**的页拖到兄弟格，freeze 会把被拖页
  pin 进源格、drop 又 pin 进目标格——同一页写进两格。一页只有一个表面，`applyLayout`
  逐格 `setBounds` 时后者覆盖前者，输的格黑屏，两格标签条还都写着同一页。修复收进纯函数
  `settleSplitPages`（`shared/embedded.ts`）：被拖页独占目标格；兄弟格撞页时改 pin 实例内
  另一页，实例只有这一页就让出格位（拖单页实例=移动）。铁律：**一个 page id 永远只允许
  出现在一个格位的生效页里**。`e2e-split-view.mjs` 补了「拖正显示的页到兄弟格=两格对调」
  与「单页拖到空格=移动」两个场景。

### 分屏之后两格长得一模一样，运行栏缩进还和层级对不上

- **现象**：一个实例里两页，把一页拖到另一格后：两格的标签条都列出整窗的两个页签，看不出
  各自在显示哪一页；运行栏又是「一个实例一行、两页缩进在下面」，而屏幕上明明是两块平级的格，
  缩进描述的关系和肉眼看到的不一致，误导人。
- **原因**：模型加了 `slotPages`（格位固定看哪页），界面还停在「一个格位 = 一个实例」的

  有效性收进纯函数 `resolveSlotPages`，明确要求「页还在 + 同实例 + 该实例仍占 ≥2 格」，
  单测直接锁这三条。关闭被 pin 的页时若同实例还有别的格位，**这一格本身也释放**。

- **状态**：有效（已落地；`tests/embedded.test.ts` 锁 pin 规则，`scripts/e2e-split-view.mjs`

### 下载面板被页面盖住：新浮层忘了登记进 `overlayOpen`

- **现象**：点工具栏的下载按钮，按钮亮起、状态也变了，但面板看不见——它被内置页面完整盖住。

### 保存时提示 `An object could not be cloned`

### 应用退出后 MCP 端口仍被占用

- **环境**：主进程内 HTTP 服务（MCP 端点），Windows
- **症状**：界面显示已退出，但 `127.0.0.1:<port>` 仍然连得上，或进程迟迟不结束。
- **原因**：MCP 客户端会保持 keep-alive 长连接。`server.close()` 只是停止接受新连接，

  回收途中发起新的启动。

- **状态**：有效（已落地，`tests/contracts/tray-mcp-lifecycle.test.ts` 守护）

### 迁移把一个空数组当成「已是新格式」，站点清空、账号全部失联

### 自建 DevTools 面板内容全空，reload 一次就永久坏掉

- **环境**：Electron 44.9.0，`setDevToolsWebContents` + 自建 `WebContentsView` 停靠面板
- **症状**：打开 DevTools 后每个面板（Elements / Console / Network）只有骨架，内容区一片空；

- **排除过的错解**：① 抖动视图宽度唤醒合成器（`reviveDevToolsCompositing`）——无效，
  和合成无关；② 换回 Electron 托管（不调 `setDevToolsWebContents`）——同样躲不过 reload，
  而且丢掉停靠能力；③ 关掉 DevTools 后新建视图重挂——无效，binding 在被测 WebContents 上。
- **解决**：绝不让前端 reload。提示条只点「Don't show again」（不触发导航）；面板里的
  F5 / Ctrl+R 不再直接放行，而是**转发给被测页**（重新加载页面，Chrome 也是这个语义），
  手势不废、前端不自毁。代价是 DevTools 界面保持英文——中文面板不值得一个空面板。
- **中文为什么不是「顺手的事」**：预置 `language=zh-CN` 到前端 localStorage 后首次加载，
  界面仍是英文（Elements 树的 `aria-label` 还是 `Page DOM`）；前端取语言包走

### `@container` 写在基础规则之前，整块样式被静默丢弃

- **现象**：设备面板在窄格位下明明触发了容器查询，`flex-direction: column` 生效了，
  但「应用设备 / 只改尺寸」两个按钮却跑到可视区外，列表区还把面板底部顶穿。
  症状像「flex 布局没算对」，反复调 `flex-basis` / `min-height` 都不见效。
- **原因**：`@container (max-width: 520px)` 块写在 `.device-body { flex: 1 1 auto;
  overflow: auto }` **之前**。容器查询本身不增加特异性，与基础规则同级，胜负由**源码顺序**
  决定。于是块内除 `flex-direction`（基础规则没写这一条）外全部被后面的声明覆盖，
  `flex: none` / `overflow: visible` 从未生效——内层仍是 `flex: 1 1 auto` + `overflow: auto`
  的固定高度滚动盒，把内容裁在中间。
- **排查方法**：别盯着 flex 算。先 `getComputedStyle` 读**实际生效值**——本例读
  `.device-body` 的 `flexBasis` / `overflow` 一眼就能看出与查询块里写的不一致，
  再回去看顺序即可定位。
- **解决**：把整块 `@container` 移到样式表末尾（所有基础规则之后），并在块上方写明原因，
  避免后来者「顺手整理」又挪回去。
- **教训**：容器查询、媒体查询、`@supports` 这类条件块都要按层叠顺序安排位置。
  `@media` 写在文件末尾已是习惯，换成 `@container` 时这个习惯很容易丢，而失败是**静默**的。
- **日期**：2026-11-10
- **状态**：有效（已落地；`docs/screenshots/devtools-device.png` 为实机验收）

### 用「距开始的总时长」当速率分母，忙页面的图表是一条直线

- **现象**：性能监视器的曲线永远近乎水平，即使被测页面正在不停地插入节点、强制布局。
  CPU 那一行缓慢漂移，布局/秒与样式重算/秒几乎是贴底的直线。
- **原因**：`deriveSample` 收的 `elapsedMs` 被传成了 `now - startedAt`（距开始的总时长），
  并被用作 `delta / interval` 的分母。于是每个 200ms 的尖峰都被摊进「已经跑了多久」，
  运行越久分母越大，曲线越平——采样频率再高也没用，是高频率的样本被同一个错误分母压平了。
- **排查方法**：先看**单位与含义**，不要先怀疑采样率。本例只要问一句「这个分母是哪段时间」
  就能定位：速率需要「距上一次的间隔」，而代码给的是累计时长。
- **解决**：分母改用 `now - firstAt`，并在每次采样后把 `firstAt` 推进到 `now`；样本的 `t`
  仍然写绝对时间（横轴要用），两个数分开维护。顺带把采样提到 200ms、横轴改按真实时间排布。
- **教训**：累计计数做差分时，「间隔」必须与「增量」覆盖同一段时间。这两个量一旦错位，
  结果会**平滑得看起来很合理**——比抛异常难查得多。
- **日期**：2026-11-10
- **状态**：有效（`tests/device-perf.test.ts` 断言 200ms 内的 50% CPU 与 25 次/秒；
  `e2e:devtools-panels` 断言采样最大间隔 < 900ms）

### 「在台上」按实例判，空白占位页盖住了真实页面

- **现象**：启动账号后页面长时间一片空白，手动刷新一下才显示内容。URL、`innerWidth`、

  含义变成「这个实例的所有页面都在台上」。而每个新实例的第一个页面是 `about:blank` 占位，
  它同样满足条件，于是和真实页一起不透明；DOM 顺序让它赢了。
- **为什么表现为「刷新就好」**：刷新会重建节点顺序与不透明度，偶然把真实页翻到上面。
  这解释了为什么它看着像加载问题、实际是层级问题——排查时先怀疑网络就会走偏。
- **解决**：`isOnStage` 只在页面是 `activeTabId` 本身时为真；视图内按 `slotPages` 的钉选判，
  并且要求该视图就是 `activeViewId`。与主进程 `slotPages` 用同一套规则。
- **教训**：**「同一个实例」不等于「同一个可见面」**。实例是一个会话，页面是多个表面；
  任何决定「谁拥有这块像素」的判断都必须落到页面粒度。这类错误在不截图时完全看不出来，
  所有 DOM 断言都会通过。
- **日期**：2026-11-10
- **状态**：有效（`tests/contracts/guest-visibility.test.ts`；
  `e2e:devtools-panels` 断言同一时刻只有一节点不透明且不是 `about:blank`）

## 凭据与账号隔离

### 登录态检测永远显示已过期，重新登录也消不掉

- **环境**：站点使用私订请求头令牌（节奏阵列：`localStorage['token']` → 请求头 `token` → 服务端 `req.headers.token`）
- **原因**：登录态探测是页内 `fetch(..., { credentials: "include" })`，只带 cookie。令牌站点的会话凭证根本不在 cookie 里，探测永远命中未登录信封（HTTP 200 + `请先登录`），与真实登录态无关——重新登录多少次都不会变。诚实的判定输出配上错误的适用前提，比报错更难察觉。
- **解决**：站点配置 `authTokenKey`（localStorage 键名，`authTokenHeader` 默认 `token`），探测在检查时从页面读令牌随请求发送；`fillLogin` 提交成功后静置 2 秒自动复检。诊断入口：看到「已过期 + signed-out marker」但用户明确已登录，先查站点鉴权机制（curl 未登录探测点、翻客户端请求拦截器），再怀疑检测代码。
- **日期**：2026-11-01
- **状态**：有效

### 换端口没有隔离账号

### 自动填充填好了，但登录页一点反应也没有

- **环境**：内置表面 + SPA 登录页（按钮是 `type="button"`、提交逻辑写在脚本事件里）
- **症状**：账号密码都填进去了，页面停在原地，必须人再点一次「登录」。代码侧却一直回报
  `submitted: true`，日志上看不出任何异常。
- **原因**：提交动作只调了 `form.requestSubmit()`。`requestSubmit()` 在「表单没有 `submit`
  监听、按钮也不是 submit 类型」的页面上，发出的 `submit` 事件没有任何监听者，既不导航也
  不发请求，但它不会抛错——于是调用方把「事件发出去了」当成了「登录提交了」。
- **定位方式**：把实现临时回退成 `requestSubmit()` 跑 E2E，登录页把密码塞进了 URL 查询串
  （页面自己的读取逻辑跑了、登录处理器没跑），一眼就能看出是真点按钮和「只发事件」的差别；
  修复版同一断言下落到了落地页。**这类"看起来成功"的失败，只有让断言在被回退的实现上变红
  才能证明测试真的在测东西。**
- **解决**：`buildFillExpression` 改为先在 form（再退到 document）里找登录按钮并 `click()`，
  过滤掉 forgot / reset / show / register / cancel 之类干扰项，优先命中
  login / sign in / submit / 登录 等文字或表单内 `type=submit`；找不到按钮才退回
  `requestSubmit()`，最后 `form.submit()`。
- **附带改动**：自动提交从站点布尔上移为「全局默认 + 站点可选覆盖」，与默认浏览器同一套分层。

- **状态**：有效（已落地）

- **环境**：Windows + Edge/Chrome，CDP 模式
- **症状**：用户自己关掉浏览器窗口（或浏览器崩溃），Ensemble 的身份卡和运行面板仍显示运行中，

    界面靠既有的 snapshot 广播自动刷新，不需要额外轮询。

## 进程生命周期

### 应用退出后浏览器还在跑

- **环境**：Windows，`spawn` 启动 system browser
- **原因**：Windows 没有「父进程退出子进程自动结束」的机制；`Browser.close` 也可能因为页面有 beforeunload 而延迟。

- **状态**：有效（已落地）

- **环境**：多成员场景
- **原因**：逐个启动，第 N 个失败时前 N-1 个已经打开。
- **解决**：记录本次自己启动的实例；catch 中全部回收再抛出，保证场景启动原子。
- **日期**：2026-10-19
- **状态**：有效（已落地）

### 内置批量启动慢且中途切「无布局」直接断掉

- **环境**：Windows，Electron 44，内置表面批量启动
- **现象**：① 批量启动 N 个账号要等 N 个页面**串行**加载完，每个都数秒；② 批量中途把视图布局
  切成「无布局」，批量当场中断，已开的页留在原地、后面的不再开。
- **原因**：批量是渲染层的一个 for 循环逐个 `await openEmbeddedTab`，主进程每次 `createTab`
  都要 `await loadURL` 等完整加载，总时长 = 各页相加。中断则是竞态：循环开头记下的 `slotCount`
  是布局切换前的快照，切到无布局后循环仍按旧值调 `pinEmbeddedTab`，主进程 `pinTab` 对越界
  槽位直接抛「槽位不存在」，循环没有 try/catch，整批死掉。
- **解决**：整个批量下沉到主进程一个 IPC（`IPC.embeddedLaunchBatch`）：页内并发建页（并发度 3，
  总时长 ≈ 单页时长 × ⌈N/3⌉）、落格时**实时重读槽数**、越界槽位静默跳过（溢出页留在视图离台
  停放，与手动拖放的规则一致）、任一失败整批连同容器一起回收（原子性对齐外置路径）。注意
  「无布局」的槽位语义是 **1 个整舞台格**（`embeddedSlotRects` 对空槽预设回退满屏矩形），不是
  0 格——第一页上台、其余停放。渲染层不再编排多步 IPC。守护：`e2e-batch-launch.mjs` 的
  Free 布局场景。
- **教训**：多步 UI 操作不要让渲染层编排——「用户中途改设置」会击穿任何调用前算好的假设；
  把整批动作收进一个原子入口，竞态和原子性一起消失。
- **日期**：2026-10-30
- **状态**：有效（已落地）

### 窗口关掉后进程不退，portable exe 一直被占用

- **环境**：Windows，Electron 44，安装版与便携版均复现
- **症状**：关闭窗口后 `Ensemble.exe` 仍在任务管理器里，没有可见窗口；因为是 portable 启动的，`release\Ensemble-0.1.0-win-x64-portable.exe` 被锁住无法覆盖。用户会以为「已经关了」，但实际上一堆进程还在后台。
- **排查**：主进程加日志后看到 `close → before-quit → closed → window-all-closed`，但 `will-quit` 永远不触发；此时 `BrowserWindow.getAllWindows().length === 0`。
- **原因**：`window-all-closed` 一旦注册了监听器，Electron 就把「是否退出」的决定权交给应用。监听器里只调用「异步清理 + 稍后 app.quit」的 `shutdownAndQuit()`，而 `before-quit` 已先把 `quitting` 置真，函数直接 return，没有第二次 `app.quit()`；quit 流程于是停住。最小 Electron 应用用同样时序不复现，差异就在这个提前置真的守卫。
- **解决**：`window-all-closed` 的无条件路径直接 `app.quit()`；异步清理仍然只在窗口 `close` 事件里做一次（`shutdownAndQuit`），两者职责分开。用 `tests/contracts/quit-on-window-close.test.ts` 锁住该写法。
- **日期**：2026-10-19
- **状态**：有效（已落地）

### `setup` 里 `watch` 一个引用了后续 `const` 的 computed，整页静默消失

- **环境**：Vue 3 渲染层，`<script setup>`
- **现象**：应用启动后右侧内容区整体空白（左栏正常、guest 节点挂在 body 下但无定位），无崩溃弹窗；DevTools 连上去也抓不到 `exceptionThrown`——错误走的是 `console.error`（Vue 的 `callWithErrorHandling`），要用 `Runtime.consoleAPICalled` 才能抓到。
- **原因**：`watch(windowInstanceId, ...)` 写在了 `windowInstanceId` 的声明之后、`activeView` 的声明之前。watch 建立时会**立即求值一次** source，computed getter 读到 `activeView`，而它还是未初始化的 `const`——TDZ `ReferenceError` 在 setup 阶段抛出，整个组件挂载失败。computed 平时是惰性的，依赖顺序错了也不报错，加一个 watch 才引爆。
- **解决**：watch 一律放在它 source 链上所有声明**之后**（script 尾部最稳）；排查用「连接后 `Page.reload` 重放挂载 + 抓 `consoleAPICalled`」的一次性探针，两分钟定位。
- **日期**：2026-11-07
- **状态**：有效

### `pnpm install` 后 `node_modules/electron/dist` 不存在（`pnpm dev` 报 `Electron uninstall`）

### 双远程静默分叉：origin（Codeup）与 github 各有人推送，push 成功不等于推对了地方

- **环境**：2026-11-03 之前仓库配两个远程——`origin` = Codeup 私有同步仓，`github` =
  github.com/OneFanki/ensemble 开源主线（dependabot 只在 GitHub 跑）。多 AI 并发是常态。
  现在只维护 github 单远程，本条保留为历史结论。
- **原因**：A 会话基于 origin 的旧 dev 提交并推送，push 成功（那一刻 github 的 dev 恰好也没人动）；
  B 线推的却是 github——两边各自 fast-forward，**任何一步都不报错**，直到有人在 GitHub 界面上
  发现「我的提交呢」。`git push` 只对单一 remote 校验 fast-forward，另一个 remote 完全不在它的
  视野里。本地开发时另一个 remote 的分支可能已领先若干提交（本例 4 个功能 + 两次发版）。
- **解决**：提交推送前 `git remote -v` + `git fetch --all`，对照 `git log --oneline <基点>..<其他远程>/dev`
  确认没有平行走线。发现分叉后：`git rebase --onto <最新线>/<base> <旧基> dev` 把补丁挪到最新线上——
  **语义覆盖不会报冲突**（3-way 干净应用可能抹掉对方的字段），rebase 后必须 grep 对方提交的
  特征符号逐个确认存活，再跑全量 `pnpm verify`（两条线的测试都会跑）；对齐另一远程用
  `--force-with-lease`，仅限覆盖自己刚推的提交。
- **遗留的通用做法**：只剩一个远程之后，「推错地方」不会再有，但**推送前仍要 `git fetch` 再比
  ahead/behind**——另一台机器或用另一个 AI 可能已经推了新提交，本地先 rebase 比推上去再收拾便宜。
- **日期**：2026-11-01（2026-11-03 更新：移除 Codeup 远端，改为单远程 github）
- **状态**：已过时（多远程分叉的前提已不存在；单远程下仍适用「push 前先 fetch 比对」）

### 新标签页开了、状态切了，画面还是旧页面

### 清掉停放页的 bounds 之后，后台页截图报 `UnknownVizError`

- **环境**：内置浏览器，`screenshot_browser_tab` 拍一个已被切到后台的页面
- **症状**：`capturePage()` 抛 `UnknownVizError`（不是空图，也不是超时），而同一页在前台时截图正常
- **原因**：两处改动叠加。`parkUnstaged()` 把不在台上的页面 bounds 清零，渲染层据此把节点移到窗口外——
  这是对的。但 `GuestCdp.screenshot()` 的 `preferRenderer` 分支当初是**跳过** `presented()` 的，
  理由是「renderer 截图不需要合成器帧」。它确实不需要帧，但 `capturePage` **需要节点有一个真实的框**：
  一个被停到窗口外的 guest 报 `UnknownVizError`。而这条路径恰恰只在「页面不在台上」时才会走，
  所以它一直在裸奔，只是以前 bounds 没被清，节点还留着框
- **解决**：`preferRenderer` 分支也走 `presented(fromRenderer)`——present 的目的从「产生合成器帧」

### 新建视图后画面和已有页面互相覆盖着闪

- **现象**：新建视图 / 批量启动几个身份时，舞台上出现几帧「整窗页面叠在一起」的画面，
  同时舞台还会先空一下再填满。单页打开时完全看不出来。
- **环境**：Electron 45 / `<webview>` guest 载体，2×2 批量启动，本地开发环境
- **原因**：两个独立缺陷叠在同一个动作里。
  1. **广播次数**：`createView` 发一次状态，之后每 `createTab` 再发一次。渲染层每次都重新
     落位，中间那几次广播对应的是「视图在、页面还没到」，于是舞台空一下。
  2. **呈现等于显示**：让后台页面可读 / 可截图的那一步（`GuestCdp.presented`）会把节点挪回
     舞台——而它顺手把 `opacity` 也设成了 1。批量启动时每个新页面都要装登录监听
     （`evaluate`），三四个页面的 `presented` 同时进行，于是三四个整窗节点以 `z-index: 3`
     叠在 `(0, 78)` 同一个矩形上。`presentDepth` 是**每个 CDP 会话各自**的计数器，它只防
     同一页面的嵌套重入，完全不知道别的页面也在呈现。
- **解决**：
  - 广播：`BrowserManager` 加 `stateHold` / `stateHeld` 与 `withoutBroadcasts()`，把
    `createView` + 整个 `launchIdentityBatch` 包进同一个 hold 窗口，结束时统一 flush 一次。
    失败路径也必须先释放 hold 再报错，否则渲染层会一直显示已经被回滚的页面。
  - 呈现：`GuestPool` 里呈现与可见性解耦——被呈现的离台页面挪到舞台上拿 box，但保持
    `opacity: 0`。合成器对透明节点照样出帧，`Page.captureScreenshot` 与 `capturePage` 都
    正常，屏幕上却什么都不多。
- **怎么证明的**：写了个探针，每个 `requestAnimationFrame` 采样所有 `.guest-pool webview`
  的可见性与矩形，两两做相交检测（2×2 本来就有 4 个可见节点，所以判据必须是「相交」而不是
  「可见数 > 1」）。修之前每次启动有 3–4 帧重叠，修之后 356 帧 / 0 帧重叠，可见数序列
  从 `1 → 4` 一次跳变。这条判据后来固化进 `e2e-batch-launch.mjs`。
- **教训**：一个是「状态广播的粒度」——凡是「先建容器、再往容器里填东西」的流程，逐条广播
  就等于逐条重排；另一个更隐蔽：**「让页面可被读取」和「让用户看见页面」是两件事**，
  实现时顺手合成一个动作，就会在并发时变成整窗闪烁，而这种 bug 只在批量路径上出现，
  点击单个页面永远复现不了。加回归测试时也别写「可见节点数量」这种判据——它会把正常的
  多格布局判成 bug。
- **日期**：2026-11-06
- **状态**：有效（已落地；e2e-batch-launch 12/12）

### 导航等待只认「你要的地址」：每个登录页都白等 10 秒

- **现象**：打开站点的根地址，页面已经渲染完了，但整个调用要 10 秒才返回；直接开子路径就很快。
- **环境**：Electron 45，`EmbeddedBrowser.whenReady`（`navigate` 之后的一次「到了吗」轮询）

- **关键事实**：`loadURL` 的 promise 早已 resolve，页面也早已 `complete`；慢的只是那次等待。「页面加载慢」和「等页面的代码慢」在用户侧无法区分。

### 「保存账号」点了报错：空字符串通过了界面，却被 schema 拒绝

### 首个采样点被当成 0：繁忙页面报出一半的 CPU

- **现象**：用探针比较不同采样间隔的 CPU，得到一条漂亮的单调曲线——1s 档 42%、500ms 档 44%、200ms 档 56%、100ms 档 54%。看上去像「采样越细越贵」，差点就此写进文档当作取舍依据。
- **环境**：性能采样器 `deriveSample` 的第一个样本
- **原因**：第一个读数没有上一个累计计数，所有速率字段（CPU、布局/秒、样式重算/秒）都只能是「未知」。代码把它写成了 `0`，于是这个假 0 被当成真实读数参与统计。1s 档 5 个样本里 1 个假 0，影响 20%；2s 档 2 个样本里 1 个假 0，直接砍半——**样本越少，假 0 越接近「一半」**，而样本少正是间隔粗或窗口短的时候。于是「间隔越细 → 假 0 被稀释得越彻底 → 读数越高」，被误读成采样成本。
- **解决**：`PerfSample.warmup?: true` 标记这类无前驱的读数；`perfSummarize`、`perfSparkPoints`、`perfPeak` 对速率类指标跳过它，计数类（DOM 节点等）保留——节点数从第一次读就有效。`PerfMetricSummary.samples` 一并暴露，让调用方能区分「测了是 0」和「还没测出来」。
- **教训 1**：**「没有数据」不能用 0 表示**。0 是一个具体的观测值，混进平均值就会污染结论，而且污染的方向与样本量成反比——恰恰在你最需要准确的那种配置（短窗口、粗间隔）里最严重。
- **教训 2**：**用被测系统自己的读数去评估被测系统的开销，会得到自我强化的假象**。采样器读到的 CPU 里包含采样器自己。真要评估成本，得找独立指标——这次是让页面自己数完成了多少批固定工作量：无采样基线 33 批/3s，各间隔档 31–33 批，100ms 档低 3%，200/500ms 档在噪声内。**结论与观察者视角完全相反。**
- **日期**：2026-11-11
- **状态**：有效（`tests/device-perf.test.ts` 新增三条：warmup 不进均值、计数保留首点、warmup 不画进曲线）

### 工具栏铃铛一点就跳走，而页面没有返回入口；详情也不该就地展开

- **现象**：两轮同一个问题。①点地址栏旁的铃铛（未读消息入口），直接切到消息中心页面；到了那边没有任何控件能回到刚才那一页。②按「改用浮层」修好之后，铃铛浮层里点单条消息是**在浮层内展开**动作按钮，于是下面几条被往下推——用户第二次纠正：「还是以浮层的方式显示额外信息比较合适，现在这样直接影响布局的方式感觉不太合理」。
- **环境**：`BrowserPage.vue` 的 `[data-messages-bell]`；铃铛浮层内 `.bell-more` 的行内展开；`MessagesPage.vue` 的行
- **原因**：①铃铛承担了「打开消息中心」这个导航动作。消息中心是外壳里的一个页面，它占据整个面板、浏览器页被卸载；一个只为瞥一眼未读消息的点击，把「看一眼」变成了「离开」，而离开之后没有回来的路径。②把「就地展开」当成了「不动布局」——展开了确实没跳页，但它撑高了那一行，把后续行整体下移。**列表在用户正在挑选的时候重新排列，和跳到别的页面一样干扰**，而且更阴险：视线还停在原处，但那一行已经换成了别的内容。
- **解决**：两层都用浮层。铃铛 → 浮层（`data-bell-panel`，锚在铃铛右缘，与下载面板同一范式）；浮层内点某条 → 再浮出 `MessageDetailLayer`（`data-message-detail`），**在浮层左侧**打开（`placement: "left"`），不覆盖列表也不撑高它；消息页点行同样开这一层，在后面（`below`）。层内是该条的完整正文、时间、动作与失效原因；点外部与 Esc 关闭，Esc 只关最内层（`stopPropagation`）。行表现（标题翻译、图标、时间、失效原因、动作标签与执行）抽到 `composables/messageRows.ts`，两处共用。
- **教训**：**「不跳页」不等于「不动布局」**。判断一个详情该怎么呈现，标准是「它出现时周围的东西会不会移位」，而不是「用户会不会离开当前页面」。列表、网格这类「用户正在其中挑选」的容器里，任何详情都必须浮起来，不能撑开容器。另外 `onClickOutside` 不要在 `v-if` + `teleport` 的组件里绑 `ref`——setup 时 ref 还是 null，绑上的处理器永远看不到那个元素；用 document 上的 `pointerdown` 捕获阶段监听，并在 `onBeforeUnmount` 移除。

- **状态**：有效（`e2e-messages` 16 条，其中几何断言：打开详情前后主浮层包围盒与每一行的 top 完全相等、详情层在主浮层外）

### 整行 hover 变暗，把曲线也一起压暗了

- **现象**：性能监视器的鼠标划过任意一行，整行（含 40px 高的曲线）一起变暗。用户描述为「曲线也不需要 hover，现在 hover 一整行会变暗，反而有点奇怪」。
- **环境**：`PerformancePanel.vue` 的 `.metric-row:hover`
- **原因**：行是两行高的复合控件（名称行 + 曲线），而 hover 样式给整个盒子加了背景。曲线的可读性依赖与背景的对比度，背景一变，曲线的观感也跟着变——读者会误以为数据在变，尤其在这个面板的用途就是「看数据怎么变」的时候。
- **解决**：去掉整行背景，hover 只把名称行的文字提亮（`.metric-row:hover .metric-head`）。行仍是开关（`<button>`），可点区域不变。
- **教训**：**当一个控件内部包含数据可视化时，它的交互态不能改变可视化的底色**。反馈应该落在同一个控件里「不是数据」的那部分上（标签、勾选点）。

### 消息页从不重读历史，失效的行一直显示可用动作

- **现象**：把一条消息源（未保存的登录捕获）在别处销毁后回到消息页，那一行仍然带着「保存账号」按钮；点下去才失败。同理，在别的页面期间新产生的消息也看不到，直到重启应用。
- **环境**：`MessagesPage.vue` 只在 store 初始化时读过一次 `listMessages()`；`BrowserPage` 的铃铛浮层挂在一个永不卸载的页面上
- **原因**：`stale` 不是存盘的字段，而是**主进程在读取历史时当场判定**的（capture 的 token 只活在进程内存里，tab / identity 可能已删除）。页面拿到的是一份快照，而这份快照的时效取决于「上次谁读了它」——一个从不重读的页面，等于把过期判定永久固化。这类缺陷不会报错，只会让按钮点了没反应。
- **解决**：消息页 `onMounted` 调 `store.refreshMessages()`（每次进入都是重新问一次）；铃铛浮层在每次打开时同样刷新。两处都不是定时轮询——进入/打开就是用户表达「现在给我看」的时刻。
- **教训**：**凡是「是否仍然有效」由进程内状态决定的数据，界面必须在每次呈现时重新求值**，不能在启动时读一次就当作事实。判断依据：这个字段会不会因为别处的操作而在后台变化？会，就不能缓存到会话结束。反过来，如果是纯存盘数据（标题、时间），缓存完全没问题。
- **日期**：2026-11-11
- **状态**：有效（`e2e-messages` 最后一条：销毁捕获 → 重进消息页 → 该行标 stale、详情只说明原因不给动作）

### 新建档案里的浏览器永远打不开，报「页面没有在预期时间内就绪」

- **现象**：在任意自建档案里开一个浏览器，十秒后 IPC 抛 `页面没有在预期时间内就绪`。内置「默认档案」和「干净会话」都正常，只有新档案不行；控制台里没有别的线索。
