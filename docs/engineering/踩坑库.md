# 踩坑库（Known Pitfalls）

> 遇到报错、现象诡异、行为不符预期时，先查这里再排查。坑是经验型知识：不进 README、
> 不进架构文档，只在这里按条目累积。
>
> 维护规则：解决后当场追加条目（含日期）；失效条目标记 `状态: 已过时` 并注明原因，
> 不删除。代价高的坑（数据损坏、账号串号、凭据泄漏、进程失控）解决后，必须同步升级为
> `AGENTS.md` 硬约束。

## 条目格式

```markdown
### <现象一句话>

- **环境**：<版本/平台/场景>
- **原因**：<根因>
- **解决**：<可复现的操作步骤>
- **日期**：YYYY-MM-DD
- **状态**：有效 / 已过时（原因）
```

## 浏览器启动与 CDP

### 场景启动失败：`启动 Microsoft Edge 失败：fetch failed`

- **环境**：Windows 11，Edge 155，Electron 44，CDP 启动方式
- **原因**：profile 目录里残留上一次运行写下的 `DevToolsActivePort`。新实例启动瞬间读到了旧端口，旧端口已经没人监听，`/json/version` 直接 fetch 失败。
- **解决**：启动前主动删除 `<profileDir>/DevToolsActivePort`；读取后不要只信文件内容，必须同时探活 `http://127.0.0.1:<port>/json/version` 才算就绪。
- **日期**：2026-10-19
- **状态**：有效（已修复并落地）

### 抓到的页面是 `about:blank`，注入脚本无效

- **环境**：Chromium 系浏览器，`--remote-debugging-port=0`
- **原因**：浏览器启动后先出现 `about:blank` 目标，随后才创建真正加载 URL 的页面。直接取 `/json/list` 第一项会拿到空白页。
- **解决**：`waitForPageTarget` 优先选择 `url !== "about:blank"` 的目标，超时后再退化为第一项。
- **日期**：2026-10-19
- **状态**：有效（已修复并落地）

### 原生 `confirm` / `alert` 被自动取消

- **环境**：任何用 Playwright 驱动人工操作场景
- **原因**：Playwright 文档明确：没有注册 `dialog` 监听时，所有对话框自动 dismiss。
- **解决**：人手操作的窗口不要交给 Playwright 托管。用系统浏览器 + CDP，只启用 Page/Runtime 的必要域，不接管 dialog。下载同理：Playwright 默认落到临时目录且 context 关闭即删除。
- **日期**：2026-10-19
- **状态**：有效（架构级约束，禁止回退）

### 浏览器没开远程调试，但也没有报错

- **环境**：企业统一管理的 Chrome / Edge
- **原因**：Edge 策略 `RemoteDebuggingAllowed=0` 会禁用 `--remote-debugging-port`，或安全软件拦截本地端口。
- **解决**：拉起后等 `DevToolsActivePort` 超时，给用户明确提示「可能被企业策略阻止」，并允许改为外部模式。不要静默卡住。
- **日期**：2026-10-19
- **状态**：有效

### 浏览器版本自动升级后 profile 行为异常

- **环境**：系统 Chrome / Edge
- **原因**：profile 格式随大版本迁移，通常单向，不支持可靠降级。
- **解决**：升级前备份 profile 元数据；出问题时新建 profile 重新登录，不要试图把 profile 降级。需要可复现版本时，单独用固定版本 Chromium，不替换系统浏览器。
- **日期**：2026-10-19
- **状态**：有效

### 便携版冷启动比安装版慢一秒多

- **环境**：electron-builder portable target，Windows
- **原因**：portable 产物是一个自解压程序，每次启动都先把 Electron 运行时解压到
  `%TEMP%\<随机目录>` 再拉起主进程，解压本身就要一秒左右，且每次都是冷目录。
- **解决**：日常使用装 `setup.exe` 或直接跑 `win-unpacked\Ensemble.exe`；便携版只用于临时
  试用。判断当前在跑哪种形态，看进程命令行路径是否在 `%TEMP%` 下。
- **日期**：2026-10-19
- **状态**：有效

### 首次启动慢：窗口在等引擎扫描和进程清理

- **环境**：启动时同步执行 `scanEngines()` 与 PowerShell 进程枚举
- **原因**：`Get-CimInstance Win32_Process` 单次约 1.1 秒；引擎探测又要串行跑注册表查询
  和版本探测。这些都在 `createWindow()` 之前，用户看到的是几百毫秒到两秒的空白。
- **解决**：`initialize()` 只读本地 JSON 与引擎缓存，立刻建窗口；进程清理与引擎扫描放到
  `startBackgroundMaintenance()` 后台执行，完成后广播。缓存文件 `engines.json` 记录上次
  扫描结果，启动时先用缓存，再静默刷新。注册表查询和版本探测改为并发。
- **日期**：2026-10-19
- **状态**：有效（已落地）：安装形态二次启动约 660ms，首次约 1.3s

### 引擎版本号显示为 `-`

- **环境**：Windows，Edge / Chrome
- **原因**：Edge 与 Chrome 的可执行文件固定在 `Application\msedge.exe`，版本号在**同级
  的版本目录**里（如 `Application\155.0.4283.62\`）。`versionFromExecutablePath` 读的是
  父目录名，取不到。另外这两个浏览器执行 `--version` 在 Windows 上不输出任何内容。
- **解决**：新增 `versionFromSiblingFolders()` 读同级的最大版本目录名；Firefox 这类没有
  版本目录的，用一次批量 PowerShell 读 `VersionInfo.ProductVersion`。
- **日期**：2026-10-19
- **状态**：有效（已落地）

## 界面与可读性

### 弹窗打开时 toast 被遮住

- **环境**：Reka UI Dialog + 自定义 toast
- **原因**：toast 容器 `z-index: 60`，而 Dialog 的遮罩是 70、内容层是 71。错误提示在
  编辑弹窗里触发时正好被压在最下面，用户只看到一片模糊背景。
- **解决**：toast 是全局反馈，层级必须高于任何模态层。统一约定：遮罩 70、弹窗 71、
  toast 100、系统级提示更高。新增浮层时先对齐这张表，不要各自取号。
- **日期**：2026-10-19
- **状态**：有效（已落地）

### 保存时提示 `An object could not be cloned`

- **环境**：Electron IPC，Vue 3，`contextBridge`
- **原因**：弹窗里的表单是 `reactive()` 对象，它的嵌套数组与记录仍是 Proxy。IPC 用结构化
  克隆序列化参数，遇到 Proxy 直接抛这个错。只在「先打开弹窗再保存」的真实路径出现，
  直接用普通对象调 IPC 反而正常，很容易漏测。
- **解决**：发 IPC 前把 draft 转成纯数据（`JSON.parse(JSON.stringify(v))`）。draft 本来就是
  JSON 形状，round trip 没有信息损失。约束：渲染层传给主进程的参数必须是可结构化克隆的值。
- **日期**：2026-10-19
- **状态**：有效（已落地）

### Windows 上中文看起来像衬线体

- **环境**：Windows 11，Electron
- **原因**：两处叠加。① 等宽字体栈以 `monospace` 泛型结尾，Windows 把其中的中文回退到
  **SimSun（宋体，衬线）**；`.mono` 被用在含中文的标签上（导航标题、页面副标题、表头）。
  ② 中文回退字体排在 Latin 字体之后且没有显式列出，某些环境会走 font linking 落到宋体。
- **解决**：等宽栈里显式列 CJK 无衬线字体（微软雅黑 / 苹方 / Noto Sans SC），并把泛型
  `monospace` 从栈里去掉；无衬线栈把 CJK 字体排在泛型之前。另外按「等宽只给技术数据」的
  原则，把含中文的标签从 `.mono` 移出。
- **验证方式**：用 canvas 逐字体绘制同一串中文并做像素哈希指纹，对比元素实际渲染结果。
  这是唯一可靠的判断方式——`getComputedStyle` 只返回栈，不告诉真实命中的字体。
- **日期**：2026-10-19
- **状态**：有效（已落地）

### 深色界面文字看不清

- **环境**：暗色主题，最小字号 8.5–9px
- **原因**：两层问题叠加。一是 `--faint` 对比度只有 2.71:1、`--dim` 3.46:1，远低于 4.5:1；
  二是大量辅助文字用了 8.5–9.5px，小字加低对比度几乎不可读。
- **解决**：重排 `tokens.css` 的灰阶层级，最低档提到 4.39:1 以上、主体档 8:1 以上；正文
  字号下限提高到 10px、主体 10.5–11.5px。浅色主题同步调整。
- **日期**：2026-10-19
- **状态**：有效（已落地）

### 新建实例仍是登录状态，并弹出同步提示与扩展欢迎页

- **环境**：Windows 11，Edge，全新 `--user-data-dir`
- **现象**：新 profile 一启动就弹「我们现在正在你的所有设备上同步你的浏览数据」，
  过一会又打开 Bitwarden 的扩展欢迎页；账号已登录、扩展已装好。
- **原因**：不是 profile 复用。Edge / Chrome 会**自动用 Windows 账户登录浏览器**，并把
  该账号的同步数据（书签、扩展、密码）灌进任何新 profile。实测新 profile 的 `Preferences`
  里立刻出现 `account_info`、`signin.allowed=true`、`sync.has_been_enabled=true`，
  且会打开 `edge://sync-confirmation-dialog/` 这个页面。
- **对照实验结果**（同一台机器，四个全新 profile）：

  | 参数 | 同步弹窗 | 同步扩展 | 说明 |
  | --- | --- | --- | --- |
  | 无额外参数 | 出现 | 同步 | 默认行为 |
  | `--disable-sync` | **消失** | **不同步** | 有效 |
  | `--disable-features=msImplicitSignIn,...` | 仍出现 | 仍同步 | 无效 |
  | 预写 `Preferences` 关闭 signin | 仍出现 | 仍同步 | 会被覆盖 |
  | `--disable-sync --disable-extensions` | 消失 | 无扩展 | 过度，会失去扩展能力 |

- **解决**：启动参数固定加 `--disable-sync`。测试 profile 本来就不需要同步；不加它，
  操作者自己的账号数据会污染每一个实例。**不要**用 `--disable-extensions`，那会连
  被测站点依赖的扩展一起禁掉。
- **补充**：已被污染的旧 profile 需要删除重建（界面提供「重建 Profile」）。仅改参数
  不会清理已经写进 profile 的账号与扩展。
- **日期**：2026-10-19
- **状态**：有效（已落地，并有契约测试守护）

## 凭据与账号隔离

### 换端口没有隔离账号

- **环境**：本地开发，`localhost:3000` 与 `localhost:3001`
- **原因**：Cookie 不区分端口；同主机的不同端口共享 cookie 域。
- **解决**：多账号必须用独立 profile；判断环境是否隔离只看 origin 的主机，不看端口。
- **日期**：2026-10-19
- **状态**：有效

### 同一个 profile 切换引擎后登录态丢失或异常

- **环境**：Chromium 与 Firefox
- **原因**：两种浏览器的 profile 目录格式不兼容，不能互换。
- **解决**：引擎绑定在身份上；换引擎是「复制身份生成新 profile」，不是改一个字段。
- **日期**：2026-10-19
- **状态**：有效

### 自动填充把密码填到了别的站点

- **环境**：登录页发生跨域重定向
- **原因**：只按选择器找密码框，没有校验当前页面归属。
- **解决**：填充前强制校验 `location.origin` 属于目标环境；跨域直接拒绝并提示。
- **日期**：2026-10-19
- **状态**：有效（已落地）

### 启动后没有自动填充，只有点「重新登录」才填

- **环境**：任意 CDP 引擎
- **症状**：点身份卡上的启动只打开登录页，账号密码框是空的；用户以为自动填充坏了。
- **原因**：填充逻辑只挂在「重新登录」这个显式动作上，`launchIdentity` / `launchScene`
  从没调用它；界面上也没有任何地方说明填充是手动触发的。
- **解决**：新增 `autoFillOnLaunch` 设置（默认开启）。窗口注册进 CDP 后起一个后台轮询，
  等密码框出现再填充，结果经 `onAutoFill` 回调以 toast 反馈；启动本身不等填充。
  「重新登录」在开启自动填充时不再二次填充，否则会重复提交。
- **日期**：2026-10-19
- **状态**：有效（已落地）

### 手动关掉浏览器窗口后，界面仍显示「运行中」

- **环境**：Windows + Edge/Chrome，CDP 模式
- **症状**：用户自己关掉浏览器窗口（或浏览器崩溃），Ensemble 的身份卡和运行面板仍显示运行中，
  点「停止」还在试图操作一个已经不存在的东西。
- **原因**：实例只存在于内存表里，启动后再没有任何地方观察浏览器的存活状态；只有应用自己调用
  `stopInstance` 才会移除条目。
- **排查陷阱**：第一版用 `child.on("exit")` 判断，结果每个实例启动后立刻被判退出。原因是 Edge/Chrome
  在 Windows 上会经兼容层重新拉起自己，我们 spawn 的启动器进程在窗口出现前就以 0 退出了，
  `child.pid` 根本不是浏览器进程。
- **解决**：
  - 存活信号改用 CDP socket：浏览器级 socket 关闭即视为退出，页面级 socket 作为兜底；
    进程退出信号只用于 Firefox（它不会自我移交）。
  - 真实进程号从 `SystemInfo.getProcessInfo` 里取 `type === "browser"` 的那条，替代 `child.pid`，
    这样兜底 `taskkill` 才杀得中。
  - 服务层监听退出事件后移除实例、清理 CDP 登记，干净会话同时删除 profile。
    界面靠既有的 snapshot 广播自动刷新，不需要额外轮询。
- **日期**：2026-10-19
- **状态**：有效（已落地，`tests/e2e-instance-exit.test.ts` 覆盖）

### 三段式登录表单（租户名 + 用户名 + 密码）只填对两个

- **环境**：SaaS 登录页，密码框前有两个文本输入框
- **症状**：租户名输入框被当成用户名，真正的用户名框被跳过；或者租户名完全没填。
- **原因**：旧逻辑只认「密码框之前第一个像用户名的输入框」，没有概念去描述额外字段。
- **解决**：环境/身份两级 `extraFields`（标签 + 值），填充时先按标签匹配并标记已用元素，
  再从剩余输入框里选用户名；未匹配到的配置字段与页面上未配置的输入框都回传界面提示。
  端到端用无头 Edge 验证：三字段页面提交结果为
  `{tenant: "acme", account: "admin", pwd: "..."}`。
- **日期**：2026-10-19
- **状态**：有效（已落地）

## 进程生命周期

### 应用退出后浏览器还在跑

- **环境**：Windows，`spawn` 启动 system browser
- **原因**：Windows 没有「父进程退出子进程自动结束」的机制；`Browser.close` 也可能因为页面有 beforeunload 而延迟。
- **解决**：记录 PID 与 profile 路径；退出时先 CDP `Browser.close`，超时后 `taskkill /PID <pid> /T /F`；启动时按命令行里的 `--user-data-dir` 匹配自有 `profiles/` 根目录再清理，绝不按进程名全杀。
- **日期**：2026-10-19
- **状态**：有效（已落地）

### 场景启动到一半失败，留下几个窗口

- **环境**：多成员场景
- **原因**：逐个启动，第 N 个失败时前 N-1 个已经打开。
- **解决**：记录本次自己启动的实例；catch 中全部回收再抛出，保证场景启动原子。
- **日期**：2026-10-19
- **状态**：有效（已落地）

### 窗口关掉后进程不退，portable exe 一直被占用

- **环境**：Windows，Electron 44，安装版与便携版均复现
- **症状**：关闭窗口后 `Ensemble.exe` 仍在任务管理器里，没有可见窗口；因为是 portable 启动的，`release\Ensemble-0.1.0-win-x64-portable.exe` 被锁住无法覆盖。用户会以为「已经关了」，但实际上一堆进程还在后台。
- **排查**：主进程加日志后看到 `close → before-quit → closed → window-all-closed`，但 `will-quit` 永远不触发；此时 `BrowserWindow.getAllWindows().length === 0`。
- **原因**：`window-all-closed` 一旦注册了监听器，Electron 就把「是否退出」的决定权交给应用。监听器里只调用「异步清理 + 稍后 app.quit」的 `shutdownAndQuit()`，而 `before-quit` 已先把 `quitting` 置真，函数直接 return，没有第二次 `app.quit()`；quit 流程于是停住。最小 Electron 应用用同样时序不复现，差异就在这个提前置真的守卫。
- **解决**：`window-all-closed` 的无条件路径直接 `app.quit()`；异步清理仍然只在窗口 `close` 事件里做一次（`shutdownAndQuit`），两者职责分开。用 `tests/contracts/quit-on-window-close.test.ts` 锁住该写法。
- **日期**：2026-10-19
- **状态**：有效（已落地）

### 干净会话宣称「关闭即清除」，profile 目录却越攒越大

- **环境**：Windows，干净会话
- **症状**：界面上写着「不登录、关闭即清除的临时窗口」，实际每个 `clean-*` 目录都留在 `%APPDATA%\ensemble\profiles\<环境>\` 下，单个约 200 MB，里面还带着 `Sync Data`、`Login Data` 和扩展目录。
- **原因**：`stopInstance` / `stopAll` 只停浏览器、移出内存表，从来没删过 profile 目录；`clean` 标记只用于展示，没有任何清理逻辑。异常退出留下的目录也没有启动清扫。
- **解决**：停止实例时若 `clean === true` 且目录名以 `clean-` 开头，停浏览器后删除该目录（双重校验，防止脏标记误删身份 profile）；启动后台维护时扫描所有 profile 根（含 Flatpak/Snap 的 `profileBase`）清掉遗留 `clean-*`。删除带重试，浏览器释放文件有延迟。干净会话启动前先等启动清扫结束，避免刚建好的目录被扫掉。用 `tests/clean-session-lifecycle.test.ts` 与 `tests/clean-profiles.test.ts` 锁住。
- **日期**：2026-10-19
- **状态**：有效（已落地）

## 构建与工具链

### `pnpm install` 后 `node_modules/electron/dist` 不存在

- **环境**：pnpm 12，Windows
- **原因**：Electron 的 postinstall 下载脚本被 pnpm 的构建审批机制拦截；若曾用旧配置安装，`pnpm install` 会判定「已是最新」而跳过脚本。
- **解决**：在 `pnpm-workspace.yaml` 的 `onlyBuiltDependencies` 放行 electron 与 esbuild；已装过时直接执行 `node node_modules/electron/install.js`。下载完成但解压失败时，压缩包在 `%LOCALAPPDATA%\electron\Cache`，可手动解压到 `dist` 并写 `path.txt`。
- **日期**：2026-10-19
- **状态**：有效

### `pnpm` 字段写在 `package.json` 里被忽略

- **环境**：pnpm 12
- **原因**：pnpm 12 不再读取 `package.json` 的 `pnpm` 字段，配置迁移到 `pnpm-workspace.yaml`。
- **解决**：`onlyBuiltDependencies` 等设置写在 `pnpm-workspace.yaml`。
- **日期**：2026-10-19
- **状态**：有效

### 相对路径多写一层导致整片 `Cannot find module`

- **环境**：TypeScript，文件位于 `src/core/` 根目录
- **原因**：`src/core/service.ts` 里应该写 `./engines`，误写成 `../engines`。所有 import 一起报错，看起来像配置问题。
- **解决**：先看报错文件自身的目录层级，再判断相对路径；tsconfig 的 paths 别名只覆盖了 `@core/*`，没有覆盖相对导入。
- **日期**：2026-10-19
- **状态**：有效
