# 路线图

记录方向判断，不代表已排期。每条做完后从「计划」移出并落到对应文档。

## 定位

Ensemble 是**多身份并行工作台**，不是抗检测工具。核心命题是「同一套系统里，多个身份同时在场，
并行操作、并排对比，验证每个身份看到的内容和能做的操作是否符合预期」。

「权限验证」只是最容易理解的例子，不是能力边界。典型场景还包括：

- 角色与权限：管理员看到删除按钮，普通成员看不到
- 多租户与数据隔离：租户 A 不该看到租户 B 的数据
- 功能开关与灰度：同一功能对不同账号是否按预期放开
- 套餐与等级差异：免费版和付费版的功能边界
- 跨账号协作：A 提交、B 审批，两边状态是否同步正确

所有功能都应服务于「同一套系统里，不同身份看到的和能做的是否正确」，而不是「如何让平台认不出是同一个人」。

因此不做指纹伪造（canvas / WebGL / 字体列表等）：那需要自行维护改过的浏览器内核，与「真实浏览器行为」的前提冲突，也与本项目的用户协议定位相悖。

## 两种浏览器表面

浏览器分内置与外部两种表面（决策见
[ADR 0006](./architecture/adr/0006-embedded-browser-first.md)）：

| | 内置（`WebContentsView`） | 外部（系统浏览器） |
| --- | --- | --- |
| 可控性：截图、接管、录制、并排、布局 | 完整 | 受限 |
| 保真度：真实版本、扩展、DRM、企业策略 | 较弱 | 最强 |

- **内置是默认与主推**：AI 驱动、静默运行、日常操作、并排对比都在这里，全程不弹系统窗口，
  人随时可以看和接管。
- **外部是保真校验**：需要确认「在用户真实环境里也一样」时切换。外部只承诺保真，
  不承诺与内置相同的功能集。
- 两者共用同一套站点、账号、凭据、视图与布局模型；切换必须由用户显式触发，因为它意味着重新登录。

## 已完成

### 浏览器表面：视图与标签页（0.5 地基）

`WebContentsView` 承载页面，画在主窗口的「浏览器」页里——不再有独立的内置浏览器窗口。
带搜索的导航顺序是 浏览器 / 站点 / 账号 / 视图 / 设置，浏览器是默认页。

- **视图是一块共享屏幕区域**：容器记住自己的布局、格位与选中标签，同一时刻只有一个
  在台上，其余视图的页面继续在窗口外运行（不是隐藏，见设计文档）。
- 内置表面布局五档（free / 2x1 / 1x2 / 2x2 / 3x1；`1x1` 与「无布局」是同一件事，已合并）
  + 自定义预设；容器的布局改动写回视图定义，下次启动保持一致。格位之间可以拖分隔缝改比例。
- 右侧运行栏跨所有页面常驻，把内置视图、内置扁平标签与外置实例放在同一处；视图是块、
  标签是行，可折叠、可整栏收起成带角标的窄边。运行栏的行可以直接拖到舞台的格位上替换
  那一格；格位头只显示编号、色点、实例页面标签与「选中」标记。
- 视图只手动创建：运行栏标题栏的「创建视图」按钮给一块空视图（默认 2×1、默认名可双击或
  右键改），空视图不会自动回收；拖标签只在列表内排序、或拖进已有视图，不会顺手建组。
- 启动目标收进标题栏的一个下拉（内置 / 外置，默认内置），账号页、批量启动、重新登录与
  视图页都跟随它；运行栏「添加标签页」固定内置，悬浮条固定只列外置窗口。
- **站点降级为登录配方，标签升为全局**（见 ADR 0008）：标题栏的站点切换器删除；账号页按
  站点分组列出全部账号，视图页列出全部视图并按「包含的站点/标签」筛选；标签一套通用，
  站点、账号、视图都能挂。跨站点视图在内置与外置两种表面都能启动。
- **站点即书签**：新建标签的分叉、运行栏的 ＋、地址栏输入站点名，都能按站点打开——干净
  打开或直接用某个账号打开。
- **打开账号 = 默认标签组新开一页**：点账号卡片永远在扁平标签组开一个新页面，不切进已有
  视图、不改台上的布局；要放进视图就把标签拖进去，或在视图里用「+」选账号。批量启动是唯一
  例外——它按默认布局新建一个视图，因为它本来就是「一次铺开多个」。
- **手动登录可保存**：内置页面里提交登录表单后提示保存，密码经 CDP binding 直达主进程，
  渲染层只拿一次性 token；确认后打开预填好的账号表单（站点按 origin 匹配，没有就就地新建）。
- **标签管理独立成页**：左侧导航新增「标签」页（不是设置里的 tab——标签是每天都要碰的
  东西，塞进设置等于藏起来），显示每个标签被几个站点 / 账号 / 视图用到，没人用的标签一眼
  可见；账号页与视图页的标签筛选条固定一行、横向滚动，标签再多也不改变页面高度。
- **页面缩放**：每页各自一份。Ctrl 加号/减号调当前页、Ctrl + 0 回默认；设置里一个全局默认
  缩放只会作用到没被手动调过的页面。档位沿用 Chrome 那一套。**不做按站点缩放**：站点是多
  账号共用的登录配方，按站点缩放会误伤碰巧同站点的其它账号，而用户真正要区分的是「这一格」。
- **开发者工具默认停靠**：画在这一页自己的格位里，四宫格可以各自开着；需要时一键拆成独立窗口。
  工具栏按钮跟着开/关状态高亮。
- **不出现 Electron 图标**：三个窗口都显式传应用图标，原生文件对话框以主窗口为父窗口，
  Windows 设置 AppUserModelID；`tests/app-icon.test.ts` 静态守住这三条。
- 每个身份独立 `persist:` 分区。MCP 暴露 18 个浏览器工具（含按标签 / 文字定位元素、
  页面内等待、一次填写整张表单、调整标签页顺序 / 归属视图、切换实例当前页），新增
  `open_browser_view`；布局与格位工具默认作用于台上的视图，全是扁平标签时会先分组。
  人能做的排列操作 AI 都能做——不然「让 AI 完全帮你操作」就断在最后一步。

控制通道走进程内 `webContents.debugger`，不开放任何调试端口；鉴权沿用已有的 MCP token。
页面读取只返回可见元素，因此「这个账号能看到什么」就是快照本身。

首个用途是让 AI 在一个窗口里驱动多个账号跑真实流程，人在旁边看，随时可以接手。

### 账号引用与地址变更检测

- 账号可以引用另一个站点的账号（`passwordMode: "reference"`）：用户名、密码、显示名、
  角色、颜色、备注完全同步，登录态与 profile 各自独立；改来源就同步到所有引用方。
- 引用只允许一层；断开引用时把解析出的密码落成本地 `custom`，不会回退到站点默认密码。
- 删除来源账号时，把密码物化到所有引用方后自动断开，避免留下无法启动的悬空身份。
- 站点记住最近一次成功填充的 origin；地址变了会拦住填充并请求一次显式确认。

### 视图跨站点复制

把一套编排搬到另一个站点：目标站点已有的同名账号直接复用，没有的建引用账号；
副本记录 `copiedFrom`，来源成员匹配不到的会在结果里列出。

### 账号包（分享给同事）

整机迁移用的配置导出不再兼任「把几个账号发给同事」：在账号页勾选站点或账号，导出一份
只含所选内容的账号包，口令可选。匹配键里没有 id——站点按地址、账号按用户名——所以
对方第一次见到这个站点也能导入。MCP 侧同样有 `export_accounts` / `preview_accounts` /
`import_accounts`，AI 可以把整套租户账号打完包交出去。

### 首次引导

三步向导（建站点 → 加账号 → 配视图），每步可跳过，可在设置里重播。

### 运行实例悬浮条

桌面置顶小条列出所有运行中的身份，按站点分组，点击即把对应浏览器窗口提到最前
（最小化会恢复，不重启不重载）。取代了「浏览器扩展形态的快速切换」设想：扩展要单独打包、
上架、处理扩展与本地的授权，成本高，而痛点只是切窗口。

### 会话健康中心

身份页入口，一屏按「正常 / 已过期 / 未确认」分类；支持一键检测全部、
一键为所有过期身份打开登录页并填入凭据。检测只按需触发，不做后台轮询；
没开窗口的身份用不显示窗口的后台浏览器读取该 Profile 的 Cookie 完成检测，
查完立即关闭，不会多出窗口。

### 恢复上次视图

设置项（默认关闭）。开启后冷启动等引擎扫描完成，再在内置浏览器里按原布局恢复上次
使用的视图；视图已删除则静默清理记录。

### 流程资产（可重跑的步骤序列）

AI 把一轮走通的操作存下来，下次一句话重跑：`save_flow` / `list_flows` / `run_flow` /
`delete_flow` 四个工具，界面对应左侧导航的**流程**页。动作只有 8 种
（`navigate` / `fill` / `click` / `select` / `press` / `login` / `wait` / `read`），
带参数与 `{{变量}}`，`read` 可以把页面上的值收进变量供后面步骤使用。

刻意做成**步骤清单而不是任意脚本**：人能在界面上读懂、改步骤、调顺序；校验在保存时完成；
失败即停并点名第几步。这条做完，跨会话的经验不再随上下文消失——这也是「同一套系统里多个
身份反复验证同一件事」最直接的落地方式。录制成流（面向人的回放）仍在中期，这里只做
AI 与人都能编辑的声明式步骤。

## 中期（真正的差异化）

### 身份对比

同一个 URL 用两个身份的内置标签页打开，对比可见元素与截图，直接回答
「删除按钮是不是只有管理员能看到」。

内置表面让这件事几乎白送：同一窗口、同一视口、各自截图，不用再处理窗口位置、
边框遮挡与 DPI 差异。

实现要点：

- 两侧统一视口尺寸后再截图，避免分辨率差异造成假阳性
- DOM 对比只比可见元素的角色、可访问名称与稳定选择器，不比 class 名
- 输出「A 有 B 无」「B 有 A 无」两栏，附带元素定位信息

### 权限断言

给视图配置一组断言：某元素对某身份应可见 / 不可见。一键跑完出报告，可导出为 QA 证据。

断言的表达要尽量窄，先支持两种：

- 选择器存在 / 不存在
- 选择器可见 / 不可见

底层的可见性判定已经在 `check_element_visible` 里实现，断言层只是把它按视图批量跑一遍。

不做「点击后应发生什么」这类流程断言，那会把工具推向通用 E2E 框架，与 Playwright 正面竞争且不占优势。

### 操作录制

内置表面天然适合录制：每个 view 拿到的都是干净的单标签画面，没有窗口边框、
不受其他窗口遮挡、视口精确。定位是「把 AI 跑过的一轮流程录下来给人看」，
不是屏幕录像工具。

### 会话预热与运行模式

AI 触发时默认在后台运行，需要人看时再把窗口提到前台。配合已有的会话健康检测，
让「打开就能接着用」成为默认体验。

### 日常模式：一个持久的个人档案

现在的内置浏览器默认落在 `persist:embedded-clean` 上。这个分区名字听起来干净，实际是
**所有没有身份归属的标签共用的一个持久 cookie 罐**：在 A 站登录过，同一次会话里另一个
无身份标签访问 A 站就是登录态；重启之后还在。它既不是「干净」，也不是一个稳定的个人档案。

如果目标是「除了验证，还能日常用」，这里得换成一个明确的模型：

1. **一个显式的「日常档案」分区**（`persist:embedded-daily`），与临时干净打开分开。
   日常标签默认落在它上面，登录一次就长期有效——这是"AI 能帮我做后台操作"的前提。
2. **书签是独立的一等对象**，不是站点的一部分。书签只有一个地址和名字，不要求凭据、
   不暗示登录；站点保持「登录配方」语义（见 [ADR 0008](./architecture/adr/0008-sites-as-login-recipes.md)）。
   两者靠**结果**区分就够清楚：点书签是直接打开地址（用日常档案的登录态），点站点/账号是
   打开登录页并自动填充。再加一层视觉区分（站点带身份色环与账号计数，书签只有图标与标题），
   以及一条「把当前页存成书签 / 从当前页新建站点」的双向入口——用户不用先选概念，用一次就懂。
3. **AI 在登录态上的权限要按来源收紧**，默认比现在严：
   - 每个标签一个「AI 只读」开关，默认对日常档案里**未经授权的来源**开启。只读意味着
     放行读页面、截图、导航，拦住所有 `Input.dispatch*`（点击、输入、按键）——这些调用
     本来就只有一处实现，拦截点集中。
   - 授权按来源（origin）给，不是按标签给：用户说"这个站可以操作"，说的通常就是这个意思。
   - 审计日志从「调了哪个工具」扩到「碰了哪个来源」，运行栏那一行显示本次 AI 操作次数。
     这是与"任何自带浏览器都能被 AI 驱动"的真正差别：用户看得见发生了什么。
   - 凭据不进入可达路径：AI 工具永远拿不到明文密码，`fill_browser_login` 只在账号自己的
     站点与来源上生效（已有约束，保持）。
   - 提示注入是这套设计的真实威胁模型：登录态 + AI 读页面 = 恶意页面可以试图指挥 AI。
     所以「导航目标只能来自用户或工作区数据」这条要作为硬规则，不允许页面内容直接变成
     下一步操作的目标地址。

前两项是产品价值，第三项里只有「按来源只读 + 来源级审计 + 每标签开关」是随它一起上的最低
门槛；完整的动作确认与撤销是后续版本。

## 远期（可选，取决于真实需求）

### 身份级代理

若确有跨地域访问被测系统的需求（验证地域策略、代运营场景），加 `--proxy-server` 启动参数即可。
定位是**网络路径测试**，不做成反检测能力，文档中也不使用这类措辞。

### 批量导入身份

CSV 导入：名称、账号、角色、备注。没有 AI 客户端的用户也需要批量建号。

### 自建 Chromium 分支

只有在内置表面受限于 Electron 的升级节奏、且这件事真的成为瓶颈时才考虑。
代价是长期维护 Chromium 升级、安全补丁、编解码与签名分发。

## 明确不做

| 方向 | 原因 |
| --- | --- |
| 指纹伪造与反检测 | 需自行维护改过的浏览器内核，与「真实浏览器行为」定位冲突，且用户群与开源定位不符 |
| 把内置分区当作指纹隔离手段 | 分区只隔离 Cookie 与存储，不做 canvas / WebGL / 字体伪装 |
| 通用 E2E 测试框架 | 与 Playwright / Cypress 正面竞争，没有差异化 |
| 浏览器扩展形态的切换器 | 需单独打包、上架并处理扩展授权，成本高于收益；切换痛点已由运行实例悬浮条解决 |
| 云端账号存储 | 纯本地是安全边界的一部分，密码不出本机 |
| Chrome 平替（书签、扩展商店、密码管理器、同步） | 内置浏览器的定位是 AI 优先的工作台，不跟通用浏览器比功能广度 |
